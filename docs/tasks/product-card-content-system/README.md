## 1. Цель и границы

**Цель.** Нижняя часть карточки (от hero-описания до FAQ включительно)
собирается из смысловых модулей, набор и заголовки которых определяются
классификацией позиции, а не шаблоном. Каждый модуль отвечает на отдельный
вопрос покупателя и несёт информацию, которой нет в других модулях той же
страницы. Соседние SKU одного семейства описываются согласованно и
перелинкованы.

**В границах:** классификация всех позиций; новые поля схемы (по визе);
библиотека модулей; правила выбора модулей и заголовков; контентный конвейер
(исследование вендора → генерация семейством → валидация → запись через
workflow); правка шаблона `[slug].astro` в части нижних секций; пилот.

**Вне границ (отдельные решения руководителя):** Invariant Pricing и цена
минимальной валидной конфигурации (влияет на `effectivePrice()` и Product
schema); переименование вендора ManageEngine/Zoho; конфигуратор составных
продуктов (композиция по `bizsoft-product-nonstandard-cards`); первый экран и
блок цены (утверждены 12–13.09.2026, не пересогласуются).

**Что не меняется:** блок «Как организовано взаимодействие» (`policies.ts`),
«Основные параметры» (только исправляются значения единицы и типа плана из
новых полей), H1/строка плана/блок фактов (правила `card-title.md`,
`card-lede-facts.md`).

## 2. Классификатор — пять осей

Классификация хранится в данных, читается шаблоном. Четыре оси берутся из
артикула новой системы (`parseSku`) и `sku-assignment.json`; две заводятся
новыми полями.

| Ось | Значения | Откуда |
|---|---|---|
| **OWNERSHIP** (тип плана) | `team` · `individual` · `universal` | сегмент `plan` артикула |
| **TERM** | `subscription(<n>M/Y)` · `perpetual` · `balance` | сегмент `term` |
| **METRIC** (единица расчёта) | `USER/DEV/SRV/CCU/ORG/PROJ/PACK/NOM` + человекочитаемый `unit_label` («рабочее место», «сервер», «наблюдаемый объект», «защищаемая нагрузка», «пользователь техподдержки») | сегмент `unit` + новое поле `unit_label` |
| **NATURE** (что продаётся) | `mono` — один продукт без декомпозиции · `suite` — реально состоит из продуктов/модулей · `addon` — не работает без базового продукта · `credit` — баланс/кредиты/токены · `service` — продление, поддержка, maintenance | сегмент `kind` даёт `addon/credit/gift`; `mono/suite/service` — **новое поле `product_nature`** |
| **PACKAGING** (как позиция соотносится с соседями) | `single` — единственный SKU продукта · `edition_tier` — редакция в линейке (Standard/Pro/Enterprise) · `volume_tier` — объём в линейке (10/25/50 объектов; 3 VM; 250 ГБ) · `configuration` — валидная поставка из нескольких обязательных SKU · `composite` — один SKU с внутренней обязательной структурой | **новое поле `packaging`** + `family_key` |

Дополнительные поля:

- `family_key` — `<ВЕНДОР>-<ПРОДУКТ-без-редакции/объёма>`; все SKU семейства
  генерируются и валидируются вместе. Правило образования — из
  `sku-products.json`, редакция/объём выносятся в `edition_label` /
  `volume_label`.
- `base_product_sku` — для `addon`: к чему дополнение (обязательно).
- `siblings` — вычисляется из `family_key`, не хранится.

Класс `addon` — отдельная модель, не вариант и не конфигурация базового продукта.
Связь — `requires / extends` (обратная к `included_in` у пакетов): карточка
существует сама по себе, но без базового продукта не имеет смысла. Срок и
модель лицензирования аддона **не наследуются** от базового продукта — их
задаёт разработчик аддона. Поля класса:

| Поле | Значения | Зачем |
|---|---|---|
| `addon_source` | `vendor` — дополнение самого производителя (APM у ManageEngine, дополнения Zoom) · `marketplace` — сторонний разработчик (JetBrains Marketplace) | у `marketplace` вендор карточки — автор плагина, а не владелец платформы |
| `license_model` | `free / monthly / annual / annual_fallback / perpetual / external` | единого «аддон = 1 год» не существует; сегодня все 867 `JB-PLG-*` закодированы `1Y` — ошибка данных |
| `fallback` | да/нет + что остаётся | у IDE JetBrains fallback после 12 месяцев есть, у плагинов — только если выбрал автор |
| `requires` | список продуктов/редакций/версий базового продукта | совместимость определяется не лицензией, а хостом, его версией и редакцией |
| `plugin_users` | число | лимит пользователей плагина отдельно от мест IDE |

Модуль `ADDON_SCOPE` обязан назвать базовый продукт, модель лицензирования и
что происходит после окончания срока (для `annual` без fallback — платная
функциональность отключается); co-terming со сроком IDE описывается как
удобство продления, а не свойство товара.

**Решение руководителя 13.09.2026 по плагинам JetBrains Marketplace:** все
867 позиций `JB-PLG-*` снимаются с витрины (`draft`), остаётся одна
договорная позиция «Плагин JetBrains Marketplace — по запросу» и абзац на
странице вендора JetBrains; конкретный плагин возвращается в каталог только
по заявке или по спросу выше порога экспозиции, записью в реестре решений.
Отдельное задание — `docs/tasks/jetbrains-marketplace-withdrawal.md`.
Класс `addon` в пилоте проверяется на дополнениях ManageEngine и Zoom.

Что ни одна ось **не** решает: тип плана по названию, единицу по вендору,
вид по «похожести на подписку». Спорная позиция — вопрос оператору
(`product-markers.md`).

Ожидаемая карта покрытия (проверить на этапе 0): `volume_tier` — ManageEngine,
Acronis по нагрузкам; `edition_tier` — Acronis Standard/Advanced, Adobe
Standard/Pro, JetBrains AI Free/Pro/Ultimate, ChatGPT Business/Premium;
`suite` — Maxon One, Red Giant, Adobe CC, JetBrains All Products;
`configuration` — сегодня в каталоге нет (подтвердить), заводить как DATA GAP.

### 3.1. Модули (18, а не 31: остальные — частные случаи этих)

### 3.2. Матрица «класс → модули»

| Класс (комбинация осей) | Обязательные | Допустимые | Запрещённые |
|---|---|---|---|
| `mono` + любой план | `CAPABILITIES`, `FIT`, `PLAN_COMPARE` (если есть сиблинги) | `TRADEOFFS`, `DEPENDENCIES`, `FAQ` | `INCLUDED` |
| `suite` | `INCLUDED` (название + назначение + ценность, по 1–2 строки), `FIT` | `CAPABILITIES` (только сквозные возможности пакета), `PLAN_COMPARE` | — |
| `team` (любая nature) | `TEAM_MODEL` + `TRADEOFFS` + ссылка на individual-сиблинга, если существует | `PLAN_COMPARE` | — |
| `individual` | `INDIVIDUAL_MODEL` (когда рационален + что отсутствует относительно team) + ссылка на team-сиблинга | `PLAN_COMPARE` | — |
| `addon` | `ADDON_SCOPE`, `DEPENDENCIES` (base product, версии), `FIT` («когда не нужен») | `ALTERNATIVES` | `INCLUDED`, `TEAM_MODEL`, счётчик мест |
| `credit` | `CREDIT_USAGE`, `PLAN_COMPARE` (API vs подписка), `FIT`, `BEFORE_ORDER` (срок действия, лимиты аккаунта) | `FAQ` | `INCLUDED`, `TEAM_MODEL`, «Что входит» |
| `perpetual` | `PERPETUAL_RULES`, `PLAN_COMPARE` (perpetual vs subscription) | `SUPPORT_MAINTENANCE` | формулировки «срок действия плана подписки», «Что входит в план» |
| `service` | `RENEWAL_RULES`, `SUPPORT_MAINTENANCE`, `BEFORE_ORDER` | `FAQ` | `CAPABILITIES` продукта целиком |
| `edition_tier` | `PLAN_COMPARE` (таблица редакций семейства — один источник на семейство), `FIT` | `CAPABILITIES` только для дельты редакции | повтор общих возможностей семейства в каждой редакции |
| `volume_tier` | `PLAN_COMPARE` («какой объём выбрать», правило масштабирования, доплата в течение срока) | `CAPABILITIES` (одна на семейство, у младшего объёма) | повтор описания продукта в каждом объёме |
| `addon` + `marketplace` | как `addon`; `ADDON_SCOPE` называет модель лицензирования и судьбу функций после срока; вендор — автор плагина | `BEFORE_ORDER` (co-terming) | наследование срока от IDE |
| `configuration` / `composite` | `CONFIGURATION` (обязательные, зависящие от количества, опциональные; минимальная валидная поставка) | `BEFORE_ORDER` | «Что входит» как список |

На одной странице — 4–7 модулей. Для `volume_tier` и `edition_tier` семейство
имеет **одну** карточку-носителя полного описания (младшая редакция/объём);
остальные несут только дельту и ссылку — это и есть SEO-дифференциация без
дублей.

### 3.3. Правило создания модуля (внутренняя запись до генерации)

```
MODULE:
QUESTION ANSWERED:
NEW INFORMATION (чего нет в HERO_LEDE и других модулях этой страницы):
SIBLING OVERLAP (что уже сказано у сиблинга-носителя):
DECISION SUPPORTED (UNDERSTAND / COMPARE / FIT / LIMITATIONS / VALIDATE / ACT):
SEO INTENT:
SOURCE (URL официальной документации или "uncertain"):
```

Нет `NEW INFORMATION` — модуль не создаётся. `SOURCE = uncertain` — факт
формулируется как условный и попадает в `uncertainties` выходного JSON.

### 3.4. Что запрещено везде

- Hero-абзац, начинающийся с «Что входит:», если на странице есть `INCLUDED`
  или `CAPABILITIES`: hero называет назначение и модель владения, состав —
  один раз в модуле.
- Вопросы FAQ о механике сделки (оплата, документы, ЭДО, регистрация
  аккаунта, сроки передачи доступа) — они принадлежат `policies.ts` и
  глобальному `/faq`. В карточке остаются только вопросы, ответ на которые
  зависит от вендора или позиции.
- `seo_text` как отдельное полотно: семантика распределяется по модулям;
  поле опустошается после проверки, что его интенты покрыты (п. 4, этап 2).
- Сквозные шаблонные конструкции («Кому подходит:», «Оформим на вашу
  компанию…», «Типичный сценарий») — переменная формулировка, проверка
  валидатором по каталогу.
- Клише: «мощное решение», «идеальный выбор», «широкий спектр», «в современном
  мире», «раскрывает потенциал», «инновационный», «передовой».

| `base_product_sku` | string, nullable | для `addon` |
| `addon_source`, `license_model`, `fallback`, `requires`, `plugin_users` | enum / enum / bool+string / string[] / int | класс `addon`, п. 2 |
| `content_modules` | JSON `[{code, title, kind: "prose"|"items"|"compare", body?, items?: [{t,d}], rows?: [{label, values{}}], links?: [slug]}]` | все модули нижней части, кроме `HERO_LEDE` и `FAQ` |
| `content_version` | string | версия конвейера, которой сгенерирован контент |

Существующие поля: `short_description` = `HERO_LEDE`; `faq` = `FAQ`;
`related_products` = ссылки `ALTERNATIVES`/`PLAN_COMPARE`; `description`,
`for_whom`, `use_cases`, `features`, `seo_text` — **legacy**, после миграции
семейства опустошаются (не удаляются: откат = `content_modules = null`, и
шаблон возвращается к legacy-рендеру).

Альтернатива без изменения схемы — расширять `vendor-content.ts` — отвергается:
файл уже 621 КБ, контент в коде не проходит через `catalog-watch` и
`content_updated_at`, и не виден WebMCP-слою.

### 4.2. Шаблон

`[slug].astro`: если `product.content_modules` заполнен — секции рендерятся из
него по порядку (`sec-head` с заголовком модуля, тип рендера по `kind`);
иначе — текущая legacy-ветка без изменений. `Основные параметры` берут
`unit_label`, `product_nature`, `packaging`; «Тип плана» — из сегмента
артикула. `data-composition` дополняется `data-nature` и `data-packaging`
для `ops-card-shot`. Правка проходит Design Approval Gate: макет на данных
трёх позиций разных классов (mobile+desktop), остановка, одобрение.

### 4.3. Пайплайн записи

Новый workflow `ops-apply-content` по образцу `ops-apply-descriptions`:
источник `data/content/families/<family_key>.json`, режим `apply=false/true`,
фильтр по семейству, штамп `content_updated_at`, запись в issue #22, после
массового применения — `ops-catalog-watch baseline=true`, затем
`ops-yandex-recrawl` (квота 150 URL/сутки — учитывать в графике).

## 5. Конвейер — этапы и промпты

Каждый этап — отдельная сессия или workflow; модель по `approach-check`:
классификация и валидация — Sonnet (по шаблону), профили вендоров и
генерация — Opus/Fable. Промпты хранятся в
`docs/tasks/product-card-content-system/prompts/`.

### Этап 0 — классификация (данные, без нового текста)

Вход: `ops-export-products` (все поля), `sku-assignment.json`, обход витрины
(приложение A).
Выход: `data/content/classification.csv` — по каждой позиции 5 осей,
`family_key`, `edition/volume_label`, `unit_label`, `base_product_sku`,
`confidence`, `needs_operator` (спорное — не угадывать).
Промпт-0 (суть): «Для каждой позиции определи оси по данным (артикул,
product_type, parent_sku, название, hero). Где ось не выводится из данных —
`needs_operator=true` и причина. Сгруппируй в семейства. Выведи сводку
покрытия по классам и список позиций, у которых текущая единица/плашка
противоречат классификации.»
Приёмка: 0 позиций без `family_key`; список `needs_operator` — руководителю
кнопками по группам, не поштучно.

### Этап 1 — профили вендоров и семейств

Вход: классификация; официальные источники по приоритету (сайт вендора →
документация → pricing/licensing → KB → datasheet → FAQ → партнёрская).
Выход: `data/content/vendors/<vendor>.md` — терминология вендора, линейка
редакций и объёмов, единицы, admin/security-функции командных планов,
правила продления/апгрейда, что прекращается после срока, минимумы,
совместимость, `uncertainties`.
Промпт-1 делается **один раз на вендора**, переиспользуется всеми SKU.
Приоритет по массе: ManageEngine → Adobe → JetBrains → Acronis → Microsoft →
Maxon → OpenAI/Anthropic → остальные.

### Этап 2 — генерация семейства

Вход: профиль вендора, все позиции семейства с полями, матрица п. 3.2,
текущие `short_description/description/features/faq/seo_text` каждой позиции
(для переноса семантики, не для копирования).
Выход: `data/content/families/<family_key>.json` — на каждую позицию:
`short_description` (HERO_LEDE, ≤330 видимых + до 3× под «Подробнее»),
`content_modules[]`, `faq[]` (0–5, только вендорно-специфичные),
`related_products[]`, `meta_title` ≤60, `meta_description` ≤160,
`seo_intents` (что покрыто, откуда перенесено), `uncertainties`,
`module_log` (записи по п. 3.3).
Промпт-2 требует: сначала выбрать карточку-носитель семейства; затем для
каждой позиции — записи п. 3.3; затем текст; в конце — дедупликация внутри
семейства (тезис живёт там, где раскрыт лучше; повтор допустим только для
срока, количества, цены, критических ограничений и CTA).

### Этап 3 — валидация (детерминированная, скрипт + один LLM-проход)

Скрипт `scripts/content/validate-family.mjs`:
- схема JSON, коды модулей из библиотеки, обязательные/запрещённые по классу;
- лимиты: hero видимая часть ≤360 знаков, meta ≤60/≤160, модуль 400–1400
  знаков, FAQ ≤5;
- запрещённые фразы и клише (список в `data/content/banned-phrases.json`);
- пересечение тезисов между модулями одной страницы и между сиблингами
  (совпадение ≥ 8 слов подряд или ≥ 0,6 по косинусу эмбеддингов);
- каталожная частота вступительных конструкций (любая конструкция > 5 %
  карточек — ошибка);
- единица в тексте = `unit_label`; цена/минимум в тексте = данным;
- у `addon` назван `base_product_sku`; у `credit` нет слов «место»,
  «подписка на пользователя»; у `perpetual` нет «срок действия подписки»;
- все `related_products` существуют и опубликованы;
- уникальность meta по каталогу (`catalog-uniqueness`).
LLM-проход отвечает на один вопрос по каждой странице: «какой вопрос
покупателя остался без ответа и какой модуль отвечает на вопрос, уже
закрытый выше».

### Этап 4 — пилот

Восемь семейств, взвешенных по массе каталога и покрывающих все классы:

1. ManageEngine OpManager — `volume_tier` + `addon` (APM Plugin) + `edition_tier`
2. Acronis Cyber Protect — `edition_tier` (Standard/Advanced) × `volume_tier`/METRIC (WS/Server/VHost/3VM)
3. Adobe Creative Cloud — `suite` + `team`/`individual`
4. Maxon Red Giant / Maxon One — `suite` + `team`/`individual` (эталон 12.09.2026)
5. JetBrains All Products Pack + одна IDE — `suite` против `mono`, `team`
6. OpenAI: API Balance + ChatGPT Business/Premium — `credit` против `edition_tier`
7. Parallels Desktop Standard perpetual + подписочный сиблинг — `perpetual` vs `subscription`
8. Одна позиция без цены (`quote_only`) — граница применимости

Порядок: этап 0 по всему каталогу → этап 1–3 по восьми семействам → макет
(Design Approval Gate) → `ops-apply-content apply=false` → одобрение →
`apply=true` → `ops-card-shot` по одной позиции каждого класса →
`ops-yandex-recrawl` → 28 дней наблюдения через `seo-daily-report`
(кластер под пилотом — без сниппет-экспериментов, правило
`snippet-experiments.md`). Только после этого — масштабирование по
семействам, приоритет по массе.

### Этап 5 — масштабирование и сопровождение

Новая позиция без `content_modules` рендерится legacy-веткой и попадает в
очередь генерации по `family_key`. Изменение профиля вендора → регенерация
семейств вендора. `content_version` позволяет найти страницы старого
конвейера.

## 6. Критерии качества (приёмка страницы)

Бинарные (валидатор): все проверки этапа 3 — зелёные.
Экспертные (руководитель, по макету): каждый модуль отвечает на новый
вопрос; сосед по семейству узнаваем и отличим за 10 секунд; ни одна фраза не
воспринимается как повторённая с другой карточки; страница `credit`/`addon`/
`perpetual` не выглядит как подписка на места.
