# Канал заявки: как он определяется и как его читать

Документ отвечает на вопрос руководителя от 01.09.2026: «Из каких каналов
приходили заявки — из рекламы Директа, из органики, из фидов или откуда?»

## Две разные записи об одном и том же

У каждой заявки есть **два** описания источника, и они не равны друг другу.

**1. Метка браузера** — то, что видно в письме менеджеру («Канал», «Первое
касание», «Вход на сайт»). Пишется на сайте (`src/lib/attribution.ts`),
хранится в localStorage посетителя 90 дней и приезжает вместе с заявкой в
воронку. Формула канала (`src/lib/quote-lead.ts`, `attributionFields`)
такая:

| Что нашли в визите | Что окажется в строке «Канал» |
|---|---|
| `utm_source` (+`utm_medium`) | `<источник> / <канал>` |
| `yclid` без utm | `yandex / cpc` |
| `gclid` без utm | `google / cpc` |
| только реферер | `<хост реферера> / referral` |
| ничего | пусто — «не определён» |

Отсюда главное ограничение: **строка `хост / referral` не означает
«переход по ссылке» в терминах Метрики.** Органический переход из Яндекса
даёт `yandex.ru / referral`, из Google — `www.google.com / referral`, ровно
так же, как переход из Яндекс.Карт или из чужого корпоративного портала.
Метка знает реферер и не знает, была это выдача или сервис.

Что метка различает надёжно: рекламу (у клика Директа всегда есть `yclid`,
у Google Ads — `gclid`) и любую размеченную ссылку (utm). Поэтому
утверждение «эта заявка **не** из рекламы» по метке делать можно, а
«эта заявка из органики» — нельзя.

**2. Визиты Метрики** — восстанавливаются по `ym_client_id`, который форма
кладёт в заявку. Прогон `ops-leads-collect` запрашивает у Stat API визиты
этого посетителя за 90 дней (`ym:s:clientID`) с источником
(`ym:s:lastTrafficSource`), поисковой системой и страницей входа. Это и есть
классификация каналов: `ad` — реклама, `organic` — поиск, `referral` —
переход по ссылке, `direct` — прямой заход, `social`, `messenger`,
`internal`.

В письме Growth Intelligence канал всегда идёт с основанием: «Метрика» или
«метка браузера». Это разной силы утверждения, и смешивать их в одну строку
нельзя.

## Товарные фиды

Фиды (`/yandex-products.yml`, `/yandex-business.xml` и остальные) на проде
закрыты и отдают 404 (`docs/yandex-feeds.md`), открывает их только
руководитель. Значит **заявок из фидов сейчас быть не может**: канала нет
физически. Классификатор (`scripts/seo/leads.py`, метки `market`, `yml`,
`feed`, `business`) фид всё равно различает — чтобы первая же заявка после
открытия площадки не была записана в «переходы по ссылкам».

## Где что лежит

| Что | Где |
|---|---|
| Метка источника у заявки | Directus, коллекция `leads`, поля `utm_*`, `yclid`, `gclid`, `first_touch_source`, `last_touch_source`, `landing_path`, `ym_client_id` |
| Выгрузка для отчёта | `reports/seo/data/leads-<дата>.json` (ветка `seo-data`), прогон `ops-leads-collect` |
| Классификация и тексты | `scripts/seo/leads.py` |
| Блок письма | «Заявки за сутки» в `report_v4.py`; показатель «Обращения» — там же |
| Заявки живьём | `/admin/leads` |

## Чего в выгрузке нет

Персональных данных: имени контакта, телефона, почты, текста обращения. С
сервера уходят только реквизиты юрлица (компания, ИНН), состав запроса,
сумма, метки источника и путь визитов — витрина живёт в репозитории, и ПДн
там не место. По той же причине блок с компаниями есть только в письме:
веб-отчёт (страница по непубличному адресу) показывает лишь число обращений
и распределение по каналам.

## Что этим измеряется, а что нет

Измеряется: сколько заявок пришло, из какого канала и каким путём клиент
дошёл до запроса. Не измеряется: сделки и выручка — стадии воронки
(«оплачено», «отказ») двигает менеджер вручную, брать их как факт рано.
В проверках качества это отдельная находка `NO_CRM_REVENUE`.
