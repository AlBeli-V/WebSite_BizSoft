## 1. Что это за система и чего она не делает

Система отвечает на пять вопросов ежедневно: усиливается ли BIZSoft в
коммерческой B2B-выдаче, кто забирает потенциальные сделки, на каких
запросах, где позиции конкурентов уязвимы и какие действия быстрее всего
перераспределят видимость в нашу пользу.

**Границы, заданные принципиально.** Система только наблюдает и
рекомендует: сайт не меняется автоматически, порядок работы —
наблюдение → анализ → рекомендация → проверка → измерение. Не используется
обход капчи, авторизации и антибот-защит; краулинг конкурентов ограничен
пятнадцатью доменами с соблюдением robots и задержек. Демпинг не
предлагается, причинно-следственные утверждения без данных не делаются.

**Ключевое ограничение достоверности.** Главный показатель — доля
взвешенной поисковой видимости. Это **не доля рынка, не доля трафика и не
доля выручки**. Он измеряет присутствие в контролируемом наборе
коммерческих запросов, взвешенное по вероятности клика.

## 2. Сбор данных: что, откуда, с какой периодичностью

### 2.1 Источники и их роли

| Источник | Что даёт | Как получаем | Периодичность |
|---|---|---|---|
| Яндекс, выдача TOP-20 | позиции всех доменов по коммерческим запросам | Yandex Cloud Search API (deferred-режим), собирает базовый SEO-контур | ежедневно, 01:37 МСК |
| Google, выдача | то же для Google | DataForSEO SERP API | еженедельно (не запущено) |
| Яндекс.Вебмастер | показы наших запросов — запасная мера спроса | API v4, собирает базовый контур | ежедневно |
| Яндекс.Wordstat | частотность запросов — основная мера спроса | Yandex Cloud API, собирает базовый контур | ежедневно |
| Directus | каталог: вендоры, товары, цены | REST через SSH | по требованию |
| Яндекс.Метрика, GA4 | калибровка выручки, проверка эффекта | API | не подключено (этап 5) |

### 2.2 Принцип неповторной закупки

Срезы выдачи Яндекса **читаются из хранилища базового SEO-контура только на
чтение** (`git show origin/seo-data:...`). Контур конкурентной разведки не
покупает те же снимки повторно и не пишет в чужое хранилище. Докупаются
только данные, которых там нет: Google и, при необходимости, дополнительные
регионы.

Экономический контроль: жёсткий месячный потолок 20 долларов на Google,
автоматическое сокращение объёма при достижении 80% и полная остановка
закупок при 100%, с обязательным предупреждением в письме. Учёт ведётся по
журналу дозаписи, повторный запуск в тот же день не удваивает расход.

### 2.3 Ограничение по географии Google

У Google **отсутствует геотаргетинг России** — локаций РФ нет ни в
live-выдаче, ни в базе провайдера (проверено контрольным вызовом 31.08:
метод работает, по российским доменам данных нет). Google снимается через
ближайшую доступную русскоязычную локацию. В каждом отчёте это помечается;
**сравнивать позиции Яндекса и Google как равноточные запрещено**.

### 2.4 Обращение с отсутствующими данными

Отсутствие данных никогда не превращается в ноль. Сбой источника
записывается как ошибка в отдельном поле и исключается из расчётов, а не
занижает чью-либо видимость. В интерфейсах пишется «нет данных» словами.

Практический случай: 31.08 сбор базового контура вернул ошибку по всем 502
запросам. Система не показала это как обвал видимости и не промолчала —
письмо ушло с вердиктом «недостаточно данных» и прямым указанием причины,
даты сбоя и того, за какое число показаны цифры.

## 3. Обработка и вычисления

### 3.1 Взвешенная видимость — базовая величина

Для каждого домена на каждой позиции берётся вес по зафиксированной кривой
CTR и суммируется по всем запросам среза:

```
видимость(домен) = Σ  CTR_вес(позиция) × коэффициент_SERP_элементов
                     × вес_спроса × коммерческий_интент × B2B_интент
```

Кривая CTR (доля кликов по позиции): 1-е место — 0,28; 2-е — 0,15;
3-е — 0,10; 5-е — 0,05; 10-е — 0,018; 20-е — 0,004; вне ТОП-20 — ноль.
Кривая вынесена в конфигурацию, а не зашита в код, и подлежит калибровке по
фактическим показам и кликам, когда накопится история.

Коэффициент SERP-элементов понижает органический CTR, когда выдачу занимают
крупные блоки: AI-ответ — 0,6; товарная галерея — 0,75; быстрый ответ — 0,8.
Берётся сильнейший из присутствующих, а не произведение — иначе получился бы
двойной счёт.

Множители спроса и интента по умолчанию нейтральны (равны единице), пока
разметка не подключена; текущий расчёт помечен как «базовый».

**Доля видимости** = видимость домена ÷ суммарная видимость поля.
При пустом поле возвращается «нет данных», а не ноль.

**Наш домен исключён из всех конкурентных срезов**: доли категорий
показывают, сколько держат конкуренты, наша доля стоит отдельной величиной.
Поэтому сумма долей категорий меньше 100%.

### 3.1а Поле измерения: версия ядра запросов и две доли

Доля считается **внутри поля**, а поле задаётся списком запросов
мониторингового ядра. Отсюда следствие, которое до версии 1.3.0 нигде не было
записано: редактирование собственного списка запросов двигает долю так же,
как движение конкурентов. Добавили в ядро десять запросов, где нас нет, —
доля упала, хотя в выдаче ничего не произошло. Убрали такие запросы — доля
выросла.

Поэтому каждый снимок дня фиксирует состав ядра:

- **отпечаток** `ядро_хеш` — sha256 по отсортированному нормализованному
  списку запросов, первые 12 hex-символов. Одинаковый отпечаток означает
  буквально тот же набор;
- **версию** `ядро_версия` — человекочитаемый номер (v1, v2, …) из
  append-only реестра `data/competitive/query-sets.json`;
- **сам список запросов** и **взвешенную видимость по каждому запросу**
  (наша и всего поля) — чтобы долю можно было пересчитать по любому
  подмножеству задним числом.

Из этого следуют **две разные величины**, которые нельзя подменять одна
другой:

| Величина | Что означает | Где используется |
|---|---|---|
| **Доля в текущем поле** | сколько мы весим сегодня среди сегодняшнего состава запросов | показывается как B2B Share в письме и отчёте |
| **Сравнимая доля** | та же величина, пересчитанная по пересечению составов сравниваемых дней | единственное основание для динамики, дельт и вердикта |

Пока состав ядра не менялся, оба числа совпадают. Как только ядро
редактируется, они расходятся, и разница между ними — ровно тот эффект,
который иначе выглядел бы как движение конкурентов.

**Правила динамики при смене ядра:**

1. Дельта доли и ряд для тренда считаются по пересечению составов; основание
   дельты подписывается явно («то же ядро» или «пересечение ядер:
   N запросов»).
2. Если пересечение меньше **70%** текущего ядра, динамика не считается
   вовсе: сравнимого поля фактически нет.
3. Для конкурентов пересчёт по подмножеству недоступен — по-доменная
   видимость по каждому запросу не хранится, — поэтому там действует более
   грубое правило: компонент динамики Threat включается только если состав
   ядра во всех днях ряда совпадал.

### 3.2 Классификация доменов

Восемь категорий: прямые B2B-реселлеры, малые B2B-реселлеры, крупные
интеграторы, профильные реселлеры, B2C и маркетплейсы, официальные сайты
вендоров, информационные площадки, платёжные посредники.

Категория «платёжные посредники» добавлена к исходному заданию по факту
наблюдения: по срезу 30.08 эта группа держит 31,9% взвешенной видимости —
больше, чем все B2B-реселлеры вместе, — и перехватывает тот же коммерческий
интент.

**В основной конкурентный рейтинг входят** первые четыре категории и
платёжные посредники. B2C, информационные площадки и официальные сайты
вендоров остаются в данных и в отчёте (они забирают клики), но не могут
стать «главным конкурентом»: с ними мы не конкурируем за сделку.

Домены официальных сайтов подтягиваются из реестра вендоров сайта, чтобы не
вести второй список. Неопознанные домены помечаются как «не
классифицировано» и в рейтинг молча не попадают — на срезе 30.08 таких 137
из 234.

### 3.3 B2B Confidence Score (0–100)

Оценка того, умеет ли конкурент продавать юридическим лицам. Сигналы
объединены в четыре группы с лимитом 25 баллов каждая:

| Группа | Что показывает | Сигналы |
|---|---|---|
| Готовность к оплате | принимает ли деньги от организации | счёт, безнал, реквизиты |
| Документальная готовность | закроет ли сделку документами | договор, НДС, закрывающие, ЭДО |
| Корпоративное лицензирование | продаёт ли на компанию | лицензирование, тарифы для команд |
| Процесс B2B-продажи | ведёт ли покупателя-юрлицо | КП, менеджер, тендеры, формулировки про юрлиц |

**Как считается.** Каждый признак имеет собственный вес: оплата по счёту —
18, формулировки про юридических лиц — 14, договор — 12, закрывающие
документы — 12, НДС — 10, ЭДО — 10, корпоративное лицензирование — 10,
реквизиты — 8, безналичный расчёт — 8, запрос КП — 8, тарифы для команд — 8,
тендеры — 6, персональный менеджер — 4.

Внутри группы веса сработавших признаков суммируются, **и сумма
ограничивается лимитом группы в 25 баллов**. Наличие группы не означает
автоматических 25: если сработал один слабый признак, группа даст его вес, а
не лимит. Итоговый Score — сумма четырёх ограниченных групп, максимум 100.

Воспроизводимый пример. Страница содержит: оплату по счёту, договор, НДС,
ЭДО, корпоративное лицензирование и запрос КП.

| Группа | Сработало | Сумма весов | После лимита |
|---|---|---|---|
| Готовность к оплате | счёт (18) | 18 | 18 |
| Документальная готовность | договор (12) + НДС (10) + ЭДО (10) | 32 | **25** |
| Корпоративное лицензирование | лицензирование (10) | 10 | 10 |
| Процесс B2B-продажи | запрос КП (8) | 8 | 8 |

Итог: 18 + 25 + 10 + 8 = **61**. Не 100 — потому что три группы из четырёх
покрыты лишь частично: нет безнала и реквизитов, нет тарифов для команд, нет
менеджера и тендеров.

**Почему группы, а не общая сумма.** В версии 1.0.0 веса складывались без
группировки (в сумме 128 с обрезкой до 100), и близкие признаки — счёт,
безнал, реквизиты — быстро давали максимум: страница с несколькими похожими
формулировками выглядела готовой к B2B сильнее, чем есть. Группировка
отражает, что готовность к оплате, документальная готовность, лицензирование
и процесс продажи — разные измерения, и сильная одна не заменяет остальные.
Проверка: страница только про оплату набирает 25 из 100.

Оценка объяснима: в карточке хранятся сработавшие сигналы и адреса
страниц-доказательств. Переоценка не реже одного раза в 30 дней. **Сейчас не
вычисляется**: требует обхода страниц конкурентов, запланирован отдельным
этапом; в интерфейсах стоит «нет данных», а не ноль.

**Как Confidence соотносится с классификацией.** Это разные инструменты, и
один не подменяет другой. Категория определяет **тип** конкурента и его
участие в основном рейтинге. B2B Confidence **подтверждает степень
готовности** обслуживать сделку с юридическим лицом. После подключения обхода
порог 60 будет означать статус «B2B подтверждён», но сам по себе не исключит
домен ни из наблюдения за выдачей, ни из основного рейтинга: реселлер с
оценкой 42 останется конкурентом своей категории, просто с явно низкой
подтверждённостью. Отдельное решение — нужен ли порог 60 для отнесения к
бизнес-конкурентам — принимается после первых замеров на реальных страницах,
а не назначается заранее.

### 3.4 Threat Score (0–100) — насколько конкурент опасен сейчас

Три компонента, измеряющие разные аспекты угрозы. Они разнесены по смыслу,
но статистически независимыми не являются: домен с высокой видимостью чаще
оказывается и выше нас. Это допустимо — намеренного тройного счёта одного и
того же признака, как в версии 1.0.0, здесь уже нет.

- **Присутствие — до 50 баллов.** Взвешенная видимость: где и как высоко
  домен вообще стоит.
- **Превосходство над нами — до 20 баллов.** Доля запросов, где он стоит
  выше BIZSoft. Это относительная характеристика положения конкурента к нам,
  а не повтор абсолютной видимости; компоненты могут коррелировать, но
  используют разные признаки. Когда счётчик «выше нас» недоступен,
  применяется приближение по ТОП-3 — и это указывается в объяснении оценки.
- **Динамика — до 30 баллов.** Изменение доли между сравнимыми окнами.

**Формулы компонентов заданы явно (1.3.0).** До этой версии они описывались
словами, и поведение на краях приходилось выводить из кода:

```
присутствие(доля)              = 50 · min(доля / 0,15, 1)              → [0; 50]
превосходство(выше_нас, n)     = 20 · min(выше_нас / n, 1)             → [0; 20]
динамика(Δ п.п.)               = 30 · min(max(Δ, 0) / 2,0, 1)          → [0; 30]
```

где `n` — число запросов поля, `Δ` — изменение доли между окнами в
процентных пунктах. Все три функции монотонно не убывают по своему аргументу,
насыщаются в точке, вынесенной в конфигурацию, и не могут стать
отрицательными.

**Поведение при отрицательной динамике задано явно: компонент равен нулю.**
Конкурент, теряющий долю, не становится безопаснее тех позиций, которые
занимает сегодня, — но и не получает добавки за падение. Отрицательное
значение компонента означало бы, что падение уменьшает угрозу ниже текущего
присутствия, а присутствие уже измерено первым компонентом. Само изменение не
теряется: оно хранится рядом как `динамика_пп` и показывается со знаком,
поэтому «падает» и «стоит на месте» различимы в отчёте, хотя обе ситуации
дают ноль баллов.

Насыщение присутствия — на 15% доли, насыщение динамики — на 2,0 п.п.
Это точки насыщения функций по текущей конфигурации поля, подлежащие
эмпирической калибровке, а не утверждения об уровне лидерства.

**Что исправлено в 1.1.0.** В версии 1.0.0 счёт складывался из доли, ТОП-3 и
ТОП-10 — то есть одно преимущество учитывалось трижды: позиция уже входила
весом в долю видимости, затем отдельно как ТОП-3, затем ещё раз как ТОП-10
(тройка входит в десятку). Модель непропорционально усиливала верхние
позиции, и объяснить это было нечем. Кроме того, динамика считалась «за
сутки» — вторая, несогласованная модель, из-за которой Threat реагировал на
шум, отбрасываемый основным фильтром. Теперь динамика использует то же
сглаживание 3×3.

**Два режима зрелости и запрет сравнения через их границу.** Пока сравнимых
измерений меньше шести, динамика не считается вовсе, и оценка живёт на шкале
**0–70** (присутствие плюс превосходство). Полная шкала **0–100** включается
только с появлением истории. **Тот же запрет действует при смене состава
ядра**: если между измерениями ядро редактировалось, ряд долей несопоставим,
динамика не считается, и оценка остаётся в базовом режиме — причина
указывается в объяснении («состав ядра менялся»).

Это не косметика. В версии 1.1.0 вес динамики просто не добавлялся, и оценка
32 из достижимых 70 выглядела как 32 из 100. При переходе к полному режиму то
же самое положение конкурента давало бы 62 — руководитель увидел бы удвоение
угрозы, хотя изменилась не обстановка, а зрелость модели. Теперь режим
хранится рядом с числом (`base_0_70` или `full_0_100`), и сопоставлять оценки
через его границу запрещено методикой и различимо в данных.

### 3.5 Разметка интента запроса (0–1)

Два независимых измерения.

**Коммерческий интент**: маркеры покупки (купить, оплата, цена, тариф,
подписка, лицензия, продление, счёт и другие). Один маркер даёт 0,7, два и
более — 1,0. Информационные маркеры («как», «что», «обзор», «аналоги»,
«бесплатно») понижают результат на 40%, но не обнуляют: «как купить figma
для компании» остаётся покупательским запросом.

**B2B-интент**: сильные маркеры (юридическое лицо, по счёту, безнал, НДС,
закрывающие, ЭДО, договор, тендер, корпоративный) дают полный вес; слабые
(business, team, enterprise, для компании) — половину, потому что «business»
чаще относится к названию тарифа, чем к покупателю.

Брендовые запросы BIZSoft исключаются из конкурентного поля.

### 3.6 Измерение спроса и две шкалы

Основной источник — частотность Wordstat. На срезе 30.08 она покрыла лишь
7 запросов из 150 (ядро мониторинга строится в том числе из запросов
Вебмастера, которых в базе Wordstat нет).

Поэтому подключён запасной источник — показы Яндекс.Вебмастера, покрывшие
143 запроса. **Шкалы нормируются раздельно**: насыщение по частотности
Wordstat — 1000, по показам Вебмастера — 200. С версии 1.3.0 оба порога
вынесены из кода в `scoring/config.json` (раздел «спрос») — это параметры
калибровки, а не константы природы, и держать их только в коде значило
прятать допущение. Пороги подобраны по наблюдаемому распределению и подлежат
пересчёту по перцентилям, когда накопится история наблюдений. Это принципиально: частотность
меряет весь рынок за месяц, показы — только ту его часть, где нас уже видно,
за две недели. Источник указывается в каждой строке; смешивать их молча
нельзя.

**Отсутствие данных о спросе не подменяется средним значением.** В версии
1.0.0 неизвестный спрос давал 0,5 — то есть незнание превращалось в «средний
спрос», хотя за ним могло стоять и 5 запросов, и 50 000. Это противоречило
собственному правилу системы «нет данных не равно нулю», просто в другую
сторону. Теперь фактор исключается из расчёта, веса известных факторов
нормализуются до 100%, а уверенность понижается на ступень.

### 3.7 Business Opportunity Score (0–100)

Основной показатель выбора цели. Состав весов в версии 1.1.0: коммерческий
интент — 20%, B2B-интент — 20%, близость позиции — 15%, спрос — 15%,
уязвимость конкурента — 15%, запас улучшения страницы — 10%, приоритет
вендора — 5%.

**Экономический фактор изъят.** В версии 1.0.0 он присутствовал как
прокси-выручка с весом 20% и считался как спрос × коммерческий интент — при
том что спрос и коммерческий интент входили в сумму ещё и напрямую. Один и
тот же признак давал баллы дважды, и модель скрытно переоценивала
высокочастотные запросы: при спросе 1000 против 100 разница набегала и через
слагаемое выручки, и через слагаемое спроса. Экономический фактор вернётся,
когда появится измеренная выручка из Метрики и GA4, а не её подобие.

**Одно правило на любое число недоступных факторов (1.3.0).** До этой версии
недоступность уязвимости обрабатывалась вручную — заранее заданной второй
таблицей весов, где вес уязвимости раздавался трём выбранным факторам, — а
недоступность любого другого фактора обрабатывалась пропорциональной
нормализацией. Два механизма на одну ситуацию давали результат, зависящий от
того, какой именно фактор пропал и в каком порядке. Теперь правило одно:

```
активный набор = факторы с известным значением и ненулевым весом
масштаб        = 100 / сумма весов активного набора
оценка         = Σ (вес × масштаб × значение) по активному набору
```

Ни один вес не передаётся конкретному фактору: недостающая масса
распределяется пропорционально между всеми оставшимися. Правило применяется
**одной операцией**, поэтому результат не зависит ни от порядка исключения,
ни от того, исключались факторы поштучно или сразу — это проверяется
инвариант-тестом на коммутативность. Перечень недоступных факторов хранится
рядом с оценкой и входит в ключ сравнимости.

Сейчас недоступна уязвимость конкурента (требует обхода его страниц),
поэтому фактических весов шесть, а **уверенность не может быть выше
средней**; каждый дополнительный отсутствующий признак понижает её ещё на
ступень.

**Сравнимость между датами.** Opportunity 82 сегодня и 82 после подключения
обхода конкурентов — математически разные числа: при недоступном факторе веса
остальных нормализуются. Поэтому каждая оценка несёт режим и перечень
недоступных факторов, а правило звучит так: *оценки сравнимы между датами
только при одинаковой версии модели и одинаковом режиме доступности факторов;
при включении ранее недоступного фактора начинается новая базовая линия, и
изменение оценки через границу режима не интерпретируется как изменение самой
возможности*. Версия модели и состояние зрелости сохраняются в каждом снимке
дня.

Близость позиции: 4-е место и выше — максимум; далее линейное убывание до
20-го; вне ТОП-20 — ноль (с такого разрыва одной правкой страницы не
доходят).

Запас улучшения страницы: страница есть и стоит ниже третьего места —
максимум (правка даёт эффект быстрее создания новой); страница в ТОП-3 —
0,2 (улучшать почти нечего); страницы нет — 0,5 (потенциал есть, но дороже).

**Прокси-выручка не рассчитывается и не используется нигде** — ни в
Opportunity, ни в ранжировании пакетов, ни в выборе главного действия. В
версии 1.0.0 она существовала как спрос × коммерческий интент и создавала
двойной счёт; в 1.1.0 изъята целиком, а не переведена в справочные.
Экономический фактор вернётся, когда появятся фактические данные о
конверсиях и выручке из Метрики и GA4.

### 3.8 Отбор точек атаки

Кандидатом становится **коммерческий небрендовый запрос**, где BIZSoft
находится на позиции с 4-й по 20-ю и выше него в пределах ТОП-10 присутствует
хотя бы один **значимый участник выдачи**.

Значимый участник определяется машинно проверяемым условием: любой внешний
органический результат, кроме нашего домена, технических доменов поисковой
системы (перечень в конфигурации) и повторов домена, уже встреченного выше в
этой же выдаче — второй результат того же сайта не удваивает конкуренцию.

Отобранный кандидат затем **классифицируется по виду конкуренции**:

- **конкуренция за сделку** — выше нас стоит участник основного бизнес-
  рейтинга, то есть компания, способная продать тому же покупателю;
- **конкуренция за клик** — выше нас только иные участники выдачи
  (официальный сайт вендора, статья, маркетплейс, а также домен, который мы
  ещё не классифицировали): переход они перехватывают точно, а сделку
  забирают реже и другим способом — производитель может продать напрямую,
  маркетплейс увести в частную покупку. Утверждать «сделку они не заберут»
  модель не вправе: она этого не измеряет. Она утверждает лишь, что признаков
  B2B-продажи у такого участника **не подтверждено**.

**Правило для неклассифицированных доменов задано явно (1.3.0):** конкурент
за клик — да, конкурент за сделку — нет. Несимметрично намеренно. Ошибка в
сторону «за клик» безобидна: домен попадает в перечень стоящих выше нас, и мы
его видим. Ошибка в сторону «за сделку» дороже: неизвестный домен стал бы
главным конкурентом письма без единого подтверждённого признака.
Неклассифицированные домены считаются отдельным счётчиком в снимке и
подлежат ручной проверке — молча в рейтинг они не попадают.

Намеренно не кандидаты: запросы, где мы уже в ТОП-3 (отбирать нечего) и где
нас нет в ТОП-20 вовсе (это работа по созданию страниц, а не атака).

**Различаются два вида конкуренции** (введено в 1.1.0). Если выше нас стоит
компания с подтверждёнными признаками B2B-продажи, — на кону *сделка*. Если
выше только участники без таких признаков — переход мы теряем точно, и это
тоже потеря: *конкуренция за клик*. В
версии 1.0.0 такие запросы выбрасывались из поля зрения целиком, что и было
отмечено внешним аудитом. Теперь они остаются кандидатами с пометкой вида
конкуренции, а приоритет при равной выгоде отдаётся сделке.

На срезе 30.08 из 150 запросов отобрано 66 кандидатов: 59 с конкуренцией за
сделку и 7 за клик — последние прежде терялись.

### 3.9 Пакеты работ — единица управленческого решения

Шестьдесят шесть точек атаки невозможно поручить: это витрина, а не задача.
Поэтому они сводятся в пакеты по **странице**: одна доработка закрывает
несколько запросов сразу, и именно её можно поручить и принять.

Для каждого пакета вычисляется:

- охват: сколько запросов закрывает. **Абсолютный спрос показывается
  раздельно по источникам и не суммируется между ними даже в интерфейсе**:
  «1370» из 700 запросов рынка в месяц и 670 показов нам за две недели
  визуально складывало бы несовместимые величины, даже когда математика уже
  разведена. В письме и отчёте пишется, например: «спрос: 149 (показы
  Вебмастера, за две недели) по 11 запросам»;
- текущий диапазон позиций и список конкурентов выше нас;
- **индекс потенциала**: Σ (вес_ТОП-3 − вес_текущей_позиции) ×
  нормированный_спрос, где **вес_ТОП-3 принимается равным CTR-весу третьей
  позиции (0,10)**. Это сознательно консервативный выбор: индекс оценивает
  потенциал достижения нижней границы тройки, а не первого места, и потому не
  завышает ожидания. Безразмерная величина для сравнения пакетов между
  собой. Метка «высокий / средний / низкий» ставится относительно — по месту
  в текущем наборе, а не по абсолютному порогу: величина индекса зависит от
  конфигурации кривой CTR и от источника спроса, поэтому сравнивать её с
  фиксированным числом было бы произволом;
- **покрытие спроса** вида «3/5» — по скольким запросам пакета спрос
  измерен. Индекс считается **только по этим запросам**, и это указывается
  рядом с ним. До версии 1.3.0 запрос с неизмеренным спросом входил в сумму
  с нулевым весом, то есть молча приравнивался к запросу без спроса — то же
  самое «нет данных = 0», которое система запрещает себе в остальных местах.
  Если спрос не измерен ни по одному запросу пакета, **индекс не считается
  вовсе**: метка «не оценён», пакет уходит в конец очереди и остаётся видимым
  как задача на доизмерение спроса, а не как задача без ценности. Главным
  поручением дня такой пакет стать не может;
- **оценка прироста переходов** — только там, где весь спрос группы измерен
  сопоставимой шкалой, то есть частотностью Wordstat. Иначе величина не
  вычисляется вовсе и вместо неё указывается причина;
- **список действий**: что сделать, где править, почему и как принять — см.
  раздел 3.9а;
- трудоёмкость: до трёх запросов — малая, до шести — средняя, далее большая;
- уверенность: берётся худшая из оценок группы;
- конкретное действие и чеклист приёмки.

Формулировки действий привязаны к типу страницы (страница вендора, карточка
товара, статья) и всегда конкретны. Формулировки вида «улучшить SEO» и
«усилить контент» запрещены и **проверяются автоматическим тестом**: их
нельзя поручить и нельзя принять.

Порядок пакетов — по убыванию индекса потенциала.

**Что исправлено в 1.1.0 — главный дефект прежней версии.** В 1.0.0 прирост
переходов считался по спросу из разных источников: для одних запросов это
была частотность Wordstat (объём рынка за месяц), для других — показы
Вебмастера (сколько раз показали нас за две недели). Числа складывались в
одну сумму, которая называлась «ожидаемым приростом переходов». Это разные
знаменатели, и такая сумма не имеет физического смысла. Теперь величины
разведены: индекс потенциала служит для сравнения пакетов между собой,
переходы называются только при сопоставимой шкале. **Уточнение 1.3.0:**
формулировка «индекс считается всегда» была неверной — при полностью
неизмеренном спросе он не считается, см. правило покрытия спроса выше.

### 3.9а Управленческие воздействия: из чего состоит поручение

**Что было не так до версии 1.4.0.** Действие выбиралось по типу страницы:
статья → «добавить коммерческий блок», карточка → «довести условия для юрлиц».
Руководитель открыл первое поручение и увидел, что оно неверно: в статье про
Depositphotos уже стояли ссылки на три карточки товара, на страницу вендора,
на документы и FAQ из шести вопросов. Система советовала сделать сделанное,
потому что в саму страницу не заглядывала. Поручить такое нельзя — непонятно,
что именно и в каком файле менять.

**Что делает система теперь.** Перед формированием действий она читает
содержимое страницы из репозитория — ровно то, что правит редактор:

| Тип страницы | Что читается | Что остаётся непроверенным |
|---|---|---|
| статья блога | `src/content/blog/<slug>.md`: заголовки, текст, FAQ, ссылки | ничего, текст доступен целиком |
| страница вендора | `src/data/vendors.ts` (tagline, about) и bespoke-страница, если она есть | тело страницы собирается из Directus |
| карточка товара | `data/seo/product-descriptions.json`: описание и мета | остальное тело карточки приходит из Directus |

Для каждого запроса пакета определяется **степень раскрытия**: «в заголовке»
(фраза есть в title, подзаголовке или вопросе FAQ), «в тексте» (есть в теле,
но не в структуре) или «нет» (значимых слов нет вовсе). Сравнение идёт по
усечённой основе слова — «оплата» и «оплаты» считаются одним словом, иначе
система советовала бы дописать уже написанное.

**Из чего состоит каждое действие.** Четыре обязательных поля; без любого из
них действие в отчёт не попадает:

- **что** — императив с конкретным объектом: «дописать текст под 2 запроса
  без единого вхождения на странице»;
- **где** — путь файла и поле: `src/content/blog/<slug>.md`, блок `faq` во
  frontmatter; для карточек — `data/seo/product-descriptions.json` и перенос
  в Directus через `ops-apply-descriptions` (правило проекта: руками в
  Directus мету не правим);
- **почему** — данные: какие именно фразы отсутствуют, каких слов не хватает,
  на каких позициях мы стоим и кто стоит выше;
- **приёмка** — проверяемый признак: «каждая фраза встречается в тексте хотя
  бы раз, в естественной формулировке, а не перечислением».

Плюс трудоёмкость и исполнитель (редактор, SEO, разработчик).

**Типы действий, которые система умеет предлагать:** дописать текст под
нераскрытые запросы · вынести раскрытые в тексте запросы в подзаголовки и FAQ ·
добавить вопросы в существующий FAQ или завести его · добавить коммерческий
переход, если его нет · пересобрать заголовок под ведущий запрос · закрыть
региональный разрыв · отправить страницу на переобход после правок.

**Два запрета, удерживающие отчёт от вранья:**

1. **Не советовать сделанное.** Если ссылка на карточку товара уже стоит, а
   FAQ уже есть, действие не предлагается. Вместо него в отчёт идёт строка
   «проверено, уже сделано»: руководитель должен видеть, что система смотрела
   на страницу, а не гадала по её типу.
2. **Не советовать необоснованное.** Внешние ссылки, поведенческие факторы и
   формулировки вида «улучшить SEO» не появляются в рекомендациях вовсе:
   контур не измеряет ни ссылочный профиль, ни поведение, а общие
   формулировки нельзя ни поручить, ни принять. Эти меры вынесены в отдельный
   список «не рекомендуем сейчас» с указанием, каких данных не хватает, чтобы
   их вообще обсуждать.

**Границы проверки называются в самом отчёте.** По вендорским страницам и
карточкам система видит только редакторскую обвязку, поэтому в действии стоит
пометка: перед правкой убедитесь, что фразы нет и в теле страницы из Directus.
Утверждать «фразы нет на странице», не видя страницы целиком, нельзя.

### 3.9б Проверка архитектуры перед рекомендацией

Правило введено в 1.6.0 после того, как руководитель взял в работу весь объём
из 32 пакетов. Разбор показал: рекомендации были технически исполнимы, но не
учитывали, как устроен сайт.

**Что выяснилось на реальном объёме:**

| Находка | Следствие | Как исправлено |
|---|---|---|
| Проверялись только данные (`vendors.ts`), а половина текста приходит из шаблона | Контур требовал дописать «купить» и «тарифы» туда, где они стоят в H1 и H2 | Проверка читает шаблон страницы: заголовки, блоки, вопросы FAQ |
| Одного слова не хватало сразу двум десяткам страниц | Двадцать одинаковых правок вместо одной | Системная правка: от трёх страниц одного типа — одно поручение по шаблону |
| В запросах встречались чужие домены («runway цена companies.rbc.ru») | Требование вписать в свой текст чужой адрес | Навигационные запросы с доменом исключены из точек атаки |
| Оценочные слова («недорого») попадали в поручение | Прямое нарушение редполитики | Список «не дописываем» с причиной в отчёте |
| Города («москва») попадали в поручение | Гео-задача словом в описании не решается | То же |
| Названия товаров приходят из Directus и невидимы проверке | Требование дописать «github» на карточку, где он в заголовке | Такие слова уходят в «проверить», а не в «дописать» |

**Правило, обобщающее эти находки.** Прежде чем предложить правку, контур
обязан ответить, откуда на странице берётся текст: из шаблона, из данных
репозитория или из Directus, — и предложить правку на том уровне, где текст
действительно живёт. Рекомендация, не прошедшая эту проверку, либо
невыполнима, либо портит текст ради формального совпадения слов.

**Что осталось непроверяемым и названо в отчёте прямо.** Тело вендорской
страницы и карточки товара приходит из Directus. По ним контур видит шаблон и
редакторские поля, но не видит описание из базы, о чём пишет в каждом таком
поручении. Закрыть эту слепую зону можно краулом собственного сайта — он же
нужен для оценки уязвимости страниц конкурентов.

### 3.9в Раздел «Точки атаки»: связь с поручениями и контролем

Замечание руководителя 02.09.2026: раздел перечислял 77 запросов, но не
объяснял, что с ними делают. Три недостатка исправлены.

**Устаревшее описание.** Текст утверждал, что Opportunity взвешивает выручку,
хотя экономический фактор убран из модели ещё в версии 1.1.0, и что запросы,
где выше стоят маркетплейсы, не рассматриваются, — хотя с той же версии они
остаются кандидатами с пометкой «конкуренция за клик». Оба утверждения
приведены в соответствие с моделью.

**Отсутствие связи с планом работ.** Теперь у каждой точки в таблице указан
пакет, который её закрывает, и текущее состояние работ.

**Отсутствие контроля.** Перед таблицей стоит сводка по четырём состояниям:

| Состояние | Что означает |
|---|---|
| правка внесена, идёт замер | страница доработана, до конца моратория новых поручений по ней нет |
| проверено, эффект измерен | окно наблюдения истекло, результат — в разделе 6 |
| в очереди на работу | поручение сформировано, правка не внесена |
| вне плана работ | запрос не сведён в пакет: спрос не измерен либо страница вне нашей зоны |

**Ожидание по результату названо явно.** Цель по каждой точке — выход в ТОП-3
по её запросу. Величина выигрыша считается не в этом разделе, а по пакету
работ: безразмерным индексом потенциала, а в переходах — только там, где спрос
измерен сопоставимой шкалой. Факт вместо ожидания появляется в разделе 6 через
две недели после внесения правки.

### 3.10 Фильтр значимости изменений

Чтобы шум не выдавался за сигнал: значимым считается вход или выход из
ТОП-3, вход или выход из ТОП-10, сдвиг на три позиции и более внутри ТОП-10,
сдвиг на пять и более в диапазоне 11–20. Сравниваются медианы трёх последних
измерений против трёх предыдущих. Изменение доли меньше 0,5 процентного
пункта считается шумом и не меняет вердикт.

## 4. Представление информации: два уровня

Разделение принципиальное: **письмо — это решение, отчёт — объяснение**.

### 4.1 Первый уровень: ежедневное письмо (10:00 МСК)

**Верхний экран — до 1000 видимых символов**, пять блоков в неизменном
порядке:

1. **Вердикт** одной строкой. Различаются два типа утверждений:
   *структурный* («BIZSoft занимает 5,4% поля, ведущий конкурент — такой-то»)
   доступен с первого дня, потому что описывает расстановку, а не движение;
   *динамический* (усиливаемся · нейтрально · ухудшение) требует **шести
   сравнимых измерений** — раньше тренда математически не существует, и
   любой вердикт о нём был бы утверждением о шуме. В версии 1.0.0 здесь была
   логическая коллизия: методика декларировала сглаживание 3×3, а вердикт
   менялся уже на втором дне по разнице двух соседних точек.
2. **Показатели**: доля видимости в Яндексе и Google, число запросов в ТОП-3
   и ТОП-10, дельты. Различаются две дельты, и это различие подписано в
   письме, чтобы не возникало вопроса «почему при минус 1,4 п.п. вердикт
   нейтральный»:
   - *оперативная* — сегодня против предыдущего валидного измерения.
     Справочная величина, показывает движение суток;
   - *сигнальная* — медиана трёх последних измерений против медианы трёх
     предыдущих. Именно она определяет вердикт, компонент динамики в Threat
     и главный сигнал.
3. **Главный сигнал** — ровно один. Есть история — самое значимое изменение,
   прошедшее фильтр значимости; истории нет — структурный факт о поле (кто
   его держит), что в первые дни и есть самая ценная информация.
4. **Что делать** — одно поручение, сформулированное через пакет работ:
   какая страница, сколько запросов закроет, какой спрос, что даст, какая
   трудоёмкость. Высокая возможность с низкой уверенностью главным действием
   не становится.
5. **За чем следим** — одна угроза.

**Ниже верхнего экрана — детализация** (в лимит не входит, по решению
руководителя должна быть не беднее ежедневного SEO-письма):

- что поручить: три пакета работ с охватом, эффектом, трудоёмкостью и
  чеклистом приёмки;
- варианты действий: минимум, оптимум, полный охват — с объёмом и отдачей
  каждого, чтобы решение принималось из альтернатив;
- показатели с источником и оценкой достоверности;
- кто держит выдачу: доли категорий с визуальными полосами;
- кто давит сильнее всего: конкуренты с уровнем угрозы;
- где ближе всего рост: пять точек атаки;
- **что система пока не знает** — обязательный блок, чтобы цифры не
  читались шире, чем они есть.

Текстовая версия письма содержит то же самое: клиент без HTML не получает
обрубок.

Графика выполнена средствами HTML и CSS, а не изображениями: почтовые
клиенты блокируют внешние картинки, а вложения требуют сборки в прогоне.
Линейные графики динамики появятся, когда накопится история — рисовать
тренд по одному дню значило бы показать декорацию вместо данных.

Анти-повтор: сравниваются хэши главного сигнала и действия с предыдущим
днём. Повторение того же невыполненного поручения допустимо с указанием
срока, полный повтор письма без причины считается дефектом.

### 4.2 Второй уровень: deep report

Отдельная страница по непубличному адресу с запретом индексации, ссылок с
сайта нет. Ежедневные снимки сохраняются неизменяемыми в архиве по датам.

Порядок погружения — от общего к частному, шесть уровней:

1. **Итоги дня**: показатели с дельтами, число точек атаки, зрелость расчёта
   с явным перечнем ограничений; кто держит выдачу по категориям.
2. **Конкуренты по уровню угрозы**: полная таблица с долей, позициями,
   Threat и **основанием оценки** — почему именно такая уверенность.
3. **Карточки конкурентов**: по каждому — на каких запросах виден, какими
   страницами ранжируется, лучшая позиция, число появлений. Это материал для
   разбора: что у них на странице есть такого, чего нет у нас.
4. **План работ**: все пакеты с раскрытием — что и где, оценка эффекта с
   пояснением расчёта, чеклист приёмки, полный список закрываемых запросов.
5. **Точки атаки**: полная таблица всех кандидатов и разбор первых десяти в
   формате факт → расчёт → вероятно → что сделать.
6. **Исходные данные**: строки выдачи, на которых всё построено, и раздел
   методики с честным перечнем того, чего система не делает.

### 4.3 Маркировка утверждений

В отчёте каждое существенное утверждение помечено уровнем достоверности:
**факт** (наблюдение из данных), **расчёт** (вычисленная величина),
**вероятно** (обоснованное предположение), **гипотеза** (требует проверки),
**что сделать** (рекомендация). Причина изменения либо подтверждена
перечисленными запросами и страницами, либо не называется вовсе.

## 5. Как определяются управленческие воздействия

### 5.1 Последовательность решения

1. **Проверка покрытия данных** с разделением на критический и
   некритический недостаток. Вердикт «недостаточно данных» выставляется при
   недостаточном покрытии **обязательного** источника (собрано менее 80%
   мониторингового ядра) или отсутствии минимального числа сопоставимых
   наблюдений для требуемого типа вердикта. Отсутствие **необязательных**
   источников и факторов (Google, B2B Confidence, уязвимость страниц)
   снижает достоверность соответствующих показателей, но не блокирует
   остальные выводы. Без этого разделения система с незапущенным Google
   обязана была бы вечно отвечать «недостаточно данных», а 149 валидных
   запросов из 150 и 20 из 150 назывались бы одинаково. Письмо отправляется
   в любом случае.
2. **Пересчёт долей видимости** по всем доменам поля.
3. **Выделение значимых изменений** через фильтр волатильности.
4. **Пересчёт угрозы конкурентов** с учётом доступности динамики.
5. **Отбор точек атаки** по критериям 3.8.
6. **Сведение в пакеты работ** и расчёт индекса потенциала; при однородном
   спросе из Wordstat — дополнительно оценка прироста переходов.
7. **Выбор главного сигнала** — ровно одного.
8. **Выбор поручения**: пакет с наибольшим индексом потенциала при
   приемлемой уверенности. При сопоставимом потенциале предпочтение отдаётся
   пакету с измеренным спросом — иначе нормализация весов давала бы
   преимущество тому, у кого неудобный фактор просто отсутствует.
9. **Формирование вариантов** действий с разной ценой и отдачей.
10. **Гейты качества** перед отправкой.

### 5.2 Правила, ограничивающие рекомендации

- Рекомендация с низкой уверенностью не становится главным действием, каким
  бы высоким ни был расчётный потенциал.
- Действие формулируется через страницу и конкретные пункты работ;
  обобщённые формулировки запрещены и проверяются тестом.
- Прирост подаётся как оценка потенциала при условии выхода в ТОП-3, а не
  как обещание результата.
- Действие не предлагается только потому, что так делает конкурент.
- Изменения сайта проходят обычный порядок: предложение → решение
  руководителя → правка через pull request → проверка → измерение.

### 5.3 Гейты качества перед отправкой

Письмо не уходит, если: превышен лимит верхнего экрана; главный сигнал не
ровно один; вердикт не проставлен; отсутствуют файлы письма. При
непройденном гейте отправляется уведомление о сбое, а не письмо с дефектом.
Дополнительно: тесты обязаны быть зелёными, иначе результат не публикуется.

### 5.4 Контроль исполнения

Прогон выполняется ежедневно в 09:20 МСК, письмо доставляется к 10:00.
Сторожевой механизм в 10:40 отправляет уведомление, если письма за сегодня
нет. Разрыв в 80 минут выбран по замеру реального дрейфа расписаний
(зафиксирован случай задержки на 26 минут): сторож, срабатывающий раньше
конца прогона, слал бы ложные тревоги, и доверие к уведомлениям исчезло бы.

Одно письмо на одну дату: повторный запуск не приводит к повторной отправке.

## 5а. Цикл проверки: что стало с выданными поручениями

До версии 1.5.0 контур был генератором предложений: он не знал, внедрено ли
вчерашнее поручение, предлагал его снова и ничему не учился на исходах.
Руководитель поставил задачу прямо: после внесения правок нужен мораторий на
время проверки результативности, новые предложения не должны включать
отработанные пункты, а внизу отчёта — статистика «было → стало» и вывод, какие
правки эффективны.

### 5а.1 Как фиксируется внедрение

**По странице, а не по отметке человека.** В момент выдачи поручения система
запоминает требования: какая формулировка и в какой степени раскрытия должна
появиться — «в тексте» или «в заголовке». Внедрение засчитывается, когда
выполнено не менее половины требований.

Степень обязательна. На этом контур один раз ошибся при первом же запуске
цикла: поручению «вынести фразу в подзаголовок» он засчитал выполнение из-за
того, что фраза и так была в тексте абзацем ниже, и отправил пять страниц под
мораторий без единой правки. Теперь «в тексте» и «в заголовке» — разные
требования, и первое не закрывает второе. Ошибка закреплена регресс-тестом.

Порог в половину требований выбран сознательно: правка редко закрывает все
формулировки сразу, требовать сто процентов — значит не зафиксировать
внедрение никогда, а одна фраза из десяти внедрением не является.

### 5а.2 Мораторий

Внедрённая страница выводится из очереди поручений на **14 дней**. Срок даёт
время на переиндексацию и обеспечивает шесть сравнимых замеров, которых
требует сглаживание 3×3. Без моратория система на следующее же утро
потребовала бы доработать только что доработанное, а измерение стало бы
невозможным: непонятно, какая из двух правок сдвинула позиции.

Страницы под мораторием не исчезают: они показаны отдельным блоком в письме и
в разделе 6 отчёта — с датой внедрения и датой окончания замера.

### 5а.3 Как считается эффект

**Разностью разностей.** Берётся изменение медианной позиции по запросам
эксперимента и — за тот же период — изменение по всем прочим запросам ядра,
где мы ничего не трогали. Эффект — разница между ними:

    эффект = (позиция_после − позиция_до) − (контроль_после − контроль_до)

Без контрольной группы любой общий сдвиг выдачи — апдейт алгоритма,
сезонность, уход конкурента — записывался бы в заслугу правке, и обучение
системы строилось бы на выдуманных победах. Отрицательное значение означает,
что позиции выросли.

Отсутствие в ТОП-20 считается позицией 21, а не пропуском: иначе вылет
страницы из выдачи улучшал бы средний результат эксперимента.

Вердикт: улучшение при эффекте от одной позиции в нашу пользу, ухудшение — при
одной позиции против, между ними — «без изменений». Достоверность помечается
«предварительной», если запросов меньше трёх или в одном из окон меньше двух
замеров.

**Оговорка, которая стоит в отчёте всегда:** это наблюдение, а не
доказательство. A/B-теста на поисковой выдаче не существует, и влияние других
причин исключить нельзя. Контрольная группа снимает общий сдвиг выдачи, но не
индивидуальные события по конкретной странице.

### 5а.3а Что нивелируется в сравнении «было → стало»

Вопрос поставлен руководителем 02.09.2026: правки вносились по одной версии
методики, а замер пойдёт по другой — как тогда корректно сопоставить «было» и
«стало»? Разбор нашёл два искажения, оба устранены.

**Первое: модель менялась между базой и замером.** Вместе с базой теперь
сохраняются условия, в которых она снята: версия методики, отпечаток
конфигурации, версия и отпечаток ядра запросов. При оценке они сверяются с
текущими, и результат получает пометку сравнимости:

| Пометка | Что значит |
|---|---|
| полная | база и замер получены одной моделью на одном ядре |
| ограничена | между замерами менялась модель или ядро; сравнение остаётся осмысленным, потому что позиция измеряется одинаково в любой версии, но приписывать всю разницу правке нельзя |
| неизвестна | условия базы не сохранялись (эксперименты до 02.09.2026) |

**Второе: контрольная группа была загрязнена той же правкой.** Часть правок
оказалась не текстом страницы, а шаблоном — она применяется ко всем страницам
своего типа. Оставить их в контроле значит сравнивать изменённое с изменённым
и получить ноль там, где эффект есть. Теперь:

- страницы типов, чьи шаблоны правились в день внедрения, исключаются из
  контрольной группы **всех** экспериментов этого дня;
- в контроль идут только запросы, где мы присутствуем в выдаче: запрос, по
  которому нас нет, стоит на условной позиции 21 в оба окна и ничего не
  измеряет — сотня таких сделала бы медиану неподвижной, а контроль всегда
  нулевым;
- состав контроля фиксируется по обоим окнам сразу, иначе разный состав до и
  после сам сдвинул бы медиану;
- при контроле меньше пяти запросов достоверность помечается предварительной.

Для этого снимок дня хранит адрес нашей страницы по каждому запросу — без
него нельзя отделить страницы, задетые правкой, от нетронутых.

**Что нивелировать нельзя.** Мы не ставим A/B-тест на поисковой выдаче.
Контрольная группа снимает общий сдвиг выдачи, но не события, случившиеся
ровно с этой страницей. Это ограничение названо в отчёте рядом с каждой
таблицей результатов.

### 5а.4 Чему система учится

Исходы группируются по типу действия: дописать текст, вынести в заголовки,
добавить FAQ, поправить мету. По каждому типу — число наблюдений, медианный
эффект и вывод.

**Пока по типу накоплено меньше пяти оценённых экспериментов, вывода нет**, а
порядок действий в поручениях не меняется. Подстраивать приоритет работ под
два-три случайных исхода — способ закрепить случайность в методике на месяцы.
После порога порядок действий внутри пакета выстраивается по накопленному
эффекту: типы, дающие выигрыш, идут первыми.

### 6.3 Известные допущения, требующие внимания аудитора

1. **Кривая CTR взята из усреднённых публичных исследований**, а не
   откалибрована по нашим данным. Это влияет на абсолютные значения долей,
   но слабо влияет на ранжирование конкурентов между собой.
2. **Показы Вебмастера используются как мера спроса** при отсутствии
   частотности. Природа величин разная; в версии 1.1.0 они разведены —
   переходы считаются только по частотности, для остальных даётся
   безразмерный индекс, — но сама подстановка одной меры вместо другой
   остаётся допущением.
3. **Категория домена определяется по спискам и признакам URL.** Из 234
   доменов среза 137 остались неклассифицированными — они честно исключены
   из рейтинга, но это означает неполноту картины поля.
4. **Оценка прироста переходов линейна** по спросу и не учитывает
   сезонность, конкурентную реакцию и изменение самой выдачи.
5. **Один день истории.** Все текущие значения — базовая линия, а не тренд;
   динамические вердикты и компонент динамики в Threat недоступны до
   накопления шести сравнимых измерений.
6. **Точка насыщения присутствия (15% доли) выбрана, а не выведена.** Она
   определяет, при какой доле компонент Threat достигает максимума, и
   подлежит калибровке по мере накопления наблюдений.
7. **Приближение в компоненте «превосходство над нами».** Когда счётчик
   запросов, где конкурент стоит выше BIZSoft, недоступен, используется
   присутствие в ТОП-3. Приближение помечается в объяснении оценки, но
   остаётся приближением.
8. **Пороги нормировки спроса (1000 и 200) выбраны, а не выведены.** Они
   вынесены в конфигурацию и подлежат замене на перцентильную нормировку,
   когда накопится распределение. До тех пор это записанное допущение.
9. **Динамика конкурентов требует полного совпадения состава ядра**, тогда
   как наша собственная динамика считается по пересечению. Причина
   техническая: по-доменная видимость по каждому запросу не хранится.
   Следствие — при редактировании ядра компонент динамики Threat отключается
   у всех конкурентов сразу.
10. **Порог пересечения ядра (70%) выбран, а не выведен.** Он определяет,
    когда сравнимого поля «фактически нет», и подлежит проверке на практике
    первых изменений ядра.

## 7б. Изменения версии 1.3.0 по результатам четвёртой рецензии

Рецензия признала концептуальных ошибок в 1.2.0 не обнаруженными и указала
два реальных дефекта и восемь мест недоопределённости. Оба дефекта
подтверждены проверкой на коде до внесения правок.

### Дефект 1: индекс потенциала при неизмеренном спросе

**Что было.** Документ утверждал «индекс потенциала считается всегда», а код
складывал вклад запроса с неизмеренным спросом как ноль. Пакет из пяти
запросов, где спрос известен по двум, получал индекс так, будто три запроса
никому не нужны, и опускался в очереди поручений ниже, чем заслуживает. Это
то же самое «нет данных = 0», которое система запрещает себе везде.

**Что стало.** Индекс считается только по запросам с измеренным спросом;
рядом хранится и показывается покрытие вида «3/5»; при полностью неизмеренном
спросе индекс не считается вовсе (метка «не оценён»), пакет уходит в конец
очереди и главным поручением стать не может. Проверяется инвариант-тестами
14–16.

### Дефект 2: смена состава ядра создавала ложную динамику

**Что было.** Доля считается внутри поля, а поле задаётся списком запросов.
Состав ядра нигде не фиксировался, и добавление или удаление запросов
двигало долю так же, как движение конкурентов, — различить эти два события
было нечем.

**Что стало.** Введены отпечаток и версия состава ядра, снимок хранит
по-запросную видимость, дельта и ряд для тренда считаются по пересечению
составов, основание дельты подписывается, при пересечении меньше 70%
динамика не считается, а компонент динамики Threat требует полного
совпадения состава. Подробности — раздел 3.1а. Проверяется
инвариант-тестами 17–22.

### Восемь мест недоопределённости

| № | Что было неопределено | Как задано в 1.3.0 |
|---|---|---|
| 1 | функции компонентов Threat описывались словами | явные формулы, раздел 3.4 |
| 2 | поведение Threat при отрицательной динамике | ноль баллов, значение сохраняется и показывается со знаком |
| 3 | правило при нескольких недоступных факторах | одна операция нормализации, независимая от порядка, раздел 3.7 |
| 4 | статус неклассифицированного домена | конкурент за клик, но не за сделку, раздел 3.8 |
| 5 | «сделку они не заберут» как утверждение о факте | заменено на «признаков B2B-продажи не подтверждено» |
| 6 | покрытие данных мерилось только числом запросов | второй гейт по объёму спроса, отдельно по каждому источнику |
| 7 | пороги нормировки спроса жили только в коде | вынесены в конфигурацию и помечены как параметр калибровки |
| 8 | условия расчёта снимка не были записаны в самом снимке | блок метаданных: версия методики, отпечаток конфигурации, версия и отпечаток ядра, покрытие, состав источников спроса |

### Статус методики

После 1.3.0 методика переводится в состояние **заморозки для эмпирической
проверки**: содержательные изменения модели до накопления шести сравнимых
измерений не вносятся, чтобы накапливаемая история оставалась сравнимой.
Исправления фактических ошибок и дефектов исполнения под заморозку не
подпадают. Калибровка вынесенных в конфигурацию параметров (кривая CTR, точки
насыщения, пороги нормировки спроса) выполняется после накопления истории и
будет отдельной версией с новым отпечатком конфигурации.

## 7в. Изменения версии 1.4.0: рекомендации вместо направлений

Замечание руководителя от 01.09.2026 после проверки первого поручения.
Подтверждено на коде: рекомендация выбиралась по типу страницы, содержимое не
читалось, и статье с готовыми ссылками на товары и готовым FAQ система
советовала «добавить коммерческий блок».

| Что изменилось | Было | Стало |
|---|---|---|
| Основание рекомендации | тип страницы | фактическое содержимое страницы из репозитория |
| Формулировка | направление («добавить коммерческий блок») | действие с файлом, полем и списком конкретных фраз |
| Обоснование | общее описание пакета | какие фразы отсутствуют и каких слов не хватает |
| Приёмка | общий чеклист по типу страницы | проверяемый признак у каждого действия |
| Сделанное | не учитывалось | отдельный список «проверено, работ не требует» |
| Неизмеряемое | не упоминалось | список «не рекомендуем сейчас» с причиной |
| Заголовок пакета | шаблон по типу страницы | первое действие ТЗ |

Проверяется 20 тестами исполнимости (`tests/test_recommendations.py`): каждое
действие отвечает на четыре вопроса, не содержит общих формулировок, не
советует сделанное, называет конкретные фразы, а при недоступном содержимом
честно превращается в ручную проверку вместо совета вслепую. Всего тестов 202.
