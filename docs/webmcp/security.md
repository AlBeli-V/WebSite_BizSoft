# WebMCP в BIZSoft: безопасность

## Модель угроз и принятые решения

Вход AI-агента считается **недоверенным всегда**. Цепочка обработки любого
вызова (сервер, `src/webmcp/`):

```
вход агента
  → валидация по JSON Schema (validate.ts: типы, длины, границы,
    additionalProperties: false — неизвестные поля это отказ)
  → нормализация (управляющие символы вычищаются, пробелы схлопываются)
  → бизнес-проверки обработчика (существование slug/sku/вендора)
  → чтение каталога существующими функциями (только status=published,
    origin != domestic — те же фильтры, что у витрины)
  → адаптер с БЕЛЫМ СПИСКОМ полей
```

### Проверенные классы угроз

| Угроза | Статус | Как закрыто |
|---|---|---|
| XSS | закрыто | ответы — только JSON (`Content-Type: application/json`), в HTML ничего не вставляется; клиентский слой не пишет в DOM вообще |
| CSRF | не применимо в v1 | все инструменты read-only, GET без побочных эффектов; write-инструментов нет |
| Injection | закрыто | вход после схемы уходит только в фильтры в памяти и в параметры Directus REST (JSON-сериализация, не конкатенация запросов) |
| Обход авторизации | закрыто | эндпоинт читает только публичный каталог (то же, что видит любой посетитель); админ-функции живут за `X-Admin-Token` и WebMCP не касаются |
| Malformed arguments | закрыто | схема + юнит-тесты (`webmcp-validate.test.ts`): не-объект, неверные типы, дроби, отрицательные, превышения, лишние поля |
| Утечка PII | закрыто | слой не читает leads/quotes вовсе; в ответах нет ничего про покупателей |
| Утечка секретов/экономики | закрыто | белый список полей адаптера; тест ловит `base_price*`, `markup*`, `peg_*`, `purchase_source`, `price_locked` в JSON ответа |
| SSRF | закрыто | эндпоинт не принимает URL и не делает исходящих запросов, кроме штатного Directus по фиксированному адресу |
| Enumeration | принято осознанно | каталог публичен по определению (HTML, sitemap, фиды) — перечисление не раскрывает ничего нового |
| Rate limit / abuse | частично | limit-параметры ограничены схемой (≤30/≤100); SSR-кэш каталога (60 с) гасит нагрузку на БД; отдельной nginx-зоны на `/api/agent/` в v1 нет — как и у HTML-каталога. При признаках злоупотребления добавить зону по образцу `bz_suggest` (deploy/nginx-rate-limit.conf) через ops-nginx-ratelimit |
| Дублирование действий | не применимо | чтение идемпотентно |
| Prompt injection | см. ниже | |

### Prompt injection и CMS-контент

Разделение слоёв — архитектурное:

- **определения инструментов** (`definitions.ts`) — статический код в
  репозитории; контент Directus не участвует в их формировании ни при
  каких условиях;
- **исполняемая логика** (`handlers.ts`, `client.ts`) — код;
- **бизнес-данные** (цены, названия, описания) — приходят из Directus и
  попадают только в **значения** JSON-ответа.

Текст товара (description, features, faq) может содержать что угодно —
он не способен изменить имя, описание или схему инструмента, потому что
поток данных туда физически не ведёт. Ответы отдаются агенту как данные
(`JSON.stringify` в text-блоке), решение о доверии тексту принимает
агент/браузер (аннотации `untrustedContentHint` спецификации — кандидат
на добавление, когда стабилизируются).

## Side effects: почему v1 только читает

Write-инструменты (`submit_request`, `create_quote` и любые другие)
в v1 **сознательно не реализованы**. Существующие формы защищены
honeypot + таймингом заполнения (`MIN_FILL_MS`) + лимитами на IP —
эта защита рассчитана на человека за браузером; агентный вызов её
семантику ломает (агент заполняет «форму» за миллисекунды). Открывать
запись можно только после отдельного решения руководителя и только при
доказанном выполнении всех условий:

- используется существующий серверный контур (`/api/lead`, `/api/quote`)
  с его валидацией, а не параллельный;
- человек остаётся в цикле: подтверждение на стороне браузера/агента
  (permission prompt спецификации) плюс наша серверная защита;
- анти-abuse не ослабляется (лимиты на IP сохраняются, тайминговая
  отсечка пересматривается, а не удаляется);
- повторный вызов не создаёт дублей (идемпотентность по ключу);
- вход агента по-прежнему недоверенный (схема + нормализация + бизнес-валидация).

До тех пор агентный путь к заявке — довести человека до страницы
(`url` в ответах инструментов), дальше человек действует сам.

## Kill switch

`PUBLIC_WEBMCP=0` — см. architecture.md. Гасит и регистрацию инструментов,
и `/api/agent/*`, не затрагивая сайт.

## Что остаётся открытым (принятые риски)

1. Нет выделенного rate limit на `/api/agent/*` (как нет его и на HTML
   каталоге) — при злоупотреблении добавить nginx-зону (см. таблицу).
2. Общесайтовая CSP отсутствует (известный долг SEC-006, не связан с
   WebMCP); слой намеренно без inline-скриптов, чтобы не удорожать её
   будущее внедрение.
3. Стандарт экспериментальный: формы API и permission-модель браузеров
   могут поменяться — слой изолирован для быстрой правки/удаления.
