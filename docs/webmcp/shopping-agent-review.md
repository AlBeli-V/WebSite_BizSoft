# Разбор: Anthropic Commerce Agents (shopping-agent) для biz-soft.pro

Дата разбора: 04.09.2026. Источник:
<https://github.com/anthropics/commerce-agents> (`shopping-agent/`),
лицензия Apache-2.0, помечен как reference implementation — правки извне
не принимаются, апстрим-обновления придётся вливать вручную.

Вопрос руководителя: возможно ли и рационально ли добавить такого агента
на сайт и какие сценарии использования у нас.

Короткий ответ: **как продуктовый образец — да, как код в проде — нет.**
Из репозитория рационально забрать модель покрытия и правила безопасности
и достроить ими существующий слой WebMCP; разворачивать Python-агента
рядом с витриной сейчас нельзя ни юридически, ни по экономике.

## 1. Что это такое

Два агента поверх Claude: **shopping** (клиентский, в приложении магазина)
и **merchant** (бэк-офис). Нас касается первый.

- **Стек:** Python 3.11+, семь pip-пакетов (`commerce-common`,
  `shopping-agent-core`, `shopping-agent-runtime`, `shopping-agent-sdk`
  и т.д.), Node 22 для восьми демо-витрин.
- **Три способа запуска:** Messages API (эталонный turn loop), Claude
  Agent SDK, Managed Agents (хостинг у Anthropic + свой MCP-сервер).
- **Одна точка интеграции** — абстрактный класс `StorefrontBackend`
  (`shopping-agent/core/shopping_agent/backend.py`): адоптер реализует
  `search_products`, `get_product_details`, `get_cart`, `add_to_cart`,
  `update_cart_item`, `remove_from_cart`, `get_preferences`, `get_orders`,
  `get_order`, `search_policies`, `get_fulfillment_options` и
  опциональные `checkout_handoff`, `get_account_context`, `get_disclosure`.
- **Инструменты модели** (`tools/registry.py`): к перечисленному добавлены
  `save_memory` / `recall_memories` (память о клиенте), презентационные
  `present_products`, `present_comparison`, `present_plan`, `present_guide`,
  `present_order_status`, `present_suggestions`, `checkout` и `load_skill`.
- **Пять скиллов** (`shopping-agent/skills/`): search-discovery,
  purchase-research, planning-goals, customer-care,
  memory-personalization — по 33–38 строк, подгружаются по требованию.
- **Безопасность** (`docs/safety.md`): фенсинг недоверенного текста,
  provenance-гейт на запись в корзину (добавить можно только id, который
  инструмент вернул в этой сессии), потолки количества, серверная сборка
  UI-карточек по id, grounding-гейты (вопрос про условия — сначала
  обязательное чтение политик), валидация памяти. **Оплаты нет:**
  `checkout` только рендерит корзину, платит хост.
- **Объём эталонной реализации** для представления о работе: демо-магазин
  `examples/retail/api/mock_retail.py` — 379 строк, общий хост
  `examples/demo_common/` — ещё ~1,5 тыс. строк (сессии, provenance,
  память, витрина).

## 2. Что у нас уже есть

Слой **WebMCP** (внедрён 30.08.2026, `docs/webmcp/architecture.md`) решает
ту же задачу с другой стороны: агент не наш и не на нашем сервере — это
агент клиента в его браузере, который через `document.modelContext`
вызывает наши инструменты, а исполнение уходит на `GET /api/agent/<tool>`.

Совпадения с commerce-agents оказались буквальными и подтверждают, что
слой спроектирован верно:

| Правило commerce-agents | Наш аналог |
|---|---|
| Один источник данных, никакой «базы для агентов» | `handlers.ts` → `lib/directus`, цена только `effectivePrice()` |
| Белый список полей в ответе | `adapters.ts` + тест `webmcp-adapters.test.ts` |
| Никаких платежей из агента | v1 read-only, `security.md` § «Side effects» |
| Тул-серфейс — функция конфигурации, лишнее имя отвергается | `definitions.ts` + тест `webmcp-definitions.test.ts` |
| Kill switch на весь слой | `PUBLIC_WEBMCP=0` |

Чего у нас нет из набора `StorefrontBackend`: **политик и условий покупки**
(`search_policies`), **сроков и способа поставки** (`get_fulfillment_options`),
фильтров в поиске (у нас только `query`, `vendor`, `limit` — нет цены,
категории, типа лицензии), корзины, заказов и памяти.

## 3. Почему разворачивать shopping-agent у нас нельзя

**3.1. Юрисдикция — блокер, а не риск.** Россия не входит в список
поддерживаемых стран Anthropic (<https://www.anthropic.com/supported-countries>):
ИП не может легально заключить договор и оплатить API, а сервер витрины
находится в РФ. Обход (зарубежное юрлицо, прокси) — нарушение условий
использования и валютные риски. Это отсекает все три способа запуска
разом: и Messages API, и Agent SDK, и Managed Agents.

**3.2. Персональные данные.** Диалог с клиентом у нас неизбежно содержит
ФИО, e-mail, телефон, компанию и ИНН — весь набор из `LeadForm`. Отправка
переписки во внешнюю модель — трансграничная передача ПДн со всеми
обязанностями по 152-ФЗ. Плюс механизм памяти агента (`save_memory`)
создаёт ещё одно хранилище ПДн с требованиями к сроку хранения, доступу
и удалению. Проект уже относится к этому строго — правило
`ym-disable-keys` маскирует ввод ПДн даже от собственного Вебвизора.

**3.3. Модель сделки.** Агент оптимизирован под самообслуживание:
поиск → сравнение → корзина → checkout. У нас сделка B2B: проверка
контрагента по ИНН (`lib/inn.ts`, DaData), КП в PDF/DOCX/XLSX/JPG,
счёт, договор, ЭДО. Оплаты картой на сайте нет и не планируется, значит
самый ценный кусок агента — доведение до оплаты — у нас пустой.

**3.4. Узкое место не там.** По данным отчёта Growth Intelligence за
19.08.2026: 78 визитов в сутки, 3 конверсии, и **все три пришли со статьи
«как купить зарубежное ПО для юрлица»** (5 визитов → 3 цели), а карточки
товаров (Marmoset 8, Vegas 8 визитов) не конвертят вовсе. Клиент
спотыкается не о подбор из 1140 позиций, а о вопрос «как это законно
оплатить с расчётного счёта». Shopping-агент лечит подбор — не наше
узкое место.

**3.5. Экономика.** Токены как раз недороги: при кэшировании префикса
диалог из 5–6 ходов на Sonnet 5 ($2/$10 за 1М токенов, чтение из кэша
≈0,1×) обходится примерно в 5–8 ₽; при 78 визитах и вовлечении 20% это
2–4 тыс. ₽/мес. Дорого другое — новый эксплуатационный контур: Python-сервис
рядом с Astro SSR в Docker, свои секреты, rate limit, логи с ПДн
(на уровне DEBUG в лог попадает вся корзина и все внедрённые факты),
свой набор эвалов. Для контура, обслуживающего 2–3 обращения в сутки,
это несоразмерно.

## 4. Сценарии использования в нашем случае

### Сценарий A. Агент клиента, через WebMCP — рекомендуется

Ничего не хостим и не платим за токены: работу делает агент покупателя.
Из `StorefrontBackend` берём недостающее покрытие:

1. **`get_purchase_terms` / `search_policies`** — условия приобретения:
   оплата с расчётного счёта, договор и закрывающие документы, ЭДО,
   сроки активации, работа с валютой, возврат. Источник — существующие
   `/docs`, `/faq`, `/how-we-work`, `/compliance`. Это ровно тот вопрос,
   на котором сайт конвертит, и сейчас агент клиента ответа на него
   получить не может — только `purchase_terms` в карточке товара.
2. **Фильтры в `search_products`** — цена, категория, тип лицензии
   (в commerce-agents это `SearchFilters`); сейчас поиск принимает
   только `query` и `vendor`.
3. **`list_categories`** — вход в каталог без угадывания слов.
4. **`request_quote` — единственный write, который стоит рассматривать.**
   Прямой аналог их `checkout`: агент не платит и не отправляет заявку
   сам, а собирает корзину и отдаёт человеку. Условия открытия записи уже
   выписаны в `docs/webmcp/security.md` § «Side effects» (существующий
   контур `/api/quote`, человек в цикле, анти-abuse не ослаблен,
   идемпотентность) — их надо выполнить, а не переписать. Требует
   отдельного решения руководителя.

Объём: пункты 1–3 — 1–2 дня с тестами и обновлением `docs/webmcp/tools.md`;
пункт 4 — ещё 2–3 дня плюс пересмотр анти-abuse.

### Сценарий B. Свой чат-консультант на сайте — не сейчас

Это и есть shopping-agent в чистом виде. Блокируется п. 3.1–3.2. Если
когда-нибудь делать, то:
- не переносить Python-стек: `src/webmcp/handlers.ts` уже является нашим
  `StorefrontBackend`, поверх него нужен только turn loop;
- модель — российская (YandexGPT, GigaChat, Cloud.ru): ПДн остаются в РФ,
  договор и оплата в рублях;
- из репозитория брать не код, а правила: фенсинг, provenance-гейт,
  сборку карточек по id на сервере, grounding-гейт «вопрос об условиях —
  сначала прочитай политику», скиллы вместо раздувания системного промпта.

Пересмотреть при росте трафика в 3–5 раз или при появлении легального
доступа к модели.

### Сценарий C. Merchant-агент (бэк-офис) — не нужен

Его работу (аналитика, листинги, цены, кампании) у нас уже делают контуры
SEO/Growth Intelligence, конкурентной разведки и Директа. Правило
`docs/rules/operational-runs.md` прямо требует детерминированных прогонов
в GitHub Actions, а не агентских сессий. Добавление merchant-агента
противоречило бы действующему правилу.

## 5. Вывод

Ценность репозитория для нас — не в коде, а в трёх вещах: перечень
методов `StorefrontBackend` как чек-лист покрытия (показал наши пробелы:
условия покупки, сроки, фильтры), `docs/safety.md` как готовый свод
требований к агентному слою (наш `security.md` совпал с ним по духу),
и `checkout` как образец того, как агент подводит к сделке, не совершая её.

Рекомендация: сценарий A, пункты 1–3, отдельным PR; пункт 4 — только
после решения руководителя; сценарии B и C — отклонить.
