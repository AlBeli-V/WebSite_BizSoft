# WebMCP-инструменты BIZSoft

Все инструменты v1 — **только чтение** (`readOnlyHint: true`), исполняются
на сервере через `GET /api/agent/<tool>`. Определения — в
`src/webmcp/definitions.ts` (единственный источник; сюда — только сводка).

## Критические пользовательские сценарии (CUJ)

Набор инструментов выведен из сценариев, а не наоборот:

| CUJ | Сценарий | Инструменты |
|---|---|---|
| CUJ-1 | Найти ПО → открыть продукт → понять условия приобретения | `search_products` → `get_product` (поле `purchase_terms`) |
| CUJ-2 | Найти производителя → его продукты → выбрать нужный | `list_vendors` / `get_vendor` → `list_vendor_products` |
| CUJ-3 | Найти конкретный SKU → доступные варианты | `get_product(sku)` → `list_vendor_products` (тарифы соседних карточек) |
| CUJ-4 | Сравнить варианты | несколько вызовов `get_product` (отдельный compare-tool не нужен) |
| CUJ-5 | Выбрать продукт → условия → перейти к запросу КП | `get_product` → переход человека по `url` карточки (write через WebMCP в v1 закрыт) |
| CUJ-6 | «Можно ли оплатить с расчётного счёта, дадите ли закрывающие» | `search_policies` |
| CUJ-7 | Подобрать по бюджету и разделу («дизайн до 50 000 ₽») | `list_categories` → `search_products` (`category`, `max_price`, `sort`) |

CUJ-6 добавлен по данным Growth Intelligence: конверсию даёт контент об
условиях покупки, а не карточки товаров. До появления `search_policies`
агент покупателя мог узнать условия только из поля `purchase_terms` одной
карточки — на вопрос «через каких операторов ЭДО работаете» ответа не было
вовсе, и модели оставалось его выдумать.

«Варианты лицензий» в модели BIZSoft — это соседние карточки того же
вендора (тарифы) плюс `license_type` карточки; отдельной сущности
«лицензионные опции» в Directus нет, поэтому и инструмента
`get_license_options` нет — его данные дал бы тот же `list_vendor_products`.
`calculate_price` тоже не существует: цена конфигурации считается только в
КП существующей серверной логикой (`/api/quote`), это write-контур.

## Справочник

| Tool | Для чего | Вход | Выход | Read-only | Где работает |
|---|---|---|---|---|---|
| `search_products` | Поиск и подбор по каталогу | `query?`, `vendor?`, `category?`, `license?` (`org`/`individual`/`student`), `min_price?`, `max_price?`, `sort?` (`relevance`/`price_asc`/`price_desc`), `limit?` (1–30, по умолч. 10); обязательно хотя бы одно из `query`, `vendor`, `category` | `{total, items[]}` — краткие карточки с ценой и url | да | все страницы |
| `list_categories` | Разделы каталога | — | `{total, items[]}`: название, slug, число товаров, url раздела | да | все страницы |
| `search_policies` | Условия работы: договор, счёт, НДС, ЭДО, сроки, порядок сделки | `query` (обяз.), `limit?` (1–20, по умолч. 5) | `{total, items[]}`: `id`, `question`, `answer`, `url` страницы с этим ответом | да | все страницы |
| `get_product` | Полная карточка товара | `slug` или `sku` (хотя бы одно) | карточка: цена (`effectivePrice`), лицензия, описание, промо, `purchase_terms`, url | да | все страницы |
| `list_vendors` | Все производители | — | `{total, items[]}`: имя, юрлицо, число товаров, url лендинга | да | все страницы |
| `get_vendor` | Один производитель | `vendor` (имя или slug) | карточка вендора | да | все страницы |
| `list_vendor_products` | Товары производителя | `vendor` (обяз.), `limit?` (1–100, по умолч. 50) | `{vendor, vendor_url, total, items[]}` | да | все страницы |

Форматы ответов — `src/webmcp/adapters.ts` (`AgentProductBrief`,
`AgentProductFull`, `AgentVendor`).

Договорённости:

- «Цена по запросу» → `price: null` + `price_note`; цифры не выдумываются
  (то же правило, что в Schema.org-разметке). Из ценового диапазона
  (`min_price`/`max_price`) такие позиции уходят: показать их внутри
  «до 50 000 ₽» — соврать о цене; в любой сортировке они остаются в конце.
- Ошибки — человекочитаемым текстом с подсказкой следующего шага
  (`…не найден. Попробуйте search_products.`). У `search_policies` пустой
  результат — это 404 с прямым запретом додумывать ответ и адресом `/faq`:
  «нет данных» безопаснее правдоподобной выдумки об условиях сделки.
- Внутренняя экономика (закупка, коэффициенты, источники цен) в ответы
  не попадает — белый список полей закреплён тестом
  `tests/webmcp-adapters.test.ts`.

## Как правятся условия работы

Только в `src/data/policies.ts` — это единственный источник и для страниц
`/faq`, `/how-we-work`, `/pricing`, и для `search_policies`. Массив
`{ q, a }` в самой странице снова разведёт текст сайта и ответ агенту,
поэтому его запрещает тест `tests/policies.test.ts`. Порядок сделки живёт
в `PROCESS_STEPS` и попадает к агенту одной собранной записью — второй
копии семи шагов не существует.

## Как добавляются новые товары и вендоры

Никак — в этом смысл. Инструменты generic и читают живой каталог:
опубликованный в Directus товар и его вендор видны `search_products` /
`get_product` / `list_vendor_products` сразу, без единой строки кода.
Чеклист приёмки — в `docs/vendors-expansion-prompt.md` (раздел 11а).

Создавать инструменты «под продукт» (`get_claude`, `get_chatgpt`)
запрещено — тест `webmcp-definitions.test.ts` не пропустит имя вне
generic-схемы.
