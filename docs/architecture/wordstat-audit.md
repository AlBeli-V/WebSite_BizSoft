# Аудит подсистемы Wordstat — AS-IS (25.08.2026)

Часть аудита маркетинговой/аналитической подсистемы biz-soft.pro
(основной отчёт: `marketing-system-audit-as-is.md`). Документ фиксирует
фактическое состояние; ничего не проектирует и не меняет.

Классификация утверждений: **FACT** — подтверждено кодом/данными/Git,
**INFERENCE** — вывод из фактов, **RISK** — риск, **OPPORTUNITY** — возможность,
**BUSINESS IMPACT** — практическое значение для бизнеса.

---

## 1. Что это такое — простыми словами

Подсистема Wordstat ежедневно спрашивает у Яндекса: «сколько раз люди искали
такие-то фразы за последний месяц». Из ответов она строит базу знаний о рыночном
спросе на программные продукты: какие вендоры и продукты интересуют покупателей,
чего не хватает в каталоге BIZSoft, какие страницы стоит создать или улучшить.
С 20.08.2026 это не «сборщик частотностей для SEO-отчёта», а самостоятельная
система обнаружения коммерческого спроса с бюджетным контролем, приоритизацией
запросов и объяснимыми рекомендациями (методика: `docs/seo/reporting-methodology.md`,
раздел «Wordstat Intelligence»).

**BUSINESS IMPACT.** Это единственный источник данных в системе, который говорит
о рынке в целом, а не о собственном сайте. Все остальные источники (Вебмастер,
Search Console, Метрика, GA4) видят только тех, кто уже нашёл biz-soft.pro.


результаты в `seo-data`. Таймаут джоба 330 минут.

К каждому вендору применяются 8 шаблонов с калиброванной продуктивностью

каталога и ручного списка, а не от ответов Wordstat.

### 4.2 Приоритизация — FACT

1. **Прирост информации до вызова** (`discovery.py:178-210`):
   `gain = productivity × novelty × coverage_bonus × (1 − duplicate_probability)`;
   отсечка `min_information_gain = 0.15`, потолок 12 вызовов на вендора.
   Продуктивность шаблонов дообучается фактами из `pattern-stats.json`.
2. **Ранг задачи** (`planner.py:49-54`):
   `business_value × information_gain × confidence / api_cost`, где business_value:
   decision_validation 1.0 → vendor_expansion 0.7 → discovery 0.6 →
   trend_monitoring 0.4 → exploration 0.2.
3. **Уровни мониторинга** (`tiers.py:23-32`): A — динамика раз в 7 дней, регионы
   раз в 90; B — динамика раз в 30 дней; C — не опрашивается. На 25.08: A=39,
   B=25, C=61 кластеров.
4. **Суточное распределение** (`planner.py:88-108`): слоты квоты, затем рублёвый
   потолок.

**FACT (план 25.08, `2026-08-25-dry-run.json`).** 273 вызова (174 getTop +
60 getDynamics + 39 getRegions), 6,63 ₽; ограничитель — «исчерпан список задач»,
не квота и не бюджет.

**FACT (расход месяца по причинам, из журнала).** vendor_expansion 1759,
trend_monitoring 420, discovery 404, regional_research 227 вызовов. То есть 63 %
обращений — проверка ручного списка 149 кандидатов, а не обход собственного
каталога.

## 5. Что запрашивается у API

- **FACT.** Endpoint: `https://searchapi.api.cloud.yandex.net/v2/wordstat`
  (Yandex Cloud Search API v2; `client.py:27`). Методы: `/topRequests`
  (частотность + связанные фразы), `/dynamics` (помесячная динамика),
  `/regions` (региональное распределение). `/getRegionsTree` реализован, но не
  вызывается. Авторизация — `Api-Key` из секрета `WORDSTAT_API_KEY`.
- **FACT.** getTop: регион только 225 (Россия), глубина 300 фраз, окно —
  скользящие «последние 30 дней». getDynamics: `PERIOD_MONTHLY`, 12 месяцев,
  только завершённые месяцы, границы строго по первым числам (сервис отвергает
  произвольные даты — 27 вызовов 20.08 упали с HTTP 400, после чего написан
  диагностический `probe_dynamics.py`). getRegions: без параметра региона.
- **FACT.** Тарифы в `config.json` с датой действия (`config.py:24-33, 95-104`):
  getTop и getDynamics 20 ₽/1000, getRegions 50 ₽/1000. Квота: в конфиге
  500 запросов/час (подтверждена поддержкой Яндекса 20.08.2026), резерв 50 слотов;
  10 запросов/сек.
- **FACT.** Лимитер (`limiter.py`): token bucket 10 rps + скользящее часовое окно;
  состояние переживает прогон в `limiter-state.json`; при 429 — пауза 60 с с
  пробным запросом и удвоением до 900 с (не слепая блокировка на час); фактическая
  квота извлекается из текста ошибки и понижает лимит. Retry — 4 попытки с
  экспоненциальной задержкой, повторяются только сетевые сбои и 5xx.
- **RISK (расхождение).** Живой `limiter-state.json` содержит
  `requests_per_hour: 500`, но `observed_quota: 100` — сервис в какой-то момент
  ответил, что квота 100. Какая квота действует фактически — по состоянию данных
  установить нельзя; наблюдаемая цифра противоречит конфигу.

## 6. Жизненный цикл ответа

```
план (planner) → client.call
                   ├─ кэш-проверка (TTL) ──── попадание → ответ из кэша
                   ├─ budget.can_spend  ──── отказ → вызов не выполняется
                   ├─ limiter.acquire   ──── квота
                   └─ POST API
                        ↓ сырой JSON
   cache/<sha256>.json        ← сырой ответ сохраняется целиком (RAW)
   ledger/2026-08.jsonl       ← журнал: причина, стоимость, статус (append)
                        ↓
   universe.observe()         ← нормализация (NORMALIZED + HISTORY)
   semantic-universe.jsonl    ← 19 440 фраз × 37 полей (полная перезапись файла,
                                история — внутри полей строк)
                        ↓
   report.build_state():
     coverage → gaps (GAP-A…H) → playbook → opportunity → vendor_expansion
                        ↓
   intelligence-state.json    ← текущий срез аналитики (перезапись, без истории)
   YYYY-MM-DD-demand-report.md ← человекочитаемый отчёт (новый файл на дату)
                        ↓
   data_sync.sh push → ветка seo-data → (данные доступны ежедневному отчёту V4)
```

### Файлы и режим записи — FACT

| Путь (в `seo-data`) | Класс данных | Режим |

## 8. Достоверность накопленной «истории»

- **RISK (самозагрязнение ряда).** При кэш-хите `run.py:174-197` всё равно
  вызывает `universe.observe()`, и в `historical_frequency` дописывается точка с
  сегодняшней датой — хотя это повторное чтение того же ответа, а не новый замер.
  Пример: фраза «куплю aws» — 6 «наблюдений» подряд со значением 687.
  Из 56 многоточечных строк реально менялось значение только у 16.
  **BUSINESS IMPACT:** ряд выглядит как история спроса, но ею не является;
  посчитанный по нему тренд был бы фиктивным. (Честно оговорено и в самом коде:
  `universe.py:150-157` предупреждает, что скользящие 30-дневные окна соседних
  дней перекрываются и не образуют временной ряд.)
- **FACT (купленные и выброшенные данные).** 227 успешных вызовов getRegions
  (2,70 ₽ — 27 % всего расхода): ответы остались только в `cache/`, ни один
  модуль анализа их не читает (в `run.py:161-172` для регионов выполняется только
  запись в журнал; grep по `affinityIndex`/`RegionsDistribution` в аналитике пуст).
  Классификация: **UNUSED COLLECTION**.
- **FACT.** `intelligence-state.json` перезаписывается — сравнить покрытие спроса
  «сегодня против прошлой недели» машинно нельзя, только глазами по семи
  `*-demand-report.md`.

## 9. Бюджет и «проверка оплаты»

- **FACT.** `budget.py` — настоящий контроллер расходов: ни один платный вызов
  не выполняется без записи в журнал с причиной и стоимостью (`budget.py:115-142`);
  предохранители: жёсткая остановка 5 500 ₽/мес, мягкая 4 400 ₽ (остаются только
  вызовы для уже принятых решений), суточный потолок 400 ₽, пилотный 500 ₽.
  Плюс метрики эффективности: стоимость 1000 уникальных фраз, доля пустых ответов,
  доля дублей.
- **INFERENCE.** Практически бюджет ничем не ограничивает: расход 10 ₽ из 5 500 ₽.
  Дефицит — не деньги и не квота, а список задач (план исчерпывается).
- **FACT.** `payment_check.py` — не про оплату API. Он проверяет, принимает ли
  сайт вендора-кандидата оплату картой (маркеры Stripe/Paddle/цен), чтобы
  рекомендация «добавить вендора» была практически выполнимой. Вердикты:
  `card | likely_card | sales_only | unknown | unreachable`.
- **FACT.** Проверки состояния самого ключа/баланса Yandex Cloud нет; единственная
  диагностика — ручной `scripts/seo/wordstat_quota.py` (печать квотных заголовков).

## 10. Аналитические модули: что и как считается

| Модуль | Что считает | Ключевые пороги | Объяснимость |
|---|---|---|---|
| `coverage.py` | 6 уровней покрытия спроса (страница → индекс → топ-10 → клики → измерение конверсии → CRM), по частотности, не по числу фраз | топ-10 ≤ 10.0; слабый CTR < 1 %; кластер в разрывы от 100 показов | уровни и неатрибутированный спрос (52 137 показов/мес) показываются явно |
| `coverage.py` (gaps) | классы разрывов GAP-A…GAP-H, ровно один на кластер | — | у каждого разрыва — класс, название, фразы |
| `opportunity.py` | `score = demand × intent × coverage_gap × trend × confidence / effort` | effort по классу GAP (1.0–8.0); trend 0.5–1.3 | **полный provenance**: компоненты сохраняются и печатаются построчно |
| `vendor_expansion.py` | каких вендоров добавить в каталог | спрос ≥ 100, коммерческий ≥ 30; сортировка сначала по возможности оплаты | даёт готовые URL/title/H1/FAQ/фразы |
| `brand_dominance.py` | доля «софтверных» показов в омонимичных брендах (zoom = 96 % чужого спроса) | доля ≥ 0.70 и ≥ 200 показов | замеры сохраняются в `brand-dominance.json` |
| `playbook.py` | по каждому разрыву — шаг, готовый текст задания, критерий успеха, дата контрольной проверки | сниппет 7 дн, страница 21 дн, платный канал 30 дн | высокая |
| `audience.py` | фильтр аудитории: отклонённые руководителем бренды (`decisions.json`) и потребительские сервисы исключаются | — | причина исключения хранится |

**FACT (срез 25.08):** покрытие page 86,6 %, indexed 66,1 %, top10 24,2 %,
clicks 0,25 %; разрывы GAP-B 20, GAP-H 17, GAP-D 11; топ возможностей —
anthropic 0.179, google 0.155, adobe 0.090; кандидаты на расширение — 93 после
фильтров, 7 рекомендованы.

## 11. Можно ли использовать данные Wordstat отдельно от ежедневного отчёта?

**Ответ: YES** (с оговорками).

- Данные — плоские самодостаточные файлы (JSONL/JSON) без СУБД; у каждой фразы —
  provenance (seed, метод, даты, регион, стоимость, атрибуция).
- Аналитические модули (`universe`, `coverage`, `opportunity`,
  `vendor_expansion`, `brand_dominance`) — чистые Python-модули без обращений к
  сети: импортируются и работают по файлам независимо от `run.py` и от письма.

Оговорки:
1. данные лежат в ветке `seo-data`, не в `main` — нужен `data_sync.sh pull`;
2. привязка спроса к позициям/кликам требует снимков
   `reports/seo/intelligence/snapshots/<дата>.json`;
3. региональные данные доступны только как сырьё в `cache/` — парсера нет.

## 12. Возможен ли анализ трендов («как менялся спрос на X за 60 дней»)?

**Ответ: PARTIALLY.**

Работает: у 101 фразы (топ-фразы кластеров уровней A/B) есть честный помесячный
ряд за 12 месяцев (2025-08…2026-07); тренд считается сравнением средних двух
половин ряда (`universe.py:196-214`) — методологически корректно; питает
`TREND_FACTOR` и классы GAP-G/GAP-H.

Не работает:
1. гранулярность только месячная (API не отдаёт иначе) — «за 60 дней» = 2 точки;
2. покрытие 101 из 19 440 фраз (0,5 %); tier C не опрашивается никогда;
3. лаг ≥ 1 месяца (текущий месяц сознательно исключён);
4. дневной ряд `historical_frequency` непригоден (см. раздел 8);
5. истории агрегатов (покрытие, разрывы) нет — `intelligence-state.json`
   перезаписывается;
6. журнал существует только за август — финансовая история 6 дней.

**OPPORTUNITY (без проектирования, только фиксация потенциала).** При текущем
расходе 10 ₽/мес и потолке 5 500 ₽ расширение динамики на все коммерческие
кластеры, датированные срезы `intelligence-state`, отказ от дописывания точек при
кэш-хитах и парсинг уже купленных региональных ответов подняли бы историческую
ценность данных на порядок. Это кандидаты во вход следующего этапа
(NEXT STAGE INPUT основного отчёта).

## 12а. Разрыв со старым контуром `semantics/`

**FACT.** До Wordstat Intelligence (20.08) существовал первый контур спроса:
`reports/seo/semantics/` (`plan.json`, `clusters.json`, `discovery.json`,
`core-<дата>.json`, `brief-<дата>.json`, `gap-<дата>.md`, помесячный кэш),
скрипт-мост — `scripts/seo/semantics.py`. Именно `brief-*.json` до сих пор
читает `snapshot.build_market_demand` (`snapshot.py:485`) — блок
`market_demand` канонического снимка строится из него.

**RISK.** Каталог `semantics/` **не входит** в `DIRS` синхронизатора
`data_sync.sh` и живёт только в `main`; последний `brief` датирован
20.08.2026, вызов `semantics.py` не найден ни в одном workflow и ни в
промпте Routine. Следствие: `market_demand` в снимке строится по замеру
20.08 и будет стареть, при том что рядом Wordstat Intelligence обновляется
ежедневно (его состояние письмо V4 читает отдельно — из
`wordstat/intelligence-state.json`). Два контура спроса существуют
параллельно: старый — замороженный, новый — живой.
