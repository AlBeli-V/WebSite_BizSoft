## 1. Executive Summary (для владельца бизнеса)

**Что существует.** За 4 дня (20–23.08.2026) вокруг сайта построена
работающая автоматическая система маркетинговой аналитики. Каждое утро она:
собирает данные из Яндекс.Вебмастера, Google Search Console, Яндекс.Метрики и
GA4; отдельно измеряет рыночный спрос через Яндекс.Wordstat; проверяет живой
сайт; собирает всё в один проверенный «снимок дня»; формирует письмо
руководителю и полный веб-отчёт; предлагает приоритеты развития каталога с
объяснением «почему».

**Что она реально делает хорошо.** Методическая честность здесь выше, чем в
большинстве коммерческих систем: «нет данных» никогда не показывается как
ноль; причина изменения не называется без списка подтверждающих страниц;
показы сайта не выдаются за рыночный спрос; у каждой рекомендации есть
разложение на компоненты «почему». Перед отправкой письмо проходит 35+
автоматических проверок содержания и формы плюс 233 unit-теста.

**Где главная уязвимость.** Мозг системы — не программа на сервере, а
ежедневная сессия ИИ-агента (Routine в 09:00 МСК), которая по текстовому
регламенту запускает расчёты и отправку. Если эта сессия не запустится,
отчётность остановится молча: не будет ни письма, ни сигнала о том, что
письма не будет. Сбор данных при этом продолжится.

**Где путаница.** В репозитории сосуществуют три поколения системы (v1 с
упразднённым «Growth Score», замороженный первый контур спроса
`semantics/`, действующий V4 + Wordstat Intelligence); часть документации
отстаёт от кода; копии данных в main не вычищены после переезда в
ветку-хранилище.

**Насколько надёжны результаты.** Цифры в письме защищены хорошо (см. выше).
Основные риски достоверности — не в расчётах, а по краям: реестр задач для
блоков «От вас» и «Журнал» ведётся агентом вручную; «дневная история» части
Wordstat-данных частично фиктивна (повторные чтения кэша записываются как
новые наблюдения); тесты письма проверяют эталон от 19.08, а не сегодняшний
выпуск.

**Накопленный актив.** Данные собираются только с 17–18.08.2026 — истории
мало (8 дней), но структура для её накопления уже есть: сырые ответы
сохраняются, журналы append-only, у 101 ключевой фразы есть честная
12-месячная динамика спроса. Часть уже купленных данных не используется
вовсе (например, региональное распределение спроса — 27 % расходов на API).

## 2. Как система работает сегодня (человеческим языком)

Ночью и утром роботы (GitHub Actions) по расписанию складывают в отдельное
хранилище (git-ветка `seo-data`) свежие данные: в 04:20 — исследование спроса
Wordstat, в 05:40 — данные четырёх систем аналитики, в 07:05 — проверка, что
цели-конверсии считаются. В 09:00 просыпается ИИ-агент: он ещё раз запускает
сбор, строит из данных «снимок дня», прогоняет 19 проверок достоверности,
собирает письмо и веб-отчёт, прогоняет проверки письма и, если всё зелёное,
кладёт результат в хранилище. Сам факт появления письма в хранилище
автоматически запускает два финальных робота: один отправляет письмо на
почту руководителя (и помнит, что за этот день уже отправлял), второй
выкладывает веб-отчёт на сервер сайта по служебному адресу.

## 3. Суточный цикл

См. подробную хронологию в `marketing-workflow-map.md` §4. Кратко (МСК):

```
04:20 Wordstat полный цикл → seo-data     04:25/10:25/16:25/22:25 добор
05:40 сбор GSC/Вебмастер/Метрика/GA4 → seo-data
07:05 приёмка целей (письмо первую неделю после границы)
09:00 Routine: сбор повторно → снимок → качество → письмо → веб-отчёт →
      гейты → push seo-data → (авто) письмо на почту + публикация на сервер
каждый час :15 — выравнивание веток по main
Понедельник — недельный отчёт; 1-е число — месячный; 30.08 — контрольная
одноразовая Routine недели переезда данных.
```

FACT: цикл подтверждён фактическими запусками 25.08.2026 в GitHub Actions
(вплоть до времени срабатываний и коммита «Данные и веб-отчёт за 2026-08-25»).

## 22. Дополнительные найденные функции

1. **Measurement Management (N)** — реестр целей в коде сайта как единственный
   источник истины + автозаведение в кабинеты + приёмка + контроль прода.

3. **Vendor Source Intelligence (P)** — воспроизводимые снимки магазина

4. **Indexation Management (Q)** — sitemap-правило, recrawl, IndexNow,

5. **Action Management (R)** — actions.json (зоны GREEN/YELLOW/RED, стадии,
   владельцы) + тикеты + журнал issue #22; ведётся агентом вручную.

## 23. Что сейчас чрезмерно связано

1. **Routine-промпт** объединяет оркестрацию сбора, аналитику, ведение
   управленческого журнала, вёрстку, публикацию и правки сайта. Изменение
   текста промпта меняет всё сразу; сам промпт живёт в настройке внешнего
   сервиса (в репозитории — копия в `TRIGGER.md`).
   *Для бизнеса:* правка регламента письма может незаметно изменить сбор
   данных или порядок правок сайта.
2. **`wordstat/report.py`** — единый прогон всей аналитики спроса (модули
   при этом чистые и отделимые — связка лечится конфигурацией, не переписыванием).
3. **`snapshot.py`** — точка встречи 4 миров: сырые данные, реестр целей из
   кода сайта, реестр экспериментов, замороженный контур `semantics/`.
4. **`data_sync.sh`** — транспорт с семантикой «полная замена» и разрешением
   гонок «последний победил».
5. **Гейты качества письма ↔ доставка**: ложное срабатывание проверки формы
   останавливает доставку содержания (инцидент 25.08, issue #148 —
   письмо дня задержано из-за правила `google_claim_has_page_evidence`).

## 29. Функциональные домены для следующего этапа (только границы)

По результатам фактического аудита самостоятельными доменами являются:

1. **DATA COLLECTION** — collect.py + wordstat/run + site-check (уже отделён
   исполнением в Actions).
2. **SEARCH PERFORMANCE** — снимок/качество/драйверы.
3. **SEMANTIC & DEMAND INTELLIGENCE** — universe + coverage + динамика
   (примечание: Semantic и Demand сегодня — одна база; граница между ними
   тоньше, чем в исходной гипотезе).
4. **VENDOR INTELLIGENCE** — vendor_expansion + payment_check + decisions.
5. **CATALOG/CONTENT OPPORTUNITY** — gaps + playbook + opportunity.

## Как на самом деле устроена эта система (для владельца бизнеса)

У компании есть три потока информации о рынке и сайте.

**Первый поток — «как нас видно».** Каждое утро система забирает у Яндекса и
Google данные о том, сколько раз сайт показался в поиске, по каким словам и
как часто по нему кликали, а у систем статистики — сколько людей пришло и
что они сделали. Это зеркало собственного сайта: оно ничего не говорит о
тех, кто нас не нашёл.

**Второй поток — «что вообще ищут люди».** Отдельная подсистема спрашивает у
Яндекса статистику поисковых запросов по каждому производителю из каталога и
по полутора сотням производителей-кандидатов. Она умеет отличать покупательский
запрос («canva оплатить для юрлица») от случайного совпадения слов и ведёт
базу из почти двадцати тысяч фраз с пометками: есть ли у нас страница под эту
потребность, находят ли её, кликают ли. Из этого рождаются конкретные
предложения: какого производителя добавить, какую страницу создать или
переписать — каждое с числами «почему» и с проверкой, сможет ли клиент
вообще заплатить этому производителю картой.

**Третий поток — «правда ли сайт всё это измеряет».** Система регулярно
проверяет живой сайт: стоят ли счётчики, заведены ли цели, выкатились ли
изменения. Это страховка от самого дорогого сбоя — когда статистика тихо
перестаёт собираться, а по отчётам это выглядит как «клиентов стало меньше».

Каждое утро в девять по Москве все три потока сводятся в одно письмо и в
подробную веб-страницу. Письмо намеренно короткое и осторожное в
формулировках: система скорее промолчит, чем назовёт причину без
доказательств, и никогда не покажет ноль там, где данных просто нет. Если
данные за день сомнительны, письмо прямо об этом говорит; если проверки
письма не пройдены — письмо не отправляется вовсе, а в журнале появляется
тревожная запись (так случилось 25.08 из-за слишком строгой проверки — это
рабочий пример того, что защита реально останавливает отправку).

Слабое место сегодня одно, и оно архитектурное: утреннюю сборку отчёта
выполняет не «железный» робот, а ИИ-агент по расписанию. Роботы, которые
собирают данные и рассылают письма, продолжат работать и без него, но само
письмо без него не соберётся — и никто автоматически не заметит, что его нет.

Эти процессы частично пересекаются: правила письма, ведение журнала задач и
запуск расчётов описаны одним регламентом; аналитика спроса пересобирается
одним блоком. Поэтому изменение одного элемента сегодня требует осторожности —
границы между функциями существуют логически, но не технически.
