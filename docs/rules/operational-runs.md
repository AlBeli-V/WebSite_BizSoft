# Операционные прогоны — только GitHub Actions

Установлено руководителем 03.09.2026 по разбору расхода токенов. Действует
во всех ветках и сессиях. История прежнего механизма (Routine на сессиях
Claude, реестр, сторожа привязок) — `operational-routines-history.md`.

## Правило

Ежедневные и еженедельные прогоны, у которых все шаги детерминированы
(сбор данных, запуск скриптов, тесты, push в ветку данных, отправка письма,
проверка отправки), выполняются workflow GitHub Actions. Сессия модели для
них не заводится: она заново платила бы за клон, CLAUDE.md, зависимости и
контекст, а модельной работы в прогоне нет.

Каждый такой workflow устроен одинаково:

- **два cron-слота** — штатный и контрольный через 35–60 минут: планировщик
  GitHub пропускает отдельные слоты (27.08.2026 — шесть часов тишины,
  03.09.2026 — слот 01:20 UTC не выполнился), и второй слот закрывает
  пропуск без человека и без сессии;
- **сторож времени `seo-morning-gate`** для утренних контуров: 04–05.09.2026
  замер показал, что слоты этого репозитория стартуют в среднем на 4–5 часов
  позже назначенного (06:35 → 11:39, 07:05 → 12:01, 03:07 → 07:52), причём
  задержка одинакова для любого часа — перенос слота не помогает. Сторож
  просыпается каждый час с 22:00 до 09:00 UTC, тратит секунды и запускает
  конвейер, когда московское время попало в окно 09–13 и письмо за сегодня
  ещё не отправлено (`scripts/ops/morning_gate.sh`, тесты
  `scripts/seo/tests/test_morning_gate.py`). Ожидание внутри job не
  используется: репозиторий приватный, минуты тарифицируются, и сон до утра
  стоил бы около 8000 минут в месяц против примерно 360 у сторожа;
- **идемпотентность по артефакту дня** (дата по МСК): если файл за сегодня
  уже в ветке данных, прогон ничего не пересобирает и только проверяет
  отправку; ручной `workflow_dispatch` с `force=yes` — осознанный пересбор;
- **очередь** (`concurrency`, `cancel-in-progress: false`): слоты не
  собирают один отчёт параллельно;
- **явный запуск зависимых workflow** через `scripts/ops/gh_dispatch_wait.sh`:
  push из Actions под `GITHUB_TOKEN` не порождает push-событий, поэтому
  почтовые и публикационные workflow вызываются `workflow_dispatch` и
  дожидаются завершения;
- **одно письмо на дату** — маркер `last-*mailed.txt` в ветке данных
  проверяется до вызова почтового workflow (его ручной запуск маркер
  игнорирует);
- **тишина**: при успехе никаких сообщений; при сбое — одна запись в
  журнал-issue #22 со ссылкой на прогон, а уведомление руководителю даёт
  сторож почтового workflow (режим notice).

## Что ушло из ежедневного прогона Growth Intelligence

Прежний промпт Routine содержал два шага с участием модели:

- **Реестр действий** `intelligence/actions.json` — статусы, стадии, сроки.
  Теперь их обновляет PR, который внедряет действие (поле `status`,
  `status_changed_at`, `pr`), а не ежедневная сессия.
- **PR с правками карточек по измеренному спросу** — отдельная задача,
  ставится руководителем по данным письма, а не запускается каждый день.

Предпросмотр письма в чат (SendUserFile) не воспроизводится: руководитель
получает само письмо и ссылку на веб-отчёт.

## Приёмка и переход

1. После слияния в main новые workflow срабатывают по расписанию сами.
2. Первый прогон каждого контура проверяется по журналу Actions и по маркеру
   отправки в ветке данных.
3. Только после этого удаляются Routine в аккаунте Claude (иначе два
   механизма соберут один отчёт; письмо при этом не задвоится — маркеры
   отправки общие).
