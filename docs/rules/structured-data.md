# Регулярное правило: новые вендоры/товары → микроразметка

Установлено руководителем 29.08.2026. При добавлении вендоров и товаров
микроразметка Schema.org обязательна и делается ТОЛЬКО штатным слоем
(`src/lib/seo.ts`, компоненты `Breadcrumbs`/`FAQ`/`JsonLd`, microdata
карточки товара) — руками в шаблонах ничего не размечать. Один тип — один
раз на страницу (BreadcrumbList — только компонент Breadcrumbs, FAQPage —
только компонент FAQ). «Цена по запросу» — без Product/Offer вовсе;
фиктивные цены/рейтинги запрещены. Цена в разметке — из `effectivePrice()`.
Приёмка: `pnpm verify` (смоук сверяет JSON-LD ↔ microdata ↔ видимую цену).
Подробности: `docs/seo/structured-data-audit.md`,
`docs/vendors-expansion-prompt.md` (раздел 11).

## Дополнение 08.09.2026: один идентификатор — один узел

Повод: Search Console 01.09.2026 закрыла карточку `/product/mj-standard`
ошибкой «Поле "brand" дублируется» (плюс три незначительные — в том числе
дубль `sku`); элемент в отчёте был один — «Midjourney Standard».

Причина. Карточка выводит товар двумя сериализациями: JSON-LD (для Google)
и microdata (для Яндекса). Обе несли один и тот же идентификатор узла —
`@id` = `itemid` = `<canonical>#product`. Google связывает узлы разных
синтаксисов именно по общему идентификатору и сливает их в одну сущность:
объединённый товар получал `name`, `sku`, `url`, `image`, `description` и
`brand` по два раза. Ошибка была не в данных (слои совпадают по значениям),
а в том, что две сериализации назывались одним именем узла.

Правило. Идентификатор узла (`@id` в JSON-LD, `itemid` в microdata) не
встречается на странице дважды. Из этого следует:

- microdata-слой карточки товара `itemid` не несёт вовсе — это независимая
  сериализация того же товара, а не тот же узел;
- если нужны дополнительные поля у уже выведенного узла (локальный профиль
  организации на главной и в контактах), узел расширяется на месте, а не
  выводится вторым узлом с тем же `@id`.

Проверки: `pnpm smoke` (три проверки: карточка товара, главная и контакты,
полнота узла организации), `scripts/seo/check-structured-data.mjs` — правило
про повтор идентификатора работает и на проде через `ops-schema-check`.

Дополнение 08.09.2026 (после проверки исправления): рекомендованные поля
Offer — `hasMerchantReturnPolicy` и `shippingDetails` — обязаны быть в обоих
слоях. Значения берутся из одной функции `offerLogistics()` (`src/lib/seo.ts`):
JSON-LD — напрямую, microdata — через `OfferLogisticsMicrodata.astro`.

## Дополнение 15.09.2026: сторож разметки и отзывы

Письма Search Console 15.09.2026 («нет hasMerchantReturnPolicy», «нет
shippingDetails», «дубль sku» — и отдельно «нет aggregateRating», «нет
review») разобраны в `docs/seo/structured-data-implementation.md` §11:
проба прода показала, что первые два поля на живой странице есть, то есть
письмо описывает индекс до выкатки 13.09.

Решения руководителя:

- **Рейтинг и отзывы не заводятся.** Нет источника отзывов о товарах —
  значит, нет `aggregateRating` и `review`; это предупреждение Google, а не
  ошибка, и оно остаётся ожидаемым. Запрет фиктивных рейтингов (выше по
  тексту) действует и тогда, когда их просит сам Google.
- **Прод сторожит `ops-schema-check`** — понедельник, слоты 06:41 и 07:29
  МСК, очередь, идемпотентность по дню (успешный прогон за сегодня
  отменяет контрольный слот). При успехе тишина, при сбое — одна запись в
  issue #22. Ручной запуск с любой ветки по-прежнему возможен: прогон
  read-only, прод он не меняет.
