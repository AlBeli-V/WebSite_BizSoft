# Routine для операционных прогонов: только с привязкой к сессии

> **Заменено 03.09.2026.** Операционные прогоны переведены в GitHub Actions
> (`docs/rules/operational-runs.md`); Routine на сессиях Claude, реестр
> `ops/routines/` и сторожа привязок упразднены. Текст ниже сохранён как
> история: почему механизм Routine оказался ненадёжным и что пробовали.

Установлено 02.09.2026 после разбора: страховочные Routine («Добивка ночного
SERP», «Добивка Wordstat», «Сторож письма конкурентной разведки»,
«BIZSoft Конкурентная разведка», «Growth Committee») с 01.09 не работали ни
разу и слали руководителю ложные тревоги «нет доступа к репозиторию и
GitHub MCP».

Причина в механизме, а не в коде. Routine, созданная инструментом
`create_trigger` в режиме «новая сессия при каждом срабатывании»
(`create_new_session_on_fire`), порождает сессию **без рабочей копии
репозитория и без connector-инструментов** (`mcp__github__*`): у такой
сессии пустой `session_context` и теги `config:routine-lineage-none`,
`routine:agent-minted`. Параметра для указания репозитория у
`create_trigger` нет вовсе, и наследование от вызывающей сессии не
происходит — проверено экспериментом. В такой сессии не работают ни
`git fetch origin seo-data`, ни `actions_run_trigger`.

Правило: **Routine, которой нужны репозиторий, ветки данных или запуск
workflow, заводится только с `persistent_session_id`** — привязкой к
постоянной сессии-исполнителю, созданной через `create_session` с
`source_url` (репозиторий подключается, GitHub MCP доступен). Режим
«новая сессия при каждом срабатывании» годится только для заданий, которым
не нужен ни репозиторий, ни GitHub. Альтернатива — завести расписание
через веб-интерфейс claude.ai/code, где репозиторий выбирается явно.

- Сессии-исполнители помечены тегами `ops-routine` и `ops-<контур>`;
  ежедневная проверка — модель Sonnet, аналитический прогон с отчётом —
  Opus.
- Контекст постоянной сессии растёт с каждым прогоном: раз в один-два
  месяца исполнителя пересоздавать (новая сессия с `source_url`, у Routine
  сменить `persistent_session_id`), старого архивировать.

### Приёмка привязки: проверять сессию, а не флаг Routine

Дополнено 03.09.2026 после второго инцидента. Ночью не отработала «Добивка
ночного SERP»: исполнитель доложил, что рабочей копии нет и GitHub MCP не
грузится. При этом все 14 Routine формально проходили прежнюю приёмку —
`persist_session: true` и непустой `persistent_session_id` стояли у всех.
Прежней приёмки НЕДОСТАТОЧНО, флаг врёт по двум причинам, и обе встретились
в одном разборе:

1. **Привязка в пустоту.** `persistent_session_id` указывает на сессию,
   которой не существует: `get_session` отвечает «the requested resource
   was not found». Так были сломаны «Добивка Wordstat», «Сторож письма
   конкурентной разведки» и «Проверка операционных Routine».
2. **Сессию выпустил планировщик.** Если у Routine к первому срабатыванию
   нет годной привязки, сервер сам заводит сессию и записывает её в
   `persistent_session_id` — задним числом карточка Routine выглядит
   правильной. Такая сессия создана без репозитория: `origin` —
   `scheduled_trigger`, теги `config:routine-lineage-none` и
   `routine:agent-minted`, в `session_context` нет `sources`. Так была
   сломана «Добивка ночного SERP».

**Приёмка идёт по карточке самой сессии-исполнителя, а не по карточке
Routine.** Заведя или пересоздав Routine, вызвать `get_session` по её
`persistent_session_id` и убедиться, что выполнено всё:

- вызов вернул сессию (ответ «not found» = привязка указывает в пустоту);
- в `session_context.sources` есть `git_repository` нужного репозитория;
- в `tags` нет `config:routine-lineage-none` и `routine:agent-minted`;
- `origin` — `claude_code_mcp_seed` или `web_claude_ai`, но не
  `scheduled_trigger` и не `force_run_trigger`.

Ни привязку, ни промпт привязанной Routine `update_trigger` сменить не
даёт — отказывает с «editing the prompt of a routine whose fires deliver
into a session that is not your own is not available via this tool»;
правится только пересозданием. Порядок заведения исполнителя целиком:

1. `create_session` с `source_url` https://github.com/AlBeli-V/WebSite_BizSoft,
   тегами `ops-routine` + контурный тег и подготовительным прогоном —
   прогон заодно проверяет рабочую копию, ветку данных и GitHub MCP.
2. `get_session` по новой сессии — приёмка из четырёх пунктов выше.
3. `create_trigger` с `persistent_session_id` этой сессии.
4. `delete_trigger` старой Routine, старую сессию архивировать.
5. Приёмка — по первому срабатыванию ПО РАСПИСАНИЮ: `get_session` по
   исполнителю, у него обязан сдвинуться `updated_at`. Пока этого не
   произошло, Routine считается непринятой.

**`fire_trigger` для приёмки не годится** (установлено 03.09.2026
экспериментом). Ручной запуск игнорирует `persistent_session_id`: он
заводит отдельную сессию с `origin: force_run_trigger`, тегами
`config:routine-lineage-none` и `routine:agent-minted` и пустыми
`sources` — то есть ровно ту калеку, от которой мы уходим. Прогон уходит
в неё, исполнитель не шевелится, и «контрольный прогон» проверяет не то.
Отсюда же признак обойдённой привязки в ежедневном стороже: `last_fired_at`
у Routine свежий, а `updated_at` у сессии-исполнителя старый.

### Контур чинится сам: реестр вместо тревог

Установлено руководителем 03.09.2026: операционные прогоны работают на
автомате — без обращений к руководителю и без уведомлений. Ни одна Routine
больше не пишет «сломана привязка, чинить должен человек».

Источник истины — `ops/routines/registry.json` в main: какие Routine должны
существовать, с каким расписанием, моделью, тегами исполнителя и файлом
промпта из `ops/routines/prompts/`. Живое состояние приводится к реестру, а
не наоборот.

- Ежедневный сторож «Проверка привязок операционных Routine» (10:00 МСК)
  читает реестр, сверяет каждую запись по карточке сессии-исполнителя и
  **сам** пересоздаёт сломанные контуры: заводит сессию с `source_url`,
  проверяет её `sources`, создаёт Routine заново, удаляет старую.
- Сам себя сторож починить не может — сломанная Routine не запускается.
  За ним присматривает ночная «Добивка ночного SERP» (02:45 МСК): раздел
  «Взаимный присмотр за сторожем» в её промпте восстанавливает сторожа по
  тому же реестру.
- Записи с `"autoheal": false` (сейчас — Growth Intelligence) автоматически
  не пересоздаются: они привязаны к рабочим сессиям с накопленным
  контекстом, его потеря дороже простоя.
- Тишина. Руководителю уходят только деловые результаты — письма
  конкурентной разведки и Growth Committee через почтовые workflow. Всё
  инфраструктурное идёт одной записью в журнал-issue #22, и только когда
  что-то делалось. Метка `alert` — для контуров с `autoheal: false` и для
  починки, не удавшейся после трёх попыток.
- Промпты правятся в `ops/routines/prompts/` через PR, а не вслепую в
  интерфейсе. В силу правка вступает, когда сторож пересоздаёт контур:
  `update_trigger` промпт привязанной Routine менять отказывается.
- Приёмка сборкой: `pnpm test` прогоняет `tests/ops-routines-registry.test.ts`
  — реестр разбирается, у каждой автоматически чинимой записи есть непустой
  промпт, cron корректен, имена уникальны, у сторожа есть присматривающий.

Подробности — `ops/routines/README.md`. Прежняя проверка была ежемесячной,
смотрела только на флаг и требовала человека — она пропустила обе поломки.
