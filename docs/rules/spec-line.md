# Спецификация для подготовки предложения (`/cart`)

Постановка руководителя 15.09.2026 по семи образцам договорных
формулировок. Правило глобальное: страница одна, и всё, что на ней
появляется, собирается из данных каталога, а не пишется руками.

## Заголовок и состав таблицы

Заголовок страницы — `СПЕЦИФИКАЦИЯ ДЛЯ ПОДГОТОВКИ ПРЕДЛОЖЕНИЯ` прописными,
без слов «Подборка для КП»: они уже сказаны кнопкой меню, крошками и
вкладкой. Прописные задаёт CSS — в разметке остаётся обычное предложение,
чтобы копия в буфер и читалка получали нормальный текст. Под заголовком —
строка о том, что со спецификацией будет дальше.

Слева от описания каждой позиции стоит знак производителя из пакета
`src/assets/vendor-icons` — тот же, что в шапке и в каталоге. Карта
«слаг → адрес файла» собирается на сервере во фронтматтере страницы и
уезжает в скрипт целиком: строки рисует браузер, а хешированные адреса
известны только сборке. Производитель без знака получает нейтральную клетку
с первой буквой имени — чужой логотип не подставляется
(`docs/rules/product-logos.md`).

Колонок пять:

| Колонка | Что в ней |
|---|---|
| `ОПИСАНИЕ` | три строки: производитель и название, артикул, договорная фраза |
| `КОЛ-ВО` | поле ввода, под ним ряд из кнопок `−` и `+` |
| `ЦЕНА РУБ` | цена единицы, уже с арендой почты, если она выбрана |
| `СУММА РУБ` | `ЦЕНА × КОЛ-ВО` — строка обязана сходиться |
| знак корзины | красный крестик в каждой строке |

Номера позиции и отдельной колонки производителя нет: номер до выпуска
предложения ничего не значит, а производитель переехал в первую строку
описания, где стоит рядом с юридическим названием — как в предмете
договора. Заголовок колонки удаления — знак корзины; слово «Удалить»
осталось доступным именем ячейки (`aria-label`), но не повторяет крестик
в каждой строке.

Счётчик количества — в два яруса: поле сверху, кнопки под ним. Ряд
`− 2 +` требовал почти восьми рем и на телефоне раздвигал таблицу.

Итоговые строки (`ИТОГО, в т.ч. НДС 5%`, `НДС 5%`) — жирные: и подпись, и
сумма. Под таблицей — плашка предварительного расчёта: жирный зачин
`ИТОГО (предварительный расчет для целей бюджетирования):`, под ним сумма
цифрами крупно и жирным, ниже — расшифровка прописью обычным начертанием.

Справа — карточка итога: `ИТОГО`, сумма крупно, строка `в т.ч. НДС 5% — …`
с копейками, кнопки «Получить КП» и «Поделиться списком» со знаками, ниже
условия поставки строками со знаком, заголовком и подписью. Под карточкой —
плашка «Нужна помощь?» со ссылкой на контакты.

## Описание позиции — заготовка предмета договора

```
Anthropic PBC / Claude Team, Standard seat
Артикул: ANTH-LIC-CLAUDETEAM-TEAM-1Y-USER-STD
Оказание услуг по предоставлению доступа к web-сервису Claude производства
компании Anthropic PBC в рамках тарифного плана Team, (тип рабочего места —
Standard seat) сроком на 1 (один) календарный год
```

Собирает `specLine()` (`src/lib/spec-line.ts`) — единственное место, где
рождается этот текст. Его же вызывает контур КП: расхождения между тем, что
видит покупатель, и тем, что уходит письмом, быть не может.

Вид фразы определяют данные, а не похожесть названия:

| Вид позиции | Откуда виден | Фраза |
|---|---|---|
| подписка | `LIC` + срок | «доступа к web-сервису / ПО X … в рамках тарифного плана / плана подписки Y … сроком на N …» |
| ключ активации | `LIC` + `PERP` | «доступа к ключу активации ПО X … в рамках тарифного плана Y» (срока нет) |
| дополнение | `ADD` | «доступа к дополнению «X» к ПО Y … сроком на N …» |
| кредиты | `CRD` | «доступа к вычислительным ресурсам API веб-сервиса X путём зачисления API-кредитов номинальной стоимостью N …» |
| подарочная карта | `GFT` | «доступа к цифровому коду пополнения баланса X номинальной стоимостью N (регион — R) …» |
| услуга производителя | `SVC` | «Оказание услуг компании X по позиции «…»» |

Морфология считается, а не пишется: `1 (один) календарный год`,
`2 (два) календарных года`, `5 (пять) календарных лет`,
`3 (три) календарных месяца`. Номинал склоняется так же:
`100,00 долларов США`, `16 000 (шестнадцать тысяч) кредитов`.

## Форма поставки — реестр, а не догадка

`web-сервис` или `ПО` берётся из `src/data/spec-delivery.json`: точечная
правка по артикулу (`bySku`), затем поимённое исключение по производителю
(`byVendor`), затем умолчание его домена из `src/data/vendors.ts`
(`defaultByDomain`). Производитель, которого нет в реестре лендингов,
называется нейтрально — «программный продукт»: соврать о форме поставки
в предмете договора нельзя. Новый вендор-сервис из «неайного» домена —
одна строка в `byVendor`, а не правка кода.

Тарифный план вынимается из названия по словарю планов; у линеек, где
план — это сам продукт (JetBrains), планом становится имя продукта, а
предметом — марка. Тип рабочего места берётся из хвоста названия
(`, Standard seat`) — это различитель позиций одного плана.

Принадлежность лицензии в названии не ищется. Каталог унифицирован, тип в
имени товара не пишется, и фраза берёт его из сегмента `ПЛАН` артикула —
того же, что печатает плашку карточки (`docs/rules/product-markers.md`):
`TEAM` — «тип лицензии — корпоративная», `IND` — «тип лицензии —
индивидуальная», `UNI` — деления нет и в договоре о нём не пишут. Маркеры
вроде «(личная лицензия)» из старых имён вычищаются: подборка живёт в
браузере покупателя и по ссылке «поделиться», и позиция, положенная туда до
унификации, не должна назвать тип дважды.

## Приёмка

`tests/spec-line.test.ts` — образцы формулировок, морфология срока и
номинала, реестр форм поставки (каждый вендор реестра разрешается, мёртвых
записей нет). Вёрстка страницы — `pnpm check:mobile`: таблица
прокручивается внутри себя, страница вбок не едет.
