# Методика отчётности BIZSoft Search Performance (v3.0.0)

## Принципы

1. Единственный источник цифр — канонический snapshot `reports/seo/intelligence/snapshots/<дата>.json`.
   В шаблонах отчёта нет вручную вписанных значений.
2. Отсутствующее значение — `null` и «нет данных». Ноль означает измеренный ноль.
3. Каждое утверждение маркируется: **ФАКТ** (видно в данных), **ИНТЕРПРЕТАЦИЯ** (объяснение),
   **ГИПОТЕЗА** (требует проверки), **РЕШЕНИЕ**, **РИСК ДАННЫХ**.
4. Критическая ошибка качества данных запрещает общий «зелёный» статус и подавляет зависящие выводы.

## Определения метрик

| Метрика | Определение | Источник |
|---|---|---|
| Показы | сколько раз страницы сайта показаны в выдаче по запросам источника. **Не** объём рыночного спроса | Вебмастер (выборка топ-100 запросов), GSC |
| Клики | переходы из выдачи по тем же запросам | Вебмастер, GSC |
| CTR | клики / показы; рассчитывается только при показах > 0 | производная |
| Средняя позиция | среднее по показам; не фиксированное место в выдаче | Вебмастер, GSC |
| «В топ-10» | средняя позиция ≤ 10 строго | производная |
| Визит | `ym:s:visits` Яндекс.Метрики | Метрика |
| Сессия | сессия GA4; не равна визиту Метрики | GA4 |
| Целевое событие | срабатывание цели Метрики (`ym:s:sumGoalReachesAny`); **не** заявка и не лид | Метрика |
| Уникальное обращение | дедуплицированное обращение одного пользователя | нет данных до DATA-001 |
| Квалифицированный лид, сделка, выручка | подтверждённые в CRM | нет данных (CRM не подключена) |

## Периоды и сравнения

- Периоды каждого источника фиксируются в snapshot: начало, конец, число дней, дата сбора,
  последняя доступная дата события.
- Относительное изменение публикуется только при равной длине периодов и предыдущем значении > 0.
- Скользящие окна (Вебмастер) пересекаются между сборами — для них публикуется абсолютное изменение
  с пометкой о пересечении, проценты не публикуются.
- При пересборе источника внутри дня каноническим считается последний сбор; факт пересмотра
  фиксируется в `data_revisions` и в отчёте.

## Округление

CTR — два знака после запятой в процентах; средняя позиция — один-два знака; абсолютные значения —
целые. Проценты изменений — один знак.

## Brand / non-brand, query / page

- Брендовым считается запрос, содержащий маркеры бренда (`bizsoft`, `биз софт`, `бизсофт`, `biz-soft`).
- Показатели по запросам и по страницам не смешиваются: средняя позиция страницы усредняется по её
  запросам, средняя позиция запроса — по его показам. Любая сводка указывает scope.

## Низкая выборка и доверие

| Порог | Значение | Следствие |
|---|---|---|
| показы | < 50 | выводы о видимости помечаются как ранний сигнал |
| визиты | < 20 | выводы о конверсии не публикуются как факт |
| конверсии | < 5 | только предварительный сигнал, обязательно указывается n |

Пороги конфигурируются в `scripts/seo/snapshot.py` (`THRESHOLDS`).

## Проверки качества данных

Выполняются до генерации текста (`scripts/seo/quality.py`), результат — sidecar
`reports/seo/intelligence/data-quality/<дата>.json`. Коды: `ROLLING_WINDOW_OVERLAP`,
`YANDEX_SAMPLE_SCOPE`, `SOURCE_RECONCILIATION` (critical), `PERIOD_MISMATCH`, `MEASUREMENT_CHANGE`,
`INTRA_DAY_REVISION`, `BASELINE_REVISED`, `LOW_CONVERSION_SAMPLE`, `GOAL_UNIQUENESS_UNKNOWN`,
`SCOPE_QUERY_VS_PAGE`, `LOW_IMPRESSION_BASE_GOOGLE`, `NO_CTR_MODEL`, `NO_CRM`,
`INDEXATION_UNCLASSIFIED`.

## Статусы вместо общего балла

Четыре независимых статуса: **видимость**, **захват трафика**, **конверсия**, **качество данных**.
Каждый сопровождается фактическим основанием. Общее предложение статуса выводится из них
автоматически. Композитный Growth Score в v2 **не рассчитывается**: его компонент
`yandex_engagement` опирался на неутверждённую CTR-модель, а сложение Яндекса и Google выполнялось
без нормализации. Историю прежних значений см. `reports/seo/intelligence/score-history.json`.

## CTR-модель

Утверждённой кривой CTR по позициям нет, поэтому «ожидаемый CTR» и «потерянные клики» не
публикуются. Построение внутренней кривой возможно при накоплении истории в разрезе:
поисковая система × позиция × устройство × brand/non-brand.

## Правила формулировок

| Запрещено | Корректно |
|---|---|
| «Яндекс наращивает доверие» | «Число страниц в индексе — 169, изменение к канонической базе: 0» |
| «HeyGen ищут 96 раз» | «Страницы получили 96 показов по запросам кластера HeyGen» |
| «Статья конвертит 60%» | «3 целевых события при 5 визитах; выборка мала, уникальность не подтверждена» |
| «Уже в топ-5» | «3 показа, средняя позиция 4,3; ранний сигнал» |
| «Правка превратит рост в деньги» | «Гипотеза: более релевантный сниппет может повысить CTR; влияние на лиды не измеряется» |
| «лучший день», «стабильно», «гарантированно», «единственное узкое место», «заявка», «спрос» | формулировки с указанием базы, периода и ограничения |

## Правила экспериментов

- Один эксперимент — одно изменение. Метаданные и контентные блоки разделяются.
- Обязательны: baseline до внедрения, контрольная группа, дата деплоя, дата появления изменения
  в выдаче, primary metric, guardrails, минимальный объём наблюдений, дата оценки, владелец.
- Вывод: **успех** (достигнута primary metric при непострадавших guardrails и достаточном объёме) ·
  **недостаточно данных** (объём ниже минимального — публикуется описательный вывод) ·
  **отрицательный результат** (метрика не достигнута или guardrail ухудшился).
- Фиксированный срок «7 дней» основанием для вывода не является.

## Executive email V3 (с 2026-08-19)

### Структура и объём
Письмо — управленческий продукт, а не выгрузка. Порядок блоков фиксирован:
заголовок и дата · итог дня (не более двух предложений) · «от вас» · четыре показателя ·
«система уже делает» · «что изменилось» · риски · следующая проверка · кнопки.
Видимый объём — 450–650 слов; alt-тексты и подвал считаются отдельно и не дублируют данные.
Полная таблица свежести заменена строкой «Данные: Яндекс/Google по DD.MM; Метрика/GA4 по DD.MM».

### Зоны ответственности и автономность
| Зона | Кто выполняет | Появляется в письме как |
|---|---|---|
| GREEN | агент автономно | «Система уже делает» |
| YELLOW | агент, руководителя информируем | «Система уже делает» |
| RED | руководитель: бюджет, юридические обязательства, цены, домены, необратимые изменения | «Требуется ваше решение» |

Владельцы GREEN и YELLOW назначаются картой ролей `reports/seo/intelligence/actions.json`;
формулировка «ответственного назначает руководитель» для них запрещена. Если RED-действий,
ожидающих решения, нет — блок «От вас» показывает «действий не требуется».

### Составной статус
Вместо одной фразы о видимости публикуются три: Яндекс (стабильно / смешанная динамика),
Google (ранний сигнал на низкой базе / без выраженной динамики) и общий вывод.

### Правило нулевой дельты
Если изменение равно нулю, в соответствующем блоке запрещены слова «вырос», «рост»,
«увеличился», «снизился», «падение». Корректная форма: «Количество страниц в поиске не изменилось — 169».
Проверяется автоматически (семантический тест и UX lint).

### Совместные внедрения
Изменения, выкаченные одной правкой, оцениваются как один эксперимент. Ретроспективное разделение
на независимые эксперименты запрещено: вклад элементов неразделим по построению.

### Визуализация в письме
Inline SVG запрещён. Графики — PNG 2x, ширина отображения 610 px, встраиваются вложениями (CID),
у каждого обязателен alt и одно предложение текстового фолбэка. Максимум два изображения.
Сквозная воронка не показывается, пока не завершена сверка источников: вместо неё «Карта измерения»
с явным разрывом сопоставимости.

### Язык письма
Технические термины (`SOURCE_RECONCILIATION`, guardrails, snapshot, `ym:s:visits`, popular queries,
rollback, stop-condition, key events) в теле письма запрещены — их место в приложении и словаре.
Идентификаторы задач допускаются как вторичная метка со ссылкой на тикет.

### Проверки письма (UX lint)
`scripts/seo/uxlint.py`: объём, число карточек показателей / изменений / действий, число изображений,
отсутствие inline SVG, размер шрифта (тело ≥14 px, метаданные ≥12.5 px), alt у изображений,
абсолютные ссылки вместо локальных путей, запрещённые термины, противоречие нулевой дельты,
запрет воронки до сверки, запрет раздельной оценки совместного внедрения, автоназначение владельцев.

## Рыночный спрос: Вордстат (с 2026-08-19)

Доступ проверен на живом ключе 19.08.2026. Источник подключён отдельно от источников
видимости и не смешивается с ними.

### Контракт API

- Хост: `https://searchapi.api.cloud.yandex.net/v2/wordstat` (Yandex Cloud Search API v2).
  Прежний адрес `api.wordstat.yandex.net` не обслуживает этот ключ — TLS-сертификат не
  соответствует имени хоста.
- Авторизация: заголовок `Authorization: Api-Key <ключ>` (секрет `WORDSTAT_API_KEY`,
  формат ключа `AQVN…`, 40 символов). `Bearer` и `Api-key` принимаются тоже; `folderId`
  не требуется.
- Методы: `POST /topRequests` (частотность и связанные фразы), `POST /regions`
  (разбивка по регионам: `region`, `count`, `share`, `affinityIndex`),
  `POST /getRegionsTree` (справочник регионов, 1103 узла),
  `POST /dynamics` (динамика; обязательны `period`, `fromDate`, `toDate` в RFC3339).
- `topRequests` принимает `phrase`, `numPhrases` (1–2000), `regions`, `devices`
  (`DEVICE_ALL` / `DEVICE_DESKTOP` / `DEVICE_PHONE` / `DEVICE_TABLET`).
  Ответ: `results[{phrase,count}]`, `associations[{phrase,count}]`, `totalCount`.
  Фактическая глубина выдачи ограничена данными: запрос 2000 фраз по «canva» вернул 1293.

### Единицы и запрет на подмену понятий

- Показы Вордстата — объём поисковых запросов в Яндексе за 30 дней. Это спрос,
  а не покупки, не заявки и не выручка.
- Данные Яндекса не переносятся на Google.
- Пустой ответ `{}` означает «частотность ниже порога выдачи», а не ноль. В снимке
  такой кластер получает статус `below_threshold` и значение `null`.
- Частотность зависит от региона, типа соответствия и сезона. По умолчанию
  фиксируются регион 225 (Россия), широкое соответствие, все устройства;
  любое отклонение указывается рядом с числом.
- Доля голоса (наши показы к рыночным) не рассчитывается до закрытия DATA-001:
  охват и периоды источников не сверены, а наша видимость известна только по
  выборке топ-100 запросов Вебмастера.

### Лимит сервиса и его следствия

Замер 19.08.2026: HTTP 429 с текстом
`search-api.wordstatRequestsPerHour.rate rate quota limit exceed: allowed 100 requests`.
Ограничение — **100 запросов в час на облако**, а не в сутки. Это 2 400 запросов
в сутки, то есть согласованный месячный бюджет 10 000 запросов лимитом не блокируется,
но один длинный проход в один час не помещается.

Следствия для конвейера:
- Сбор возобновляемый: помесячный кэш `semantics/cache-<ГГГГ-ММ>.json` хранит уже
  полученные ответы, каждый прогон добирает до 90 новых фраз и останавливается.
- Полный проход по каталогу (около 560 запросов) занимает примерно семь часовых
  прогонов; воркфлоу запускается ежечасно 1–2 числа месяца.
- В снимке пишется `quota.collected_total / planned_total` и признак `complete` —
  выводы по неполному проходу помечаются как предварительные.
- Лимит относится к облаку целиком: ручные проверки в консоли и прогоны сборщика
  расходуют одну и ту же квоту. Квоту можно поднять заявкой в поддержку Yandex Cloud.

### Наблюдаемое поведение (замеры 19.08.2026)

- Задержка ответа 0,45–0,7 с; ограничения по частоте в секунду не замечено —
  упирается именно часовой счётчик.
- Региональный срез сильно меняет число: «canva» — 143 009 без региона,
  119 076 по России, 15 529 по Москве, 6 830 по Санкт-Петербургу.
- Срез по устройствам: 85 539 десктоп, 52 802 телефон, 4 666 планшет.
- Кавычки и оператор `!` поддерживаются и дают более узкие числа, вплоть до
  пустого ответа на низкочастотных фразах.

### Согласованные полномочия (решение руководителя 19.08.2026)

- Бюджет обращений к Вордстату — до 10 000 запросов в месяц. Фактический расход
  пишется в `quota` каждого снимка; потолок одного прогона — 3 000 запросов.
- Правки карточек товара по данным спроса агент готовит и вносит самостоятельно,
  включая слияние в main. Обязательные условия: изменение опирается на измеренную
  коммерческую фразу из `semantics/core-<дата>.json`, тесты и сборка проходят,
  каждая правка описана в PR с указанием фразы и её частотности.
- Цены, юридические обязательства, домены и рекламный бюджет остаются за руководителем.

### Регламент сбора

- Частотность обновляется помесячно (воркфлоу `seo-wordstat.yml`, 1-е число),
  а не ежедневно: суточная квота конечна, а сезонность считается по месяцам.
- План запросов строится из каталога сайта: `build_clusters.py` читает
  `src/data/vendors.ts` и добавляет к каждой карточке коммерческие модификаторы
  («купить», «оплата», «для юридических лиц», «тариф», «подписка», «лицензия»).
  Ручные тематические кластеры и приоритеты — в `reports/seo/semantics/clusters.json`.
- Разведка рынка — `reports/seo/semantics/discovery.json`: бренды вне каталога
  проверяются одной фразой покупки на юрлицо.
- Глубина выдачи (`numPhrases`) квоту не тратит — это один и тот же запрос;
  квоту тратит число фраз, поэтому расширяется в первую очередь глубина.
- Фразы кластера фильтруются якорем бренда. Без фильтра транслитерации притягивают
  омонимы: по «корел купить» приходят «корал тревел», «пионы корал шарм»,
  «корела водка» — на замере 19.08.2026 это давало 24 922 чужих «коммерческих»
  показа у CorelDRAW. Число отброшенных фраз пишется в снимок.
- Артефакты: `core-<дата>.json` (спрос, сезонность, регионы, разведка с метаданными
  региона, соответствия и окна), `gap-<дата>.md` (разрывы и кандидаты),
  `brief-<дата>.json` (выжимка для приложения к письму).
- Решение по карточке принимается по сумме показов коммерческих фраз, а не по общей
  частотности бренда: у «canva» 119 076 показов, из них покупательских — единицы.
- В письмо руководителю попадают только выводы уровня решения; таблицы спроса —
  в приложении.

### Спрос в ежедневном отчёте (с 19.08.2026)

Спрос обновляется раз в месяц, а отчёт выходит ежедневно. Месячная величина,
показанная как суточное изменение, — выдуманная динамика, поэтому источник входит
в письмо строго в трёх местах и ни в одном другом.

1. **Строка свежести.** Одна фраза: дата замера, пометка «собирается», если проход
   не завершён, и периодичность обновления. Читатель сразу видит возраст данных.
2. **Обоснование действия.** У действия, вызванного разрывом семантики, выводится
   строка «Зачем»: до двух фраз и их частотность за месяц. Так каждое действие в
   письме опирается на измеренное число, а не на мнение. Связь действия с кластерами
   задаётся полем `demand_clusters` в `intelligence/actions.json`; без замера строки нет.
3. **Событие обновления.** Запись в блоке «Что изменилось» появляется только в день
   нового замера и прямо говорит: это обновление картины рынка, а не изменение наших
   показателей за сутки. В остальные дни спрос в этом блоке молчит.

Чего спрос не делает:

- **Не становится показателем дня.** Среди четырёх карточек показателей его нет и быть
  не может — тест `test_demand_never_becomes_a_kpi_card` это фиксирует.
- **Не сравнивается с нашими показами.** Доля голоса не рассчитывается, пока не закрыт
  DATA-001: наша видимость известна по выборке топ-100 запросов Вебмастера.
- **Не подменяет спрос покупательским намерением.** Решение принимается по сумме
  коммерческих фраз, а не по частотности бренда.

Проверки: `MARKET_DEMAND_ABSENT`, `MARKET_DEMAND_STALE` (старше 45 дней),
`MARKET_DEMAND_PARTIAL` (проход не завершён), `DEMAND_NOT_COMPARABLE_TO_VISIBILITY`.
Правила публикации: `allow_market_demand_wording` включается только при наличии замера,
`allow_assortment_decisions` — только при завершённом проходе.
Правила письма: `demand_not_daily` (нельзя смешивать месячный спрос с суточными словами)
и `demand_not_our_impressions` (нельзя выдавать спрос за наши показы).

Вся тяжесть — в приложении, раздел 15: таблица коммерческого спроса по карточкам,
разрывы, кандидаты-товары, полнота замера и ограничения источника.

# V4 — Executive Command Center (с 19.08.2026)

## Исправление методики DATA-001

Прежняя постановка требовала свести Вебмастер, Метрику и GA4 к одному определению
визита. Это была ошибка: источники измеряют разные сущности на разных охватах, и
приведение их к одному числу означало бы потерю смысла, а не устранение проблемы.

Зафиксированы пять самостоятельных сущностей: показы Вебмастера, клики Вебмастера,
визиты Метрики, сессии GA4, обращения CRM. Каждая описана в карте измерений полями
`source`, `metric`, `entity`, `scope`, `period`, `filters`, `coverage`,
`comparable_with`, `difference_explanation`.

Запрещено называть 6 кликов по выборке 100 запросов и 37 органических визитов всего
сайта «кратным расхождением источников»: пока охваты не совпадают, это разные
множества, а не противоречие. Показы и клики одной выборки сравнимы между собой,
поэтому публикуется **CTR выборки** с обязательной пометкой охвата.

Статус здоровья данных:

| Статус | Когда | Цвет |
|---|---|---|
| `verified` | охваты и периоды сопоставлены | зелёный |
| `limited` | источники исправны, охваты различаются | жёлтый |
| `degraded` | источник сломан, сбор не прошёл, разметка сломана | красный |

Красный блок разрешён только при реальном сбое: отказ источника, пропущенный сбор,
сломанное отслеживание, повреждённый снимок, риск перерасхода, ошибка на проде.
Расхождение охватов оформляется жёлтым.

## Структура письма

A Заголовок · B Статусы · C От вас · D Четыре показателя · E Сигналы дня ·
F Драйверы и детракторы · G Контроль эксперимента · H Автономное исполнение ·
I Радар возможностей · J Здоровье данных · K Контрольные точки · L Ссылки.

Объём 800–1000 видимых слов, первый экран — не более 250.

## Причинность

Причина изменения либо подтверждена перечисленными страницами и запросами, либо не
называется. Формулировки вида «поиск стал чаще показывать наши карточки» без списка
адресов запрещены; при отсутствии разложения выводится «причина изменения пока не
определена», а декоративный график не создаётся.

Разложение сравнивает одноимённые сущности соседних снимков. Окно источника при этом
сдвигается на сутки, поэтому рядом с числами указывается, что это изменение
накопленного окна, а не календарного дня.

## Контроль экспериментов

Показываются гипотеза, изменение, дата запуска, прошедшие дни, минимальная и текущая
экспозиция, состояние сниппета в выдаче, целевой показатель, текущий результат,
достоверность, дата следующей проверки и вердикт
(`too_early` / `observing` / `positive` / `negative` / `inconclusive`).

Выкат на сайте и обновление сниппета в выдаче — разные факты. Проверка живых страниц
подтверждает выкат; обновил ли поисковик сниппет, по своему же сайту установить
нельзя, поэтому это состояние публикуется как «не подтверждено».

Совместное внедрение (метаданные и FAQ одной правкой) оценивается как один
эксперимент: раздельная оценка на общих страницах невозможна по построению.

## Радар возможностей

`opportunity_score = commercial_intent × observable_demand × confidence ×
expected_impact / effort`, не более трёх позиций.

Наши показы по запросу — свидетельство нашей видимости, а не рыночный спрос.
Формулировка «рыночный спрос» разрешена только при наличии замера Вордстата.

## Вёрстка

Сетка показателей — fluid hybrid: карточка задана `max-width`, а не процентом,
поэтому одна колонка на узком экране получается без медиазапросов. Это существенно:
Gmail вырезает `<style>` из тела письма, и вёрстка, опирающаяся только на
медиазапросы, там разъезжается. Для Outlook добавлены ghost-таблицы в условных
комментариях. Журнал работ использует `table-layout:fixed`, иначе шесть колонок
распирают письмо до 420 px.

Проверка выполняется в браузере на 375 и 680 px в двух вариантах — со стилями и без
них: отсутствие горизонтальной прокрутки и минимальные размеры шрифтов.

## Графики

Не более трёх: мини-график показателя, вклад драйверов, таймлайн эксперимента.
Без заголовка внутри изображения, без легенды для одной серии, прямые подписи,
не более трёх цветов, белый фон, экспорт 2x, отображаемая высота до 220 px.
График не создаётся, если он лишь повторяет два числа.

## Веб-отчёт

Письмо не ведёт руководителя в исходники репозитория: репозиторий приватный, и
ссылка на файл в нём для читателя письма не открывается.

Адрес полного отчёта выбирается по порядку:

1. `PUBLIC_REPORT_BASE_URL` — собственный домен, страница дня `/daily/ГГГГ-ММ-ДД`;
2. `reports/seo/public/report-url.txt` — адрес опубликованной страницы;
3. ссылка на репозиторий — последний вариант, всегда с пометкой «техническая копия».

Страница `reports/seo/public/latest.html` перезаписывается каждым прогоном и живёт
по одному и тому же адресу: ссылка в письме не меняется день ото дня, поэтому
вчерашнее письмо не превращается в мёртвую ссылку. История по датам остаётся в
`reports/seo/public/daily/ГГГГ-ММ-ДД/index.html`.

Страница самодостаточна: графики встроены как data-URI, шрифты подключены с
Google Fonts с системным запасным набором. Темы светлая и тёмная объявлены
токенами на голом `:root`, отдельно для системной настройки и для явного выбора.

Проверка `report_link_target_exists` в UX lint не пропускает письмо, если ссылка
ведёт на файл, которого нет. Она добавлена после реального случая: генератор V4
перестал создавать `-appendix.md`, а ссылка на него осталась, и все остальные
25 проверок были зелёными.

## Условный вывод

Пустые и неизменившиеся разделы не выводятся: нет драйверов — блок скрыт, нет решения
руководителя — одна строка, задача не менялась — в журнал не попадает, экспозиции
недостаточно — «рано для вывода», CRM нет — приглушённое состояние без повторов.

## Проверки

`uxlint_v4.py` — 25 проверок письма как продукта, включая объём, первый экран,
число карточек и строк, мобильную вёрстку, типографику, повторы фактов
(один факт не более двух раз), необоснованную причинность и правила измерений.
`contentcheck.py` — 10 проверок содержания: атрибуция показателей, совпадение со
снимком, база сравнения у сигналов, подтверждение причины, соответствие вердикта
экспозиции, запрет подмены рыночного спроса.

# Wordstat Intelligence (с 20.08.2026)

Вордстат перестал быть источником частотности и стал системой обнаружения
коммерческого спроса и формирования приоритетов развития.

## Экономика: ограничивает квота, а не бюджет

Разрешённый месячный потолок — 5 500 ₽. Аудит показал, что при квоте
100 запросов в час израсходовать его невозможно.

| Квота | Вызовов в месяц | Максимальный расход | Бюджет ограничивает |
|---|---|---|---|
| 100/час | 72 000 | 1 656 ₽ | нет |
| 500/час | 360 000 | 8 280 ₽ | да |

Дефицитный ресурс — слоты квоты и время, поэтому система оптимизирует полезную
информацию на вызов, а не освоение рублей. План месяца — около 240 вызовов
(примерно 5 ₽), это 0,1 % потолка. Контроллер бюджета остаётся обязательным как
предохранитель и как учёт.

## Тарифы

Вынесены в `reports/seo/wordstat/config.json` с полями `method`, `price_per_1000`,
`currency`, `effective_date`. Цена вызова берётся по тарифу, действовавшему на дату
вызова: расчёт прошлого периода не должен меняться при смене прайса.

## Управление квотой: три правила, выведенные на практике

**Резерв слотов.** Плановое исследование берёт 70 из 100 часовых слотов.
Без резерва прогон по расписанию выбирал окно целиком, и срочная проверка ждала
следующего часа — на замере глубины выдачи 20.08.2026 это и произошло дважды.
Тридцать слотов остаются под валидацию решений и разовые замеры.

**Пуш кода не тратит квоту.** Триггер по изменению исходников запускает только
построение плана. Прежде каждая правка кода отнимала часовой слот у исследования.

**Адаптивное восстановление после отказа.** Прежнее поведение блокировало работу
на час от момента 429, хотя сервис мог освободить окно раньше — мы его даже
не спрашивали. Теперь ждём десять минут, делаем один пробный запрос, при успехе
снимаем блокировку, при повторном отказе удваиваем интервал до часа.

## Предохранители

| Порог | Что происходит |
|---|---|
| 5 000 ₽ | мягкая остановка: разрешены только вызовы для уже принятого решения |
| 5 500 ₽ | жёсткая остановка: платные вызовы запрещены |
| 400 ₽ в сутки | суточный потолок |
| 500 ₽ | отдельный потолок пилотного прогона |

Плюс остановка seed после трёх подряд пустых ответов, отказ от вызова при высокой
вероятности дублирования, кэш с раздельным временем жизни, запрет повторного
запроса до истечения TTL, экспоненциальная задержка при сбоях, соблюдение
10 запросов в секунду и часового окна.

## Semantic Universe

Постоянная база `reports/seo/wordstat/semantic-universe.jsonl`: фраза, нормальная
форма, морфологический ключ, seed, вендор, категория, кластер, подкластер, интент
двумя независимыми шкалами, частотность с историей по датам, регион, стоимость
получения, связь со страницей, индексация, позиции, показы, клики, CTR, доверие.
История не перезаписывается — по ней считается тренд.

## Покрытие спроса

Считается по частотности, а не по числу ключевых слов: тысяча низкочастотных фраз
не равна одной фразе с тысячей показов, и метрика, считающая строки, ведёт
к неверным приоритетам.

Шесть вложенных уровней: есть страница → страница в поиске → мы на первой
странице → есть переходы → конверсия измеряется → обращения подтверждены CRM.
Считается по вендорам, категориям и подкластерам.

Уровень «переходы» ограничен пересечением нашей семантики с выборкой топ-100
запросов Вебмастера: за её пределами переходы по конкретной фразе не наблюдаются.
Это ограничение указывается рядом с числом.

## Классы разрывов

| Класс | Состояние | Действие |
|---|---|---|
| GAP-A | спрос есть, страницы нет | новая страница или материал |
| GAP-B | страница есть, не индексируется | техническое SEO |
| GAP-C | индексируется, позиции слабые | оптимизация страницы |
| GAP-D | позиция хорошая, переходов мало | эксперимент со сниппетом |
| GAP-E | трафик есть, конверсий мало | предложение и форма |
| GAP-F | спрос большой, органика будет долгой | исследование платного канала |
| GAP-G | спрос растёт | ранняя возможность |
| GAP-H | спрос снижается | снизить приоритет |

## Уровни мониторинга

A — стратегические кластеры, динамика раз в неделю, география раз в квартал.
B — перспективные, динамика раз в месяц. C — длинный хвост, динамика только
по событию. География запрашивается только для уровня A и кандидатов в платный
канал: она в 2,5 раза дороже и меняется медленно.

## Модель возможностей

`Opportunity = NormalizedDemand × CommercialIntent × CoverageGap × TrendFactor
× Confidence / EstimatedEffort`

Компоненты хранятся и показываются отдельно. Итоговый балл упорядочивает список,
но основанием решения сам по себе не является.

## Что система делает сама и что запрещено

Разрешено без отдельного согласования: создавать исследовательские задачи,
обновлять радар возможностей и базу семантики, предлагать задачи SEO, брифы
на контент и исследования платного канала, менять приоритеты вендоров.

Запрещено: публиковать новые страницы, менять коммерческие условия и цены,
запускать рекламу, расходовать рекламный бюджет, удалять страницы.

## Спрос в ежедневном письме

Блок «Спрос и направления развития»: объём измеренного покупательского спроса,
три уровня покрытия и одно ближайшее направление с обоснованием. Технических
подробностей — вызовов, квоты, рублей, кэша — в письме нет; они живут в
приложении и в `reports/seo/wordstat/<дата>-demand-report.md`.
