# Аудит идеи «Growth Loop» (40 механик) и план внедрения

Дата: 30.08.2026. Статус: анализ, ничего на сайте и в workflows не изменено.
Основание: предложение о переходе от «SEO-maintenance» к автономной петле роста
(наблюдение → возможность → оценка денег → гипотеза → изменение → измерение →
решение → накопление опыта) и запрос руководителя оценить непротиворечивость,
полноту, полезность/безвредность, пересечения с существующим и способ контроля.

---

## 1. Общее заключение

**Заключение положительное, с тремя существенными оговорками.**

1. **Идея верна по направлению, но предпосылка критики устарела.** Оценка
   «40% обслуживание, 30% контент, 30% управление ростом» не соответствует
   текущему состоянию репозитория. Действующая система «BIZSoft Search &
   Growth Intelligence» — это уже петля роста, а не набор cron-задач:
   opportunity score считается в двух реализациях (`scripts/seo/opportunity.py`
   и `scripts/seo/wordstat/opportunity.py`), спрос Wordstat покрыт разведкой с
   классами разрывов GAP-A…H и готовыми промтами-заданиями (`playbook.py`),
   эксперименты ведутся с гипотезой, метрикой успеха и контрольной группой
   (`intelligence/seo-experiments.json`, живой пример — PAGES-EXP-001,
   PR #211), решения фиксируются в четырёх журналах, изменения раскладываются
   на драйверы (`drivers.py`), а ежедневное письмо V4 проходит гейты качества
   перед отправкой. Из 40 предложенных механик **~10 уже реализованы полностью
   и ~12 частично** (таблица в §3).

2. **Настоящая ценность предложения — три отсутствующих сенсора и один
   отсутствующий контур решений.** Полностью отсутствуют: каннибализация (№6),
   query-to-page mismatch (№5) — обе упираются в одно ограничение данных (пары
   «запрос × страница» из GSC не собираются); жизненный цикл страниц как
   явная сущность (№14, 15) и всё, что требует SERP-данных (№7, 8, 16, 17,
   18 — состава выдачи у системы нет вообще). Плюс нет еженедельного
   «письма решений» (№39, 40) — данные есть, а формата «5 действий недели +
   результаты прошлых гипотез» нет.

3. **Главный риск внедрения — не поломка сайта, а построение параллельной
   системы.** Если реализовывать 40 пунктов «с нуля», получится второй
   opportunity score, третий журнал экспериментов и второе письмо — и петля
   развалится на две конкурирующие. Поэтому правильная стратегия — не
   перестройка, а **достройка**: недостающие сенсоры добавляются в существующий
   конвейер `collect → snapshot → report`, недостающие механики — модулями в
   `scripts/seo/`, недостающие письма — поверх существующего SMTP-контура с
   теми же гейтами. Перестройка workflows не требуется вообще: все изменения
   аддитивны (новые шаги сбора, новые модули, новые письма), ни один
   действующий workflow не меняет поведения.

Ответ на вопрос «можно ли назвать это комбайном развития» — да, но точнее это
**конвейер с замкнутой петлёй**: сенсоры (сбор данных) → мозг (скоринг и
приоритизация) → исполнение (PR по гипотезе) → память (журналы) → контроль
(письма). Именно так система уже спроектирована; предложение добавляет ей
недостающие органы чувств и еженедельный «орган решений».

## Жёсткие ограничения, в которых обязан жить любой новый контур

1. Прямой сети у сессии нет: всё внешнее — только через GitHub Actions.
2. Production-workflow запускаются только с main; деплой — только push в main.
3. Товарные фиды закрыты (открыт только фид Директа, решение 29.08);
   любые действия с фидами — только по команде руководителя.
4. Квоты: Wordstat — потолок 5 500 ₽/мес; переобход Вебмастера — 150 URL/сутки;
   GSC URL Inspection — медленный (пауза 1 с/URL).
5. Методика запрещает: наивную CTR-модель «ожидаемый CTR для позиции»
  (дефект №3, `reporting-current-state.md`), называть цели Метрики «заявками»
  (NO_CRM), сравнение через границы измерения (`measurement-limits.json`).
6. Расписания GitHub Actions недетерминированы (дрейф часами, инцидент 27.08) —
   критичное по времени живёт в Routine или в cron сервера.
7. Анти-doorway: новые страницы — только по замеренному спросу, волнами,
   с контрольной группой и метрикой отключения (практика PAGES-EXP-001).
8. Growth-сессии запрещено коммитить в main, менять workflows/скрипты
   самостоятельно и сливать PR — всё через PR и решение руководителя.

## 4. Безвредность: почему достройка ничего не ломает

- **Сайт.** Этапы 0–4 не трогают `src/` вообще (кроме будущих контентных PR,
  которые и сегодня идут обычным циклом PR → verify → main → deploy). Новые
  модули живут в `scripts/seo/` и пишут только в ветку `seo-data`.
- **Workflows.** Ни один существующий workflow не переписывается. Новые шаги
  сбора добавляются в `seo-data-collect` аддитивно (новый JSON-файл рядом со
  старыми; существующие потребители его не читают, пока их не научат).
  Обязательный чек `verify` и ruleset `main-protection` не меняются.
- **Письма.** Ежедневное письмо V4 не меняет структуру (она зафиксирована в
  `reports/seo/README.md`); новое — отдельное еженедельное письмо со своими
  гейтами и своим маркером анти-дублей по образцу `last-mailed.txt`.
- **Данные.** Снимок schema 2.2.0 расширяется только новыми необязательными
  блоками (совместимость вниз); `quality.py` получает новые коды проверок, не
  меняя старых.
- **Откат.** Любой этап откатывается удалением модуля/шага — состояние
  прежней системы не затрагивается.

Единственные места, где возможен реальный вред, и как он исключается:
массовые правки контента/ссылок (только предложения-PR + Confidence Gate §5),
блокирующий CI-гейт (только advisory до решения руководителя), внешние
источники SERP (только по решению руководителя), автоудаление страниц и
disavow (запрещены политикой).

Confidence Gate (формализация в `experiments.py`/`actions.json`):
- ≥90% уверенности **и** обратимо **и** в разрешённой зоне (контент карточек,
  меты, добавление ссылок) → PR сразу, руководитель видит его в письме;
- 60–90% → предложение в еженедельном письме, исполнение после «да»;
- <60% → наблюдение, запись в реестр идей;
- всегда только через решение руководителя: canonical/удаление/массовая
  перелинковка/фиды/реклама/всё внешнее.

## 6. Контроль письмами (ответ на вопрос о «наборе писем»)

Группировка по логике принятия решений, а не по функционалу — три письма
плюс существующие событийные:

1. **Ежедневное — «Growth Intelligence» (есть, не меняем).** Оперативный
   статус: что происходит, RED-зона, ≤3 возможности. Отправитель, гейты,
   анти-дубли — как сейчас.
2. **Еженедельное — «Growth Committee» (новое, пн 09:30 МСК).** Ровно пять
   вопросов: что выросло; что упало; почему (только подтверждённые драйверы);
   3 сильнейшие возможности; ≤5 действий следующей недели (allocator).
   Плюс два обязательных блока: (а) **вердикты гипотез** — по каждому активному
   эксперименту: baseline → 7/14/28/56 дней → вердикт (`experiments.py`);
   (б) **подтверждение исполнения** — таблица loop-health: контур / последний
   успешный прогон / просрочка. Для каждого внедрённого изменения — эффект
   **накопленный с даты включения** и **дельта к прошлой неделе**, с честной
   пометкой границ измерения (наследуем `measurement-limits.json`).
3. **Ежемесячное — «Ревизия комбайна» (новое, 1-е число).** Подтверждение,
   что каждый контур реально работает регулярно: SLA-таблица всех механик,
   кумулятивный эффект принятых гипотез с начала применения, отклонённые
   и «не работает» (negative knowledge), расходы (Wordstat-ledger, Директ),
   план на месяц.

Механизм контроля исполнения (чтобы письма не были самоотчётом «на доверии»):
реестр `intelligence/loop-health.json` — по каждому контуру ожидаемая
каденция и факт последнего успешного прогона; заполняется самими прогонами;
просрочка = строка в RED-зоне ежедневного письма + issue с меткой `alert`
(существующий канал). Отсутствие еженедельного письма ловит тот же сторож,
что уже ловит отсутствие ежедневного (расширение `seo-report-email`).

## 7. Пошаговый план внедрения

Каждый этап — отдельные PR, `pnpm verify` зелёный, ничего из существующего не
переписывается; следующий этап начинается после приёмки предыдущего.
Трудоёмкость указана в календарных неделях работы сессий.

**Этап 0 — фундамент данных и учёта (неделя 1).**
1. PR: в `collect.py` добавить третий разрез GSC `query+page` (пары
   «запрос × страница», отдельный файл `gsc-pairs-<дата>.json`, пагинация,
   rowLimit до 1000) и поднять полноту разреза `page`. Существующие файлы и
   потребители не меняются.
2. PR: `intelligence/loop-health.json` + заполнение из Routine-прогона;
   строка в RED-зону письма при просрочке.
3. PR: консолидация opportunity — единый скоринг с явной полосой позиций
   4–20 (компоненты обеих реализаций сохраняются), витрина «money-запросы».
4. Политика (этот документ): запрет авто-disavow, автоудаления страниц,
   автоизменения canonical; Confidence Gate из §5.
5. PR (добавлено 30.08 по вопросу руководителя): проба SERP —
   `ops-serp-probe` + `scripts/seo/serp_probe.py`. Wordstat уже работает через
   Yandex Cloud Search API (`searchapi.api.cloud.yandex.net`, ключ
   `WORDSTAT_API_KEY`); веб-поиск `/v2/web/search` — тот же сервис. Проба
   делает один платный запрос и отвечает, работает ли существующий ключ для
   SERP; при успехе пункты №7/8/16/18 из этапа 5 переходят из «нужен внешний
   источник» в «источник уже подключён, нужен только бюджет на запросы».
   Приёмка этапа: пары собираются ≥3 дней подряд, loop-health виден в письме,
   результат пробы SERP — в issue #22.

**Этап 1 — недостающие детекторы на новых данных (неделя 2).**
5. PR: `mismatch.py` — запросы, стабильно ведущие «не туда» (интент страницы
   ≠ интент запроса), с оценкой потерянных показов.
6. PR: `cannibalization.py` — детектор нестабильности «несколько URL по
   одному запросу со сменой лидера», без автодействий: только карточка
