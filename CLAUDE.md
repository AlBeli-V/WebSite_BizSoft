# Правила проекта biz-soft.pro

## Регулярное правило: новые страницы → sitemap → индексация

После добавления новых страниц сайта (лендинги в разделе «Производители»
`/vendors/*` и продуктовые страницы `/product/*`) обязательно:

1. **Sitemap.** Проверить, что новые URL попали в `/sitemap.xml`.
   Sitemap динамический (SSR из Directus, `src/pages/sitemap.xml.ts`):
   товары и вендоры из БД подхватываются автоматически, но новые
   **статические/bespoke-страницы** нужно вручную добавить в `STATIC_ROUTES`.
   Товары с `noindex` и sku из `productNoindex()` (плагины JB-PLG-*, личные
   лицензии *-IND) в sitemap не попадают — их не индексируем.
2. **Принудительная индексация.** Запросить переобход новых URL в
   Яндекс.Вебмастере через workflow `ops-yandex-recrawl` (вход `urls` —
   список URL через запятую; квота 150 URL/сутки). Результат — комментарий
   в журнал-issue #22.

## Регулярное правило: новые вендоры/товары → микроразметка

Установлено руководителем 29.08.2026. При добавлении вендоров и товаров
микроразметка Schema.org обязательна и делается ТОЛЬКО штатным слоем
(`src/lib/seo.ts`, компоненты `Breadcrumbs`/`FAQ`/`JsonLd`, microdata
карточки товара) — руками в шаблонах ничего не размечать. Один тип — один
раз на страницу (BreadcrumbList — только компонент Breadcrumbs, FAQPage —
только компонент FAQ). «Цена по запросу» — без Product/Offer вовсе;
фиктивные цены/рейтинги запрещены. Цена в разметке — из `effectivePrice()`.
Приёмка: `pnpm verify` (смоук сверяет JSON-LD ↔ microdata ↔ видимую цену).
Подробности: `docs/seo/structured-data-audit.md`,
`docs/vendors-expansion-prompt.md` (раздел 11).

## Регулярное правило: новые вендоры/товары/страницы → WebMCP

Внедрено 30.08.2026. На сайте есть WebMCP-слой для AI-агентов
(`src/webmcp/`, эндпоинт `/api/agent/*`, рубильник `PUBLIC_WEBMCP=0`;
архитектура — `docs/webmcp/architecture.md`). Правила:

- Новые товары и вендоры в Directus видны generic-инструментам
  (`search_products`, `get_product`, `get_vendor`, `list_vendor_products`,
  `list_vendors`) автоматически — WebMCP-код под них НЕ пишется.
  Приёмка — чеклист в `docs/vendors-expansion-prompt.md` (раздел 11а).
- Запрещены product-specific инструменты (get_claude и т.п.) и любая
  параллельная база товаров/цен для агентов: единственный источник —
  Directus → `effectivePrice()` → адаптеры `src/webmcp/adapters.ts`.
- Write-инструменты (заявки, КП, заказы) через WebMCP ЗАПРЕЩЕНЫ без
  отдельной команды руководителя и регламента `docs/webmcp/security.md`.
- Информационные и служебные страницы инструментов не получают;
  для новых форм Declarative WebMCP пока не применяется.
- Вызовы инструментов не должны отправлять цели Метрики/GA4 и создавать
  pageviews; `/api/agent/*` — noindex и вне sitemap (смоук стережёт).
- Изменил слой — прогнать `pnpm verify` и `pnpm test:webmcp-browser`.

## Регулярное правило: уникальные title и description

Установлено руководителем 01.09.2026 после находки Вебмастера (дубль
meta_title у `/product/deposit-unl-month` и `/product/deposit-unl-year`).

Заголовок карточки — это `meta_title` из Directus (`src/pages/product/[slug].astro`,
бренд добавляется в `SeoHead.astro` только если его нет в строке). Поэтому
у тарифов одного продукта, различающихся периодом или объёмом, `meta_title`
обязан различаться: период («помесячно», «на год»), объём или редакция —
в самом заголовке, длина до 60 символов. То же для `meta_description`
(до 160). Одинаковые title Яндекс считает дублями и снимает страницы с
индексации.

- Правка мета-тегов в проде — только через `data/seo/product-descriptions.json`
  + workflow `ops-apply-descriptions` (сначала `apply=false` — план, потом
  `apply=true`): тексты проходят ревью в PR, воркфлоу переносит согласованное
  в БД. Руками в Directus и мимо репозитория мету не править.
- После правки — переобход изменённых URL через `ops-yandex-recrawl`.
- Проверки автоматические, руками ничего не сверяется:
  - `pnpm test` — `tests/catalog-uniqueness.test.ts`: новая группа карточек
    с одинаковым `name` ИЛИ одинаковым `short_description` в
    `scripts/catalog/*.json` роняет сборку (известный долг зафиксирован в
    `data/seo/known-duplicate-names.json` и не должен расти); там же
    проверяются партии текстов — уникальность `meta_title`,
    `meta_description` и `short_description`, длины 60/160, отсутствие
    пустых значений;
  - `pnpm smoke` — уникальные `<title>` у страниц из sitemap, мета из
    Directus доезжает до разметки, бренд в title не задваивается;
  - `ops-content-audit` — раз в неделю (понедельник, 10:00 МСК) и по
    запросу: дубли фактического заголовка, `meta_description`, названия
    товара и `short_description` по прод-каталогу, отчёт в issue #22
    (`full=true` — весь перечень групп, а не первая десятка).
- Общий на линейку `short_description` — тот же дубль, только в лиде
  карточки, в `Product.description` разметки и в фидах. Разводится штатно:
  `node scripts/seo/dedupe-descriptions.mjs <файл-со-слагами> --write
  --sync-catalog` — различитель берётся из названия товара, тексты ложатся
  в партию и в пакет каталога (иначе следующий импорт вернёт дубль).
- Заведение новых кластеров страниц (вендоры, товары, решения, сравнения):
  различитель — объём, модуль, период, редакция, модель лицензии — обязан
  быть в самом `name`, а не только в слаге или цене; `short_description`
  у соседних позиций тоже должен различаться. Подробности —
  `docs/vendors-expansion-prompt.md`, раздел 11.
- Коррекция штатная: пустую мету заполняет `ops-fix-meta` (заголовок из
  названия, описание из краткого описания), уникальные тексты —
  `ops-apply-descriptions`.

## Каталог и привязки

- Directus — единственный источник товаров; вендор товара — точное значение
  поля `vendor` (сверять с `src/data/vendors.ts`, поле `vendor` записи).
- На bespoke-страницах (`vendors/openai|figma|zoom|jetbrains.astro`) НЕ
  фильтровать товары по префиксу sku: часть товаров живёт под
  «интеграционными» sku (INT-AI-CHATGPT, INT-DESIGN-FIGMA). Ключи меты и
  порядка карточек — slug ИЛИ sku.
- Живую выгрузку каталога (vendor/name/slug/sku/price) даёт workflow
  `ops-export-products` (комментарий в issue #22).

## Товарные фиды: открытие только по команде руководителя

Установлено руководителем 29.08.2026. Действует во всех ветках и сессиях.

Товарные фиды (`/yandex-products.yml`, `/yandex-business.xml`,
`/yandex-direct.yml`, `/yandex-market.yml`, любые будущие) держатся
готовыми, но ЗАКРЫТЫМИ: по умолчанию отдают 404 (`X-Feed-Status: disabled`).
Решения о публикации принимает только руководитель. Без его явной команды
нельзя: включать `YANDEX_FEEDS_ENABLED` на проде, добавлять фиды в кабинеты
Яндекса, отправлять обращения в поддержку площадок, загружать YML куда-либо.
Подробности — `docs/yandex-feeds.md`.

## Доступ к прод-серверу

Прямой сетевой доступ сессии к сайту закрыт. Все проверки и операции — через
ops-* workflows (GitHub Actions → SSH), результаты — в issue #22. Деплой —
только через deploy.yml при пуше в main.

## Часовой пояс: письма и расписания — по Москве

Установлено руководителем 21.08.2026. Действует во всех ветках и сессиях.

Любое время, названное в задаче без указания пояса («в 10:00», «утром»,
«к вечеру»), означает **московское время (UTC+3, без перехода на летнее)**.
Это касается писем на почту, отчётов, напоминаний и расписаний.

- Планируя запуск, переводить в UTC вычитанием трёх часов: 10:00 МСК = 07:00 UTC.
- В cron GitHub Actions и в Routines время задаётся в UTC — писать уже
  пересчитанное значение и оставлять рядом комментарий с московским.
- Бишкек (UTC+6) по умолчанию НЕ использовать, даже если так было заведено
  в ранее созданных расписаниях: новые и изменяемые — по Москве.

## Язык общения: только русский

Установлено руководителем 21.08.2026. Действует во всех ветках и сессиях.

Весь текст, который видит руководитель, — на русском языке: ответы в чате,
**рассуждения по ходу исполнения**, сообщения коммитов, заголовки и описания
PR, комментарии в коде, тексты писем и отчётов.

Английский допустим только там, где он является частью технической записи и
переводу не подлежит: имена файлов, идентификаторы, ключи API, команды,
названия полей и коллекций, цитаты из ответов внешних сервисов.

## Production-workflow: запуск только с main

Установлено 23.08.2026 после инцидент-аудита (PR #135, #136, #137).

Ручной запуск (workflow_dispatch) любого workflow, который деплоит сайт,
ходит по SSH на прод-сервер, пишет в Directus, меняет цели аналитики или
шлёт письма, выполняется **только с ветки main** — в поле «Use workflow
from» всегда выбирать main. Запуск с другой ветки упадёт на первом шаге
`Guard - only default branch`; это защита, а не поломка — не обходить её
правкой workflow-файла в рабочей ветке.

Ветки назначения в ops-fetch-assets и ops-me-crawl (поле `branch`) —
только рабочие ветки, main указывать нельзя: шаг с force-push откажется
писать в main.
