# Правила проекта biz-soft.pro

## Регулярное правило: новые страницы → sitemap → индексация

После добавления новых страниц сайта (лендинги в разделе «Производители»
`/vendors/*` и продуктовые страницы `/product/*`) обязательно:

1. **Sitemap.** Проверить, что новые URL попали в `/sitemap.xml`.
   Sitemap динамический (SSR из Directus, `src/pages/sitemap.xml.ts`):
   товары и вендоры из БД подхватываются автоматически, но новые
   **статические/bespoke-страницы** нужно вручную добавить в `STATIC_ROUTES`.
   Товары с `noindex` и sku из `productNoindex()` (плагины JB-PLG-*, личные
   лицензии *-IND) в sitemap не попадают — их не индексируем.
2. **Принудительная индексация.** Запросить переобход новых URL в
   Яндекс.Вебмастере через workflow `ops-yandex-recrawl` (вход `urls` —
   список URL через запятую; квота 150 URL/сутки). Результат — комментарий
   в журнал-issue #22.

## Регулярное правило: новые вендоры/товары → микроразметка

Установлено руководителем 29.08.2026. При добавлении вендоров и товаров
микроразметка Schema.org обязательна и делается ТОЛЬКО штатным слоем
(`src/lib/seo.ts`, компоненты `Breadcrumbs`/`FAQ`/`JsonLd`, microdata
карточки товара) — руками в шаблонах ничего не размечать. Один тип — один
раз на страницу (BreadcrumbList — только компонент Breadcrumbs, FAQPage —
только компонент FAQ). «Цена по запросу» — без Product/Offer вовсе;
фиктивные цены/рейтинги запрещены. Цена в разметке — из `effectivePrice()`.
Приёмка: `pnpm verify` (смоук сверяет JSON-LD ↔ microdata ↔ видимую цену).
Подробности: `docs/seo/structured-data-audit.md`,
`docs/vendors-expansion-prompt.md` (раздел 11).

## Регулярное правило: новые вендоры/товары/страницы → WebMCP

Внедрено 30.08.2026. На сайте есть WebMCP-слой для AI-агентов
(`src/webmcp/`, эндпоинт `/api/agent/*`, рубильник `PUBLIC_WEBMCP=0`;
архитектура — `docs/webmcp/architecture.md`). Правила:

- Новые товары и вендоры в Directus видны generic-инструментам
  (`search_products`, `get_product`, `get_vendor`, `list_vendor_products`,
  `list_vendors`) автоматически — WebMCP-код под них НЕ пишется.
  Приёмка — чеклист в `docs/vendors-expansion-prompt.md` (раздел 11а).
- Запрещены product-specific инструменты (get_claude и т.п.) и любая
  параллельная база товаров/цен для агентов: единственный источник —
  Directus → `effectivePrice()` → адаптеры `src/webmcp/adapters.ts`.
- Write-инструменты (заявки, КП, заказы) через WebMCP ЗАПРЕЩЕНЫ без
  отдельной команды руководителя и регламента `docs/webmcp/security.md`.
- Информационные и служебные страницы инструментов не получают;
  для новых форм Declarative WebMCP пока не применяется.
- Вызовы инструментов не должны отправлять цели Метрики/GA4 и создавать
  pageviews; `/api/agent/*` — noindex и вне sitemap (смоук стережёт).
- Изменил слой — прогнать `pnpm verify` и `pnpm test:webmcp-browser`.

## Регулярное правило: уникальные title и description

Установлено руководителем 01.09.2026 после находки Вебмастера (дубль
meta_title у `/product/deposit-unl-month` и `/product/deposit-unl-year`).

Заголовок карточки — это `meta_title` из Directus (`src/pages/product/[slug].astro`,
бренд добавляется в `SeoHead.astro` только если его нет в строке). Поэтому
у тарифов одного продукта, различающихся периодом или объёмом, `meta_title`
обязан различаться: период («помесячно», «на год»), объём или редакция —
в самом заголовке, длина до 60 символов. То же для `meta_description`
(до 160). Одинаковые title Яндекс считает дублями и снимает страницы с
индексации.

- Правка мета-тегов в проде — только через `data/seo/product-descriptions.json`
  + workflow `ops-apply-descriptions` (сначала `apply=false` — план, потом
  `apply=true`): тексты проходят ревью в PR, воркфлоу переносит согласованное
  в БД. Руками в Directus и мимо репозитория мету не править.
- После правки — переобход изменённых URL через `ops-yandex-recrawl`.
- Проверки автоматические, руками ничего не сверяется:
  - `pnpm test` — `tests/catalog-uniqueness.test.ts`: новая группа карточек
    с одинаковым `name` ИЛИ одинаковым `short_description` в
    `scripts/catalog/*.json` роняет сборку (известный долг зафиксирован в
    `data/seo/known-duplicate-names.json` и не должен расти); там же
    проверяются партии текстов — уникальность `meta_title`,
    `meta_description` и `short_description`, длины 60/160, отсутствие
    пустых значений;
  - `pnpm smoke` — уникальные `<title>` у страниц из sitemap, мета из
    Directus доезжает до разметки, бренд в title не задваивается;
  - `ops-content-audit` — раз в неделю (понедельник, 10:00 МСК) и по
    запросу: дубли фактического заголовка, `meta_description`, названия
    товара и `short_description` по прод-каталогу, отчёт в issue #22
    (`full=true` — весь перечень групп, а не первая десятка).
- Общий на линейку `short_description` — тот же дубль, только в лиде
  карточки, в `Product.description` разметки и в фидах. Разводится штатно:
  `node scripts/seo/dedupe-descriptions.mjs <файл-со-слагами> --write
  --sync-catalog` — различитель берётся из названия товара, тексты ложатся
  в партию и в пакет каталога (иначе следующий импорт вернёт дубль).
- Заведение новых кластеров страниц (вендоры, товары, решения, сравнения):
  различитель — объём, модуль, период, редакция, модель лицензии — обязан
  быть в самом `name`, а не только в слаге или цене; `short_description`
  у соседних позиций тоже должен различаться. Подробности —
  `docs/vendors-expansion-prompt.md`, раздел 11.
- Коррекция штатная: пустую мету заполняет `ops-fix-meta` (заголовок из
  названия, описание из краткого описания), уникальные тексты —
  `ops-apply-descriptions`.

## Регулярное правило: запросы на действия — кнопками с визой

Установлено руководителем 02.09.2026, в тот же день подтверждено и
расширено. Любой запрос решения (мерж, выбор варианта, вердикт
эксперимента, действия по рекламе, приоритеты, чистка веток, публикация
материалов, включение фидов) выдаётся кнопками выбора, а не текстом со
списком вариантов.

- Каждый вариант несёт визу исполнителя — «РЕКОМЕНДУЮ» или
  «НЕ РЕКОМЕНДУЮ» — и обоснование из трёх частей: чем подтверждается
  (факты, прогоны, цифры), что даёт, чем рискуем.
- Рекомендуемый вариант ставится первым, виза — в описании варианта,
  а не в тексте под кнопками.
- Вариантов 2–4, взаимоисключающих; отдельную кнопку «Другое» не
  добавляем — свой ответ руководитель может вписать всегда.
- Кнопки выдаются в тот момент, когда решение действительно нужно:
  всё, что не зависит от ответа, исполнитель доделывает сам и приносит
  готовым, а не откладывает до визы.
- Правило действует во всех ветках и сессиях — рабочих, ежедневных
  прогонах, разборах инцидентов, ответах по расписанию и в фоне —
  и не зависит от того, есть ли этот раздел в CLAUDE.md рабочей ветки:
  ветки, ответвлённые до 02.09.2026, подчиняются ему так же.
- Текстом без кнопок остаются только доклады и уведомления, где решения
  руководителя не требуется.

## SERP: один сбор — все потребители

Установлено 03.09.2026 с подключением xmlriver (российская выдача Google).
Действует во всех ветках и сессиях. Подробности —
`docs/competitive/decisions-2026-09-03.md`.

- Выдачу собирает только workflow `seo-serp-watch` (Яндекс — Search API,
  ежедневно; Google RU — xmlriver, еженедельно) в `reports/seo/serp`
  ветки `seo-data`. Потребители — веб-отчёт Growth Intelligence
  (`scripts/seo/serp_analysis.py`) и конкурентная разведка
  (`competitive-intelligence/discovery/serp_source.py`) — читают готовый
  срез. Прямые вызовы xmlriver/DataForSEO из контуров-потребителей и любые
  параллельные сборщики SERP запрещены.
- Google RU — серия `google_ru` (местоположение 2643, глубина 10 позиций:
  параметр page xmlriver игнорирует). Прокси-гео через
  DataForSEO снято; автоматического запасного источника нет: без свежего
  среза (8 дней) показывается «нет данных», а не старые позиции и не ноль.
  Позиции Яндекса и Google как равноточные не сравниваются — сравнивается
  присутствие в топе.
- Повторный запуск сборщика за ту же дату докачивает только недостающее
  (`--refetch` — полный пересбор). Расход — по журналам
  `ledger/google-<месяц>.jsonl` (вызовы) и `ledger/google-runs.jsonl`
  (прогоны). Потолки и расписание меняются только через PR в
  `data/seo/xmlriver.json`.

## Каталог и привязки

- Directus — единственный источник товаров; вендор товара — точное значение
  поля `vendor` (сверять с `src/data/vendors.ts`, поле `vendor` записи).
- На bespoke-страницах (`vendors/openai|figma|zoom|jetbrains.astro`) НЕ
  фильтровать товары по префиксу sku: часть товаров живёт под
  «интеграционными» sku (INT-AI-CHATGPT, INT-DESIGN-FIGMA). Ключи меты и
  порядка карточек — slug ИЛИ sku.
- Живую выгрузку каталога (vendor/name/slug/sku/price) даёт workflow
  `ops-export-products` (комментарий в issue #22).
- `lastmod` товара в sitemap — поле `content_updated_at` (дата содержательного
  изменения), а не `date_updated`: последний Directus сдвигает при любом
  PATCH, и ежедневная переоценка по курсу ЦБ ставила всему каталогу одну
  дату (разбор 03.09.2026). Штамп ставит слой `src/lib/directus.ts`
  (`withContentStamp`: цены, наценки, закупка и `sort` — нейтральны, всё
  остальное — содержательно) и workflow мета-правок; переоценка и
  `ops-annual-reprice` его не трогают. Без штампа `lastmod` у товара не
  отдаётся. Поле заводит `ops-directus-schema` (schema-only).
- Одна и та же позиция, заведённая дважды (разные sku и слаги), склеивается
  штатно: `ops-merge-product` (вход `keep`/`drop`, сначала `apply=false` —
  план). Остающаяся карточка получает слаг снятой в `old_slugs` — страница
  начинает отдавать 301 (`src/pages/product/[slug].astro`), снятая уходит с
  витрины сменой статуса на `draft` и в базе сохраняется. Какую из пары
  оставить — решение руководителя; удалять карточки нельзя.

## Регулярное правило: решение по кандидату — в машинный реестр

Установлено 02.09.2026 после повторной рекомендации NordVPN и Ansys, уже
отклонённых руководителем 29.08.2026.

Отказ или одобрение вендора-кандидата действует, только если записано в
машинный реестр решений. Запись в отчёт, в markdown или в переписку системой
не читается, и кандидат вернётся в рекомендации на следующем прогоне.

- Реестры парные: `reports/seo/wordstat/decisions.json` (разделы `rejected` и
  `approved`) и `reports/seo/intelligence/vendor-decisions.json`. Оба читают и
  исследование (`scripts/seo/wordstat/audience.py`), и письмо с веб-отчётом
  (`scripts/seo/report_v4.py`) — запись в любой закрывает вопрос, но заводим в
  оба, чтобы формат каждого оставался полным.
- Живут в ветке-хранилище `seo-data`, синхронизация `scripts/seo/data_sync.sh`
  (`pull` перед правкой, `push` после).
- У записи обязательны `brand`, `decided_on`, `reason`, `by` — иначе через
  месяц не восстановить, чьё это решение и почему.
- `reports/vendors/rejected-products.md` — пояснение для человека, не источник
  для системы; его обновляем следом, а не вместо.

## Часовой пояс: письма и расписания — по Москве

Установлено руководителем 21.08.2026. Действует во всех ветках и сессиях.

Любое время, названное в задаче без указания пояса («в 10:00», «утром»,
«к вечеру»), означает **московское время (UTC+3, без перехода на летнее)**.
Это касается писем на почту, отчётов, напоминаний и расписаний.

- Планируя запуск, переводить в UTC вычитанием трёх часов: 10:00 МСК = 07:00 UTC.
- В cron GitHub Actions и в Routines время задаётся в UTC — писать уже
  пересчитанное значение и оставлять рядом комментарий с московским.
- Бишкек (UTC+6) по умолчанию НЕ использовать, даже если так было заведено
  в ранее созданных расписаниях: новые и изменяемые — по Москве.

## Routine для операционных прогонов: только с привязкой к сессии

Установлено 02.09.2026 после разбора: страховочные Routine («Добивка ночного
SERP», «Добивка Wordstat», «Сторож письма конкурентной разведки»,
«BIZSoft Конкурентная разведка», «Growth Committee») с 01.09 не работали ни
разу и слали руководителю ложные тревоги «нет доступа к репозиторию и
GitHub MCP».

Причина в механизме, а не в коде. Routine, созданная инструментом
`create_trigger` в режиме «новая сессия при каждом срабатывании»
(`create_new_session_on_fire`), порождает сессию **без рабочей копии
репозитория и без connector-инструментов** (`mcp__github__*`): у такой
сессии пустой `session_context` и теги `config:routine-lineage-none`,
`routine:agent-minted`. Параметра для указания репозитория у
`create_trigger` нет вовсе, и наследование от вызывающей сессии не
происходит — проверено экспериментом. В такой сессии не работают ни
`git fetch origin seo-data`, ни `actions_run_trigger`.

Правило: **Routine, которой нужны репозиторий, ветки данных или запуск
workflow, заводится только с `persistent_session_id`** — привязкой к
постоянной сессии-исполнителю, созданной через `create_session` с
`source_url` (репозиторий подключается, GitHub MCP доступен). Режим
«новая сессия при каждом срабатывании» годится только для заданий, которым
не нужен ни репозиторий, ни GitHub. Альтернатива — завести расписание
через веб-интерфейс claude.ai/code, где репозиторий выбирается явно.

- Сессии-исполнители помечены тегами `ops-routine` и `ops-<контур>`;
  ежедневная проверка — модель Sonnet, аналитический прогон с отчётом —
  Opus.
- Контекст постоянной сессии растёт с каждым прогоном: раз в один-два
  месяца исполнителя пересоздавать (новая сессия с `source_url`, у Routine
  сменить `persistent_session_id`), старого архивировать.

### Приёмка привязки: проверять сессию, а не флаг Routine

Дополнено 03.09.2026 после второго инцидента. Ночью не отработала «Добивка
ночного SERP»: исполнитель доложил, что рабочей копии нет и GitHub MCP не
грузится. При этом все 14 Routine формально проходили прежнюю приёмку —
`persist_session: true` и непустой `persistent_session_id` стояли у всех.
Прежней приёмки НЕДОСТАТОЧНО, флаг врёт по двум причинам, и обе встретились
в одном разборе:

1. **Привязка в пустоту.** `persistent_session_id` указывает на сессию,
   которой не существует: `get_session` отвечает «the requested resource
   was not found». Так были сломаны «Добивка Wordstat», «Сторож письма
   конкурентной разведки» и «Проверка операционных Routine».
2. **Сессию выпустил планировщик.** Если у Routine к первому срабатыванию
   нет годной привязки, сервер сам заводит сессию и записывает её в
   `persistent_session_id` — задним числом карточка Routine выглядит
   правильной. Такая сессия создана без репозитория: `origin` —
   `scheduled_trigger`, теги `config:routine-lineage-none` и
   `routine:agent-minted`, в `session_context` нет `sources`. Так была
   сломана «Добивка ночного SERP».

**Приёмка идёт по карточке самой сессии-исполнителя, а не по карточке
Routine.** Заведя или пересоздав Routine, вызвать `get_session` по её
`persistent_session_id` и убедиться, что выполнено всё:

- вызов вернул сессию (ответ «not found» = привязка указывает в пустоту);
- в `session_context.sources` есть `git_repository` нужного репозитория;
- в `tags` нет `config:routine-lineage-none` и `routine:agent-minted`;
- `origin` — `claude_code_mcp_seed` или `web_claude_ai`, но не
  `scheduled_trigger` и не `force_run_trigger`.

Ни привязку, ни промпт привязанной Routine `update_trigger` сменить не
даёт — отказывает с «editing the prompt of a routine whose fires deliver
into a session that is not your own is not available via this tool»;
правится только пересозданием. Порядок заведения исполнителя целиком:

1. `create_session` с `source_url` https://github.com/AlBeli-V/WebSite_BizSoft,
   тегами `ops-routine` + контурный тег и подготовительным прогоном —
   прогон заодно проверяет рабочую копию, ветку данных и GitHub MCP.
2. `get_session` по новой сессии — приёмка из четырёх пунктов выше.
3. `create_trigger` с `persistent_session_id` этой сессии.
4. `delete_trigger` старой Routine, старую сессию архивировать.
5. Приёмка — по первому срабатыванию ПО РАСПИСАНИЮ: `get_session` по
   исполнителю, у него обязан сдвинуться `updated_at`. Пока этого не
   произошло, Routine считается непринятой.

**`fire_trigger` для приёмки не годится** (установлено 03.09.2026
экспериментом). Ручной запуск игнорирует `persistent_session_id`: он
заводит отдельную сессию с `origin: force_run_trigger`, тегами
`config:routine-lineage-none` и `routine:agent-minted` и пустыми
`sources` — то есть ровно ту калеку, от которой мы уходим. Прогон уходит
в неё, исполнитель не шевелится, и «контрольный прогон» проверяет не то.
Отсюда же признак обойдённой привязки в ежедневном стороже: `last_fired_at`
у Routine свежий, а `updated_at` у сессии-исполнителя старый.

### Контур чинится сам: реестр вместо тревог

Установлено руководителем 03.09.2026: операционные прогоны работают на
автомате — без обращений к руководителю и без уведомлений. Ни одна Routine
больше не пишет «сломана привязка, чинить должен человек».

Источник истины — `ops/routines/registry.json` в main: какие Routine должны
существовать, с каким расписанием, моделью, тегами исполнителя и файлом
промпта из `ops/routines/prompts/`. Живое состояние приводится к реестру, а
не наоборот.

- Ежедневный сторож «Проверка привязок операционных Routine» (10:00 МСК)
  читает реестр, сверяет каждую запись по карточке сессии-исполнителя и
  **сам** пересоздаёт сломанные контуры: заводит сессию с `source_url`,
  проверяет её `sources`, создаёт Routine заново, удаляет старую.
- Сам себя сторож починить не может — сломанная Routine не запускается.
  За ним присматривает ночная «Добивка ночного SERP» (02:45 МСК): раздел
  «Взаимный присмотр за сторожем» в её промпте восстанавливает сторожа по
  тому же реестру.
- Записи с `"autoheal": false` (сейчас — Growth Intelligence) автоматически
  не пересоздаются: они привязаны к рабочим сессиям с накопленным
  контекстом, его потеря дороже простоя.
- Тишина. Руководителю уходят только деловые результаты — письма
  конкурентной разведки и Growth Committee через почтовые workflow. Всё
  инфраструктурное идёт одной записью в журнал-issue #22, и только когда
  что-то делалось. Метка `alert` — для контуров с `autoheal: false` и для
  починки, не удавшейся после трёх попыток.
- Промпты правятся в `ops/routines/prompts/` через PR, а не вслепую в
  интерфейсе. В силу правка вступает, когда сторож пересоздаёт контур:
  `update_trigger` промпт привязанной Routine менять отказывается.
- Приёмка сборкой: `pnpm test` прогоняет `tests/ops-routines-registry.test.ts`
  — реестр разбирается, у каждой автоматически чинимой записи есть непустой
  промпт, cron корректен, имена уникальны, у сторожа есть присматривающий.

Подробности — `ops/routines/README.md`. Прежняя проверка была ежемесячной,
смотрела только на флаг и требовала человека — она пропустила обе поломки.
