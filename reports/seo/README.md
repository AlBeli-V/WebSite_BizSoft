# BIZSoft Growth Intelligence — Executive Command Center (v4)

Ежедневная система отчётности по поисковой видимости biz-soft.pro. Два уровня:
**executive email** для руководителя и **веб-отчёт** (полные таблицы, разделы
отсортированы по критичности, оглавление). Письмо уходит в 09:00 МСК (UTC+3,
правило проекта) на avbelyaev@biz-soft.pro.

Методика: `docs/seo/reporting-methodology.md` · переход с v1: `docs/seo/reporting-v2-migration.md` ·
аудит прежнего pipeline: `docs/seo/reporting-current-state.md`.

## Loop-health: контроль, что конвейер реально работает

`scripts/seo/loop_health.py` (вызывается из `report_v4.py`) сверяет каждый
контур с его артефактом: сбор данных, пары GSC, Вордстат, снимок, качество,
письмо, отправка, статистика Директа. Просрочка — красная строка в блоке
«Здоровье данных» письма и таблица в веб-отчёте («Работа конвейера»).
Расписаниям Actions система не верит на слово: контур считается отработавшим
только по датированному артефакту (инцидент 27.08.2026 — планировщик GitHub
молчал шесть часов).

## Правила, обязательные к соблюдению

1. Цифры только из snapshot — вручную в текст письма значения не вписываются.
2. Нет данных → «нет данных», не ноль.
3. ФАКТ / ИНТЕРПРЕТАЦИЯ / ГИПОТЕЗА / РЕШЕНИЕ / РИСК ДАННЫХ — каждое утверждение маркировано.
4. Критическая ошибка качества данных блокирует зависящие выводы и «зелёный» статус.
5. Показы — видимость сайта, не рыночный спрос. Цели Метрики — события, не заявки и не лиды;
   заявки берутся только из воронки сайта (`leads-<дата>.json`), и канал каждой называется
   с основанием — «Метрика» или «метка браузера» (`docs/marketing/lead-attribution.md`).
6. «В топ-10» — строго средняя позиция ≤ 10; запросы и страницы не смешиваются.
7. Письмо: 450–650 видимых слов, ≤4 показателя, ≤3 изменения, ≤3 действия, ≤2 изображения (PNG, не SVG),
   без технических терминов и локальных путей; ссылки — кликабельные URL.
7б. Зоны: GREEN/YELLOW выполняют агенты (владелец из карты ролей `intelligence/actions.json`),
   RED — решение руководителя. Нет RED — блок «От вас» показывает «действий не требуется».
7в. Нулевая дельта — формулировка «не изменилось», слова роста и падения запрещены.
7г. Совместное внедрение оценивается как один эксперимент; воронка не показывается до завершения сверки.
8. Технические задачи — тикетами в `reports/seo/tasks/`, исполнитель сам создаёт ветку и PR.
9. Изменения сайта — через PR. Правки карточек по данным спроса разрешены агенту
   решением руководителя от 19.08.2026 (см. `docs/seo/reporting-methodology.md`).
10. Спрос Вордстата — показы в поиске Яндекса, не покупки. Общая частотность бренда
   не выдаётся за покупательский спрос: решение принимается по коммерческим фразам.
11. Бюджет обращений к Вордстату — 10 000 запросов в месяц (согласован 19.08.2026);
   фактический расход фиксируется в `semantics/core-<дата>.json`.
12. Спрос не является показателем дня: в письме он присутствует строкой свежести,
   обоснованием действий, записью в день нового замера и блоком «Спрос и направления
   развития». Полные таблицы — в веб-отчёте и `reports/seo/wordstat/`.
13. Ни один платный вызов Вордстата не выполняется без записи в журнал бюджета
   с причиной и стоимостью. Жёсткий потолок 5 500 ₽ в месяц, мягкая остановка 5 000 ₽.
14. Покрытие спроса считается по частотности, а не по числу ключевых слов.

## Структура executive email (порядок фиксирован)

A. Заголовок и дата · B. Итог дня (≤2 предложений, составной статус Яндекс/Google/общий) ·
C. «От вас» (либо «действий не требуется», либо одно RED-решение) · D. Четыре показателя ·
карта измерения (PNG) · E. «Система уже делает» (≤3 действия с ролью, статусом и сроком) ·
F. «Что изменилось» (≤3 события) + график Google неделя к неделе (PNG) ·
G. Один блокирующий риск и ≤2 предупреждения · H. Следующая проверка ·
I. Кнопки «Полный отчёт» и «Журнал работ».

Всё остальное — полная таблица свежести, все предупреждения, методика, контрольные показатели,
откат, названия метрик API, сырые данные — в приложении.

## Ограничения среды мониторинга

Яндекс, biz-soft.pro и рекламные кабинеты недоступны напрямую из контейнера (egress) — сеть работает
через GitHub Actions. Контрольные замеры конкурентов через WebSearch (US-прокси) — вспомогательный
сигнал, не позиции.

## Ежедневная процедура (для агента)

0. `git pull`; `git fetch origin main`; синхронизировать `intelligence/seo-experiments.json` с main;
   статусы задач определять по main и по `seo-site-check`, не по прошлому отчёту.
1. Запустить `seo-data-collect.yml`, дождаться коммита данных, `git pull`.
2. `snapshot.py` → `quality.py` → `report_v3.py` → `uxlint.py` → скриншоты → `unittest`.
3. Убедиться, что UX lint и тесты зелёные (иначе письмо не отправляется).
4. Обновить реестры экспериментов; при изменении методики — `docs/seo/reporting-methodology.md`
   и раздел истории в приложении.
5. Коммит и push (перед push `git pull --rebase`) — письмо уходит автоматически.
6. Отправить пользователю preview письма, скриншоты и приложение.
