## 4. Заключение

**Аппаратных ресурсов более чем достаточно — расширять не нужно.**

- CPU загружен на **&lt;2 %** в среднем и &lt;4 % в пике: запас ≈ 25–50-кратный.
- Память: свободно 4+ ГБ, swap и OOM не задействованы ни разу за неделю.
- Диск заполнен на 25 % (реально ~13 % после чистки build-кэша).
- Пиковая нагрузка 0.82 rps — сервер такой конфигурации уверенно держит десятки rps SSR-трафика; текущий трафик можно увеличить в **50–100 раз** без апгрейда.
- Ошибки 5xx: 2 шт. на 33.5 тыс. запросов (0.006 %) — надёжность отличная.

Даунгрейд тарифа возможен (2 vCPU / 4 ГБ хватило бы), но текущий запас разумен под рост каталога и SEO-трафика — менять ничего не рекомендуется.

## 5. Рекомендации по оптимизации (по убыванию пользы)

1. **Очистить docker build cache — освободит ~9.6 ГБ**: добавить в `deploy/deploy.sh` после `docker image prune -f` строку `docker builder prune -f --keep-storage 2GB` (сейчас кэш копится с каждого деплоя: 277 записей).
2. **Срезать сканерный 404-шум (39 % запросов)**: в nginx добавить ранний `return 444` для типовых сканерных путей (`~* \.(php|asp|aspx|env)$`, `/wp-admin`, `/wordpress`, `/xmlrpc.php`, `/.git` и т.п.) и, опционально, для запросов без User-Agent — они перестанут доходить до SSR и засорять статистику. fail2ban уже работает — стоит добавить jail по nginx 404-флуду (адреса вроде 91.214.190.75 с 4.4 тыс. запросов будут баниться автоматически).
3. **Мониторинг под рост**: sysstat уже стоит; при желании — алерт на load>4, mem available<500 МБ и долю 5xx. Достаточно cron-скрипта или бесплатного uptime-мониторинга.
4. **Права на логи**: пользователь `deploy` не входит в группу `adm` — логи nginx пришлось читать обходным путём. `usermod -aG adm deploy` упростит будущую диагностику.
5. Ничего критичного в логах приложений нет: astro/directus без ошибок, контейнеры без рестартов 5+ недель.
