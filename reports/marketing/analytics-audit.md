## 1. Executive Summary

**Можно ли доверять текущей маркетинговой аналитике BIZSoft — нет, в части
конверсий и спроса; да, в части трафика и поисковой видимости, с оговорками.**

Систему нужно оценивать в двух слоях, и они находятся в очень разном состоянии.

**Слой отчётности (`scripts/seo/*`) — зрелый и честный.** Здесь уже сделано то,
что в большинстве проектов не делается никогда: разделены сущности измерения
(`measurement.py`), отсутствие данных отличается от нуля (`snapshot.py`),
работает предпубликационный контроль качества с правилами публикации
(`quality.py`), заведён реестр объявленных пределов измерения
(`measurement-limits.json`), запрещены формулировки «лид» и «рыночный спрос»
без подтверждения. Отчёт V4 сам сообщает читателю, что три конверсионные цели
не измеряются. Этот слой не нужно переделывать — его нужно достроить.

**Слой измерения (сайт → системы аналитики) — сломан на всех конверсиях.**
Именно здесь находятся все P0.

Три факта, установленные по фактическим выгрузкам API:

1. **Ни одна из 23 целей, которые отправляет сайт, не существует в счётчике
   Метрики.** В счётчике 110206070 заведено ровно 4 цели, и все четыре —
   автоцели. Пересечение множества отправляемых имён и множества заведённых
   целей — пустое. Все `reachGoal` уходят в никуда.
2. **Ни одно из двух ключевых событий GA4 не отправляется сайтом.** Как key
   events размечены `form_submit` и `generate_lead`; сайт шлёт `lead_sent`,
   `quote_pdf`, `add_to_cart` и 20 других имён. Пересечение — пустое.
3. **Все зафиксированные GA4 конверсии — визиты владельца сайта.** За всю
   историю сбора GA4 записал 2 key events, и оба пришли из источника
   `metrika.yandex.ru`, то есть с перехода из интерфейса Яндекс.Метрики.
   GA4 классифицирует этот источник как Organic Search.

**Самое опасное — не то, что конверсий ноль, а то, что рядом лежит источник
спроса, который выглядит рабочим и при этом ведёт в другой бизнес.**
51,6 % всего «коммерческого спроса» BIZSoft (252 950 из 490 638 запросов в
месяц) — это кластер `google`, внутри которого 175 387 запросов приходится на
покупку смартфонов Google Pixel и на «google не работает». Отчёт от 21.08
называет этот кластер направлением номер один: «Ближайшее направление: google —
техническое SEO (252 950 запросов в месяц)». Работа по этой рекомендации не
может дать ни одной B2B-заявки на лицензии.

**Какие решения прямо сейчас принимаются на неверных данных:**

| Решение | На чём основано | Почему неверно |
|---|---|---|
| Приоритет SEO-направлений | «google — 252 950 запросов/мес» | 69 % кластера — смартфоны Pixel |
| Объём рынка BIZSoft | «490 638 покупательских запросов/мес» | Завышен: телефоны, кроссовки Nike, суммирование вложенных частотностей Вордстата |
| Оценка покрытия каталога (77 % спроса закрыто страницей) | Доля частотности с `page_exists` | Запросы про Pixel засчитаны как «покрытые» страницей `/vendors/google` |
| Рост видимости в Яндексе «+107 показов» | Разница сумм двух выгрузок | Окна разной длины (13 дн. против 12) + сменилось 26 из 100 запросов выборки |
| Эффективность канала (конверсии) | 6 целевых событий Метрики / 2 key events GA4 | Автоцели + собственные визиты владельца |
| Ценность источника трафика | Метрика/GA4 по каналам | UTM в проекте отсутствуют полностью; заявка не связана с источником |

**Общий вердикт: RED по конверсиям, атрибуции и спросу; YELLOW по трафику и
поисковой видимости; GREEN по методологии отчётов и по безопасности секретов.**

**Ветка данных.** Весь склад маркетинговых данных (`reports/seo/data`,
`snapshots`, `wordstat`) живёт и пишется в ветку
`claude/biz-soft-rating-tracking-5rf03g`, а не в `main`. Сборщик, отчёт и
рассылка привязаны к ней жёстко (`ref:` в трёх workflow, `BRANCH` в
`report_v4.py`). Удаление или переименование ветки уничтожает историю
измерений и останавливает всю отчётность. Это архитектурный риск P1.

## 5. Conversion Funnel

### Фактическая воронка (что измеряется сегодня)

```
Показ в поиске        → Вебмастер (выборка 100 из 506 запросов) / GSC ✓ частично
Клик из выдачи        → Вебмастер (та же выборка) / GSC              ✓ частично
Визит                 → Метрика ym:s:visits / GA4 sessions           ✓
Просмотр страницы     → автоматический page_view                     ✓
Вовлечение            → bounceRate, pageDepth                        ✓
─────────────────────── ниже этой линии измерения нет ───────────────
Интерес к товару      → add_to_cart                                  ✗ цель не заведена
Намерение             → click_get_quote и др.                        ✗ цель не заведена
Заявка                → lead_sent                                    ✗ цель не заведена
КП скачано            → quote_pdf                                    ✗ цель не заведена
Заявка в CRM          → Directus leads                               ✗ не связана с аналитикой
Квалифицированная     → статус лида                                  ✗ не выгружается
Сделка / выручка      → —                                            ✗ отсутствует
```

Воронка обрывается ровно там, где начинается коммерция. Всё, что ниже визита,
не измеряется — при этом бэкенд эти события фактически принимает и сохраняет.

### Ключевая методологическая ошибка уровней

`click_get_quote` (18 мест) — это **клик по кнопке**, после которого
пользователь ещё должен заполнить форму из шести обязательных полей. Если
завести его как цель-конверсию наравне с `lead_sent`, конверсия сайта окажется
завышенной в разы. Уровни обязаны быть разделены:

| Уровень | События | Смысл |
|---|---|---|
| engagement | `view_*_landing`, `click_product_card`, `click_related_link`, `quiz_step`, `open_comparison_table` | посмотрел |
| micro conversion | `add_to_cart`, `quiz_complete`, `form_start` | проявил интерес |
| lead intent | `click_get_quote`, `click_choose_plan`, `click_clarify_price`, `click_request_invoice`, `click_buy_org` | нажал, но не заполнил |
| **lead** | `lead_sent` (HTTP 200 от `/api/lead`), `quote_pdf` (PDF сформирован) | сервер принял заявку |
| qualified lead | статус в Directus ≠ `new`/`spam` | менеджер подтвердил |
| sale | статус `won` + сумма | выручка |

Только два события уровня **lead** имеют право называться конверсией, и оба
привязаны к подтверждённому ответу сервера — это правильное решение,
реализованное в коде (`trackGoal` вызывается только внутри `try` после
проверки `res.ok`). Архитектура фронтенда здесь верна; сломана регистрация
целей на стороне счётчиков.

## 6. Attribution Audit

**UTM-разметка в проекте отсутствует полностью.** Поиск по всему репозиторию
(`src/`, `scripts/`, `.github/`) по `utm_source|utm_medium|utm_campaign|
utm_content|utm_term|yclid|gclid|clientId|client_id` даёт **ноль совпадений**.

Следствия:

1. Заявка, приходящая в `/api/lead`, содержит поля `name, company, email,
   phone, message, product_ref, consent, source, status`. Поле `source` — это
   **не источник трафика**, а идентификатор формы (`pricing`, `question`,
   `quote`, `site`). Его легко спутать с каналом: в письме менеджеру строка
   называется «Источник: pricing».
2. First-touch и last-touch атрибуция не просто конфликтуют — ни одна из них
   не существует. Источник первого касания не сохраняется нигде: ни в
   `localStorage`, ни в скрытом поле формы, ни в cookie.
3. Связать лид с каналом невозможно ни в одну сторону: в Метрике/GA4 нет
   события лида, в CRM нет источника визита.
4. Запуск любой рекламной кампании (Директ, Ads) сегодня даст расход без
   возможности посчитать ROI: `yclid`/`gclid` не перехватываются, автометки не
   переживают навигацию по сайту, в заявку не попадают.

**Наблюдаемые проблемы атрибуции в фактических данных:**

**Один из четырёх сборщиков не проверяет ответ.** В `collect_metrika` и

результат присваивается безусловно:

```python
r = requests.post(..., json=body, timeout=30)
result['analytics'][dims[0]] = r.json()      # collect.py:55 — нет проверки r.ok
```

При 403/429/500 в файл ляжет тело ошибки Google. У него нет ключа `rows`,

→ `impressions_window = 0`. **Ошибка API станет нулём показов.** Проверка
`quality.py` `LOW_IMPRESSION_BASE_GOOGLE` сработает, но её текст — «малая
абсолютная база показов», то есть сбой будет прочитан как падение трафика.

### Окна источников — разной длины и с разным концом

| Источник | Запрошено | Фактически возвращено (21.08) | Задержка |

| Вебмастер (20.08) | `today-14 … today` | `2026-08-06 … 2026-08-17` (12 дн.) | 3 дня |
| Метрика | `today-14 … today-1` | `2026-08-07 … 2026-08-20` (14 дн.) | 1 день |
| GA4 | `today-14 … today-1` | `2026-08-07 … 2026-08-20` (14 дн.) | 1 день |

Задержка Вебмастера **плавает** (2–4 дня), а сборщик всегда просит фиксированные
14 дней от «сегодня». В результате длина фактического окна меняется день ото
дня — 12, 13, 14 дней — и никем не нормализуется.

### Проверка №1 (чтение кода) + Проверка №2 (пересчёт вручную)

Отчёт от 21.08 сообщает: **«Видимость в Яндексе: 967 показов (+107)»**.
Пересчёт по исходным выгрузкам:

```
Выгрузка 20.08: окно 2026-08-06 … 2026-08-17  = 12 дней, сумма 860 показов
Выгрузка 21.08: окно 2026-08-07 … 2026-08-19  = 13 дней, сумма 967 показов
```

1. **Окна разной длины.** Текущее окно на сутки длиннее. Средний день выборки —
   967/13 ≈ 74 показа. Одна лишняя дата объясняет ~74 из 107.
2. **Состав выборки изменился.** Из топ-100 выбыло 26 запросов и вошло 26
   новых. Вошедшие принесли 92 показа, выбывшие унесли 55 → **+37 показов
   создано самой пересборкой списка**, а не ростом видимости.
3. **Знаменатель тоже изменился.** Общее число запросов, о которых знает
   Вебмастер, выросло с 416 до 506, а забирается по-прежнему 100.

74 + 37 = 111 при заявленном приросте 107. **Заявленный рост видимости
полностью объясняется артефактами измерения.** Реальное изменение
неотличимо от нуля.

`quality.py` фиксирует `ROLLING_WINDOW_OVERLAP` и запрещает публиковать
относительные проценты, но абсолютную дельту не запрещает — а испорчена
именно она.

### Согласованность GSC между разрезами

Одна и та же выгрузка от 21.08, один и тот же период:

| Разрез | Строк | Показов | Кликов |
|---|---|---|---|
| `date` | 26 | 114 | 1 |
| `query` | 30 | 47 | 1 |
| `page` | 36 | 138 | 1 |

Расхождение нормально для GSC (анонимизация запросов, разное определение
строки), но в разрезе `query` видно лишь 41 % показов. Любой «CTR по запросам»,
посчитанный от суммы `query`, и любое сравнение с общим числом кликов из
`date` дадут несопоставимые величины. Сейчас `snapshot.py` берёт `impressions_window`
из `date`, а `queries_tracked` из `query` — величины из разных множеств лежат в
одном блоке `totals` без пометки.

### Скрытая хрупкость `daily[-7:]`

`snapshot.build_google` берёт последнюю неделю срезом по индексу строк:
`last7, prev7 = daily[-7:], daily[-14:-7]`. Сегодня это работает: GSC вернул
26 строк подряд без пропусков и в возрастающем порядке дат. Но GSC **не
возвращает дни с нулевыми показами**, и порядок строк документирован как
сортировка по метрике, а не по дате. Как только у сайта появятся клики или
день без показов, «последние 7 строк» перестанут быть последними 7 днями, и
недельное сравнение сместится молча.

### Zero ≠ No data — где правило соблюдено и где нарушено

| Место | Состояние |
|---|---|
| `snapshot.py` — доктрина «None = нет данных, 0 = измеренный ноль» | ✓ объявлено и соблюдается |
| `measurement-limits.json` ANL-001 | ✓ ноль по трём целям объявлен как «не измерялось» |
| `collect_metrika` / `collect_ga4` — ошибка → `{'error': ...}` | ✓ |
| `collect_gsc` — ошибка API → тело ошибки → `rows=[]` → 0 показов | ✗ **нарушено** |
| `coverage.py` `conversion_measured: 0.0` | ✗ **нарушено**: конверсии не измеряются вовсе, но уровень покрытия выдан как измеренный ноль рядом с `qualified_leads: null` |
| `drivers.decompose` — `cv = (c or {}).get(metric) or 0` для выбывшей сущности | ✗ выбытие из выборки трактуется как падение до нуля |

нельзя.

появятся клики (порядок строк изменится) или день без показов (пропуск даты).
Оба события ожидаемы по мере роста.

**Business impact.** Недельные сравнения молча сместятся; заметить это по
отчёту будет невозможно.

**Recommended fix.** Строить `daily` по календарю: заполнять отсутствующие
даты нулями явным флагом `measured: false`, срез делать по датам, а не по
индексам.

**Verification method.** Юнит-тест: вход с пропущенной датой и перемешанным
порядком строк даёт корректные `last7`/`prev7`.

### MKT-015 · P2 · Timezone

**Problem.** Заявленный часовой пояс отчётности не совпадает ни с политикой
компании, ни с часовым поясом источников.

**Evidence.**
`scripts/seo/snapshot.py:22` — `TIMEZONE = "Asia/Bishkek (UTC+6)"`.
`CLAUDE.md`: «Часовой пояс: письма и расписания — по Москве… Бишкек (UTC+6) по
умолчанию НЕ использовать».
GA4 `metadata.timeZone` в каждой выгрузке — `Europe/Moscow`.
`seo-data-collect.yml` — `cron: "40 2 * * *"` с комментарием «02:40 UTC
(08:40 Бишкек)»; 02:40 UTC — это 05:40 МСК.
`collect.py:22` — `TODAY = dt.date.today()` на раннере, то есть в UTC.

**Why it matters.** «Сегодня» различается между именем файла (UTC),
данными GA4/Метрики (МСК) и заявленным поясом отчёта (UTC+6). При запуске
между 21:00 и 00:00 МСК имя файла и содержимое разойдутся на сутки.

**Business impact.** Пока сбор идёт в 05:40 МСК, расхождение не проявляется —
но любой ручной прогон вечером или сдвиг расписания даст файл с чужой датой,
и сравнение периодов сломается незаметно.

**Recommended fix.** Задать `TIMEZONE = "Europe/Moscow (UTC+3)"`, вычислять
`TODAY` в московском поясе (`ZoneInfo("Europe/Moscow")`), поправить
комментарий cron на «02:40 UTC = 05:40 МСК».

**Verification method.** Прогон `collect.py` с `TZ=UTC` в 22:00 МСК даёт файл
с московской датой.

### MKT-016 · P2 · GA4

**Problem.** Параметры событий не зарегистрированы как custom dimensions.

**Evidence.** `trackGoal` передаёт `sku`, `source`, `page_url`, `block_name`,
`quote_no`. В GA4 Admin ничего, кроме key events, не настраивается
(`seo-ga4-admin.yml` создаёт только keyEvents). `collect_ga4` запрашивает
только `sessionDefaultChannelGroup`, `sessionSource`, `landingPage`.

**Why it matters.** Параметр, переданный в событии, не появляется в
стандартной аналитике GA4 и недоступен Data API, пока не зарегистрирован как
custom dimension. Даже после починки MKT-001/MKT-006 разрез «заявки по вендору
и sku» останется недоступным.

**Business impact.** Невозможно построить обязательную для BIZSoft аналитику
vendor/product (раздел 16 задания).

**Recommended fix.** Зарегистрировать event-scoped custom dimensions: `sku`,
`vendor`, `form_source`, `block_name`; добавить их в запросы `collect_ga4`.

**Verification method.** `GET properties/543500233/customDimensions` содержит
все четыре; Data API возвращает их как `customEvent:sku` и т. д.

### MKT-017 · P2 · Consent / Privacy

**Problem.** Аналитика и Вебвизор запускаются до получения согласия;
cookie-баннер декоративный.

**Evidence.** `BaseLayout.astro:67–68` — `<Analytics />` рендерится всегда,
`<CookieNotice />` — отдельным компонентом ниже. `CookieNotice.astro`:
единственное действие кнопки — `localStorage.setItem('bizsoft_cookie_ok','1')`
и `el.hidden = true`. Ни один счётчик не зависит от этого состояния.
Вебвизор включён (`webvisor:true`) и записывает сессии до согласия.

**Why it matters.** Вебвизор пишет содержимое страниц и взаимодействия с
формами. Формы содержат ФИО, e-mail, телефон, ИНН, наименование организации.
Маскирование полей в коде не настраивается — используется поведение Метрики по
умолчанию, что нигде не задокументировано и не проверено.

**Business impact.** Регуляторный риск (152-ФЗ) и репутационный риск. На
качество данных влияет слабо (для РФ-аудитории блокировщики бьют сильнее), но
это единственная находка с юридическим измерением.

**Recommended fix.** (1) Проверить в интерфейсе Метрики, что поля форм
маскируются в Вебвизоре, и зафиксировать это как настройку. (2) Либо связать
`bizsoft_cookie_ok` с инициализацией счётчиков, либо привести текст баннера в
соответствие с фактом (уведомление, а не запрос согласия) — но тогда
маскирование обязательно.

**Verification method.** (A) Запись Вебвизора по тестовой заявке — поля ФИО,
телефон, e-mail замаскированы. (B) Просмотр `/privacy` на предмет упоминания
записи сессий.

### MKT-018 · P2 · Reporting

**Problem.** Проверка живого сайта считывает фактические счётчики прода, но
результат никуда не попадает.

**Evidence.** `.github/workflows/seo-site-check.yml:31–37` выполняет
`grep -o 'gtag/js?id=[A-Z0-9-]*'` и `grep -o 'metrika/tag.js?id=[0-9]*'` по
главной странице прода и печатает результат в лог шага. Сохраняемый JSON
(`site-check-2026-08-21.json`) содержит только блок `experiments`; ID счётчиков
в нём отсутствуют. Ни один шаг не падает при несовпадении.

**Why it matters.** Это единственная в проекте проверка «что реально отдаёт
прод». Её результат — единственный способ поймать, например, деплой без
`PUBLIC_METRIKA_ID` или второй счётчик. Сейчас он теряется в логе, который
никто не читает.

**Business impact.** Поломка тега на проде будет обнаружена только по
исчезновению трафика в отчётах, то есть через несколько дней.

**Recommended fix.** Сохранять в JSON `metrika_ids`, `ga_ids`, число
вхождений каждого; падать со статусом ошибки, если множество не равно
`{110206070}` и `{G-V9BK2D1431}` соответственно; передавать блок в снимок и в
раздел «Здоровье данных».

**Verification method.** Прогон workflow — в JSON появились ID; подмена
ожидаемого значения роняет job.

### MKT-019 · P3 · Data Quality

**Problem.** Разбор драйверов изменения работает на шумовых величинах и
трактует выбытие сущности как падение до нуля.

**Evidence.** `drivers.py`: `MIN_ABS = 2`, `MIN_SHARE = 0.05`;
`cv = (c or {}).get(metric) or 0` — сущность, выбывшая из выборки топ-100,
получает текущее значение 0 и попадает в детракторы. Отчёт 21.08 называет
драйверами `/vendors/blackmagic (+4)` и `/vendors/openai (+2)` при недельной
базе Google в 38 показов.

**Why it matters.** Дельта в 2–4 показа на такой базе неотличима от
пуассоновского шума. Для Яндекса добавляется MKT-005: выбытие из выборки
неотличимо от падения показов.

**Business impact.** Ложная причинность: страница «выросла» или «упала» без
единого реального изменения.

**Recommended fix.** Поднять `MIN_ABS` до величины, зависящей от базы
(например, `max(3, 0.05 × total)`), и для Яндекса помечать `state:"lost"`
отдельным статусом «выбыл из выборки», а не нулём.

**Verification method.** Юнит-тест: сущность, отсутствующая в текущей выборке,
не попадает в детракторы, а получает статус выбытия.

### MKT-020 · P3 · Data Quality

**Problem.** Синтетический трафик от `ops-screenshot` исполняет JS на проде.

**Evidence.** `ops-screenshot.yml` работает через Playwright по адресу
`https://biz-soft.pro/`. `ops-perf.yml` и `seo-site-check.yml` используют
`curl` — JS не исполняется, счётчики не срабатывают.

**Why it matters.** Playwright-визит даёт полноценный `page_view` и, на
лендинге вендора, автоматический `view_vendor_landing`.

**Business impact.** Минимальный при ручном запуске, но на базе ~7 визитов в
день каждый лишний визит — это 14 % дневного трафика.

**Recommended fix.** Добавлять к URL `?internal=1` и исключать этот параметр
фильтром в GA4/Метрике, либо блокировать домены счётчиков через
`page.route()`.

**Verification method.** Прогон workflow не меняет счётчик визитов за день.

### MKT-021 · P3 · API

**Problem.** Идентификаторы счётчиков в сборщике и на сайте не сверяются.

**Evidence.** Сайт использует хардкод `110206070` и `G-V9BK2D1431`
(`src/lib/analytics.ts:17,19`). Сборщик использует секреты
`YANDEX_METRIKA_COUNTER_ID` и `GA4_PROPERTY_ID` (`543500233`). Ничто не
проверяет, что это тот же счётчик и тот же поток. Фактически на 21.08
значения совпадают (`counter: 110206070` в выгрузке).

**Why it matters.** ID счётчика Метрики публичен по природе (он в HTML), но
хранится как секрет — это не даёт защиты и создаёт возможность расхождения.
`GA4_PROPERTY_ID` (число 543500233) и Measurement ID (`G-V9BK2D1431`) — разные
сущности; их соответствие не проверено ничем.

**Business impact.** При расхождении отчёты будут собираться из другого
счётчика и выглядеть правдоподобно.

**Recommended fix.** Сверять в начале сбора: `YANDEX_METRIKA_COUNTER_ID` ==
`110206070`; для GA4 — запросить `properties/543500233/dataStreams` и убедиться,
что среди потоков есть `G-V9BK2D1431`. Несовпадение — critical в
`data_health`.

**Verification method.** Прогон с подменённым секретом падает.

## 13. Может ли система ответить на вопрос маркетолога

**Вопрос:** «Какие 20 продуктов BIZSoft реально имеет смысл продвигать в первую
очередь?»

**Ответ: нет, доказательно — не может.** Разбор по компонентам ответа:

| Компонент | Есть? | Состояние |
|---|---|---|
| search demand | ⚠ | Есть Wordstat, но загрязнён (MKT-002, MKT-003) и переучтён (MKT-012) |
| impressions | ⚠ | Вебмастер — выборка 100/506; GSC — есть, но Google для сайта почти не работает |
| ranking | ✓ | `AVG_SHOW_POSITION` по выборке, `position` по GSC |
| CTR | ⚠ | Только как «CTR выборки», честно помечено |
| sessions | ✓ | Метрика + GA4 |
| engagement | ⚠ | `bounceRate`, `pageDepth` — только по посадочным, не по товару |
| CTA | ✗ | События есть в коде, целей нет |
| leads | ✗ | Не измеряются |
| conversion | ✗ | Не измеряется |
| commercial intent | ⚠ | Классификатор есть, но даёт «google не работает» = commercial |
| margin / revenue | ✗ | Цены в Directus есть, к аналитике не подключены |

Из одиннадцати компонентов четыре отсутствуют полностью, пять требуют
исправления. Сегодня система может ответить только на более слабый вопрос:
«по каким запросам мы уже показываемся высоко, но не получаем переходов» — и
она на него отвечает (блок «Где ближе всего рост»: `heygen тарифы`,
`оплата depositphotos для юридических лиц из россии`). Это полезный, но
принципиально более узкий ответ, чем требуется.

**Что нужно, чтобы ответ стал возможен** — по порядку: MKT-001 (цели) →
MKT-004 (атрибуция) → MKT-016 (custom dimensions) → выгрузка Directus `leads`
в снимок → MKT-002/003/012 (чистка спроса). После этого связка
`запрос → посадочная → сессия → товар → CTA → заявка → сделка` становится
вычислимой.

## 14. Готовность к рекламным экспериментам

Отчёт помечает «Рекламный тест — заблокировано, остановлено правилом». Аудит
подтверждает: **решение верное**, а причина — MKT-004.

Требуемая цепочка `AD QUERY → AD → LANDING → PRODUCT → CTA → LEAD`:

| Звено | Готово? |
|---|---|
| AD QUERY → AD | ✗ рекламный кабинет не подключён |
| AD → LANDING (`yclid`/`gclid`) | ✗ автометки не перехватываются |
| LANDING → PRODUCT | ✓ навигация отслеживается Метрикой |
| PRODUCT → CTA | ✗ цель `click_get_quote` не заведена |
| CTA → LEAD | ✗ цель `lead_sent` не заведена |
| LEAD → источник | ✗ UTM не доходят до Directus |

Запускать платный тест до закрытия MKT-001 и MKT-004 нельзя: расход будет
неизмерим. Оба закрываются быстро — это аргумент за то, чтобы делать их первыми.
