# BIZSoft Analytics Verification Checklist

**Назначение.** Повторяемый regression-чеклист маркетинговой аналитики.
Прогоняется после каждого изменения сайта, счётчиков, сборщиков и отчётов.

**Принцип.** Каждый критичный пункт проверяется **двумя независимыми
способами**: метод A — статический (код, конфигурация), метод B —
фактический (ответ API, живая страница, ручной пересчёт). Пункт считается
пройденным только если оба метода дали согласованный результат.

**Когда прогонять:**

| Событие | Разделы |
|---|---|
| Деплой сайта в `main` | A, B, C |
| Изменение форм или API заявок | B, C, F |
| Изменение целей в Метрике / key events в GA4 | A, C, H |
| Изменение `scripts/seo/**` | D, E, G |
| Еженедельно, планово | всё |
| При подозрительном числе в отчёте | E, G |

## J. Синтетические сценарии

Прогонять после каждого изменения форм и после закрытия MKT-001/MKT-004.
Каждый сценарий проверяется по **обеим** сторонам: событие в аналитике **и**
запись на бэкенде.

| # | Сценарий | Ожидаемая цепочка | Проверка на бэкенде |

| J-1 | Органика → товар → CTA → форма → успех | `page_view → view_item → click_get_quote → form_start → lead_sent` | заявка в Directus, `status: new` |

## K. Спецификация автоматических проверок

Предлагается добавить в CI (`.github/workflows/ci.yml`, шаг «Проверки
аналитики») и в предпубликационный слой (`scripts/seo/quality.py`).
Сегодня ни одна проверка аналитики в CI не выполняется: `pnpm test`, `smoke`
и `check:artifacts` не содержат ни одного утверждения о счётчиках или целях.

### K-1. Статические проверки кода (CI, блокирующие)

| Тест | Условие провала |
|---|---|
| `analytics.single-loader` | `<Analytics />` встречается в layout больше одного раза |
| `analytics.ids-present` | `METRIKA_ID` или `GA_ID` пусты либо схлопываются в `undefined` |
| `analytics.no-pii` | payload `trackGoal` содержит `email`, `phone`, `name`, `inn` |
| `analytics.ev-handler` | файл содержит `data-ev=` без привязки слушателя |
| `analytics.known-events` | имя цели отсутствует в реестре measurement plan |
| `analytics.required-params` | событие уровня `lead` отправлено без обязательных параметров |
| `analytics.goal-after-ok` | `trackGoal` уровня `lead` вызывается вне ветки успеха |
| `metrics.single-formula` | `opportunity_score` присваивается более чем в одном модуле |

### K-2. Проверки соответствия кода и счётчиков (ежедневно, после сбора)

| Тест | Условие провала |
|---|---|
| `goals.declared-vs-configured` | имя цели из кода отсутствует в `goals_configured` снимка — **закрывает MKT-001 навсегда** |
| `ga4.keyevents-vs-code` | key event GA4 не отправляется кодом |
| `ga4.custom-dimensions` | параметр события не зарегистрирован как custom dimension |
| `counters.match` | счётчик сборщика ≠ счётчику сайта ≠ счётчику на проде |

Данные для `goals.declared-vs-configured` **уже собираются**:
`snapshot.build_analytics` кладёт `goals_configured` в снимок, а имена целей
извлекаются из `src/` регулярным выражением. Проверки нет — при её наличии
MKT-001 был бы обнаружен в день появления.

### K-3. Проверки данных (в `quality.py`, до генерации отчёта)

| Код находки | Уровень | Условие |
|---|---|---|
| `API_ERROR_AS_ZERO` | critical | выгрузка без `error`, но и без `rows` ни в одном разрезе |
| `WINDOW_LENGTH_MISMATCH` | critical | `current_period_days ≠ comparison_period_days` |
| `SAMPLE_CHURN` | warning | сменилось > 10 % сущностей выборки между снимками |
| `SAMPLE_TRUNCATED` | warning | `fetched < count` у источника |
| `STALE_DATA` | warning | `latest_event_date` старше 4 дней |
| `TIMEZONE_MISMATCH` | warning | пояс снимка ≠ поясу источника (`metadata.timeZone`) |
| `INTERNAL_TRAFFIC_IN_ORGANIC` | warning | среди `organic_sources` есть `metrika.yandex.ru`, `webmaster.yandex.ru`, `alice.yandex.ru` |
| `GOAL_NOT_CONFIGURED` | critical | код шлёт цель, которой нет в счётчике |
| `EMPTY_DATASET` | warning | ответ API успешен, но `rows` пуст при непустом предыдущем замере |
| `FRONTEND_BACKEND_DRIFT` | critical | расхождение `lead_sent` и записей Directus > 10 % |

### K-4. Новые правила публикации

Добавить в `publication_rules`:
`allow_absolute_delta` (снимается при `WINDOW_LENGTH_MISMATCH`/`SAMPLE_CHURN`),
`allow_channel_conversion_claims` (снимается при `INTERNAL_TRAFFIC_IN_ORGANIC`),
`allow_conversion_wording` (снимается при `GOAL_NOT_CONFIGURED`).

## L. Форма протокола прогона

```
Дата прогона:            ______   Кто:  ______
Повод:                   деплой / изменение целей / плановый / расследование
Разделы:                 A B C D E F G H I J
Пройдено:                __ / __
Не пройдено (ID):        ______
Открыто новых находок:   ______
data_health на дату:     verified / limited / degraded
Записи в measurement-limits.json изменены:  да / нет
```

Протокол хранить рядом с отчётом дня —
`reports/seo/intelligence/verification-<дата>.md`.
