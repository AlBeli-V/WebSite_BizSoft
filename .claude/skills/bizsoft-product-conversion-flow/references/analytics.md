# Воронка карточки

## Последовательность

```
view_product → product_interaction → add_to_cart → form_open → form_start → lead_sent
```

Имена — из реестра `src/lib/analytics.ts`, а не из методики. Реестр
единственный: цель, вызванная в коде и не заведённая в кабинете Метрики,
принимается счётчиком и в отчёте не существует; два имени на один шаг делят
каждый отчёт пополам. Обе ошибки уже случались, обе стерегутся тестами
`tests/analytics-goals.test.ts` и `tests/analytics-contract.test.ts`.

| Шаг методики | Цель проекта | Где отправляется |
|---|---|---|
| product_view | `view_product` | карточка, при загрузке |
| product_interaction | `product_interaction` | карточка, первое осмысленное действие |
| — | `add_to_cart` | кнопка «Добавить в расчёт» |
| quote_cta_click | `form_open` | окно заявки открылось |
| form_start | `form_start` | первый ввод в поле |
| lead_sent | `lead_sent` | после `res.ok`, не раньше |

Отдельной цели на клик по призыву нет: призыв открывает окно заявки, и
`form_open` считает ровно это. Заводить рядом второе имя — тот самый раскол
отчёта.

## product_interaction

Первое осмысленное действие в карточке: смена количества, прикидка на
команду, раскрытие вопроса, разворот описания. Вид действия — в параметре
`kind`. Отправляется **один раз за загрузку** (`trackGoalOnce`): дальше эти
действия считаются своими целями, а размноженная цель задвоила бы шаг.

Цель заведена решением руководителя 12.09.2026.

## Как новая цель попадает в кабинеты

Руками — никак. Реестр в коде единственный, и из него цели заводит
`scripts/seo/goals_sync.py` через workflow `seo-goals-sync`: сначала сухим
прогоном (`apply=false`) — он покажет, чего не хватает, — потом заведением
(`apply=true`). Запуск только с `main` (правило
`docs/rules/production-workflow-main-only.md`), то есть **после слияния**
ветки. Скрипт ничего не удаляет: снятая по ошибке цель обнуляет историю.

Порядок для новой цели: запись в `GOALS` → вызов в коде → слияние в `main` →
сухой прогон `seo-goals-sync` → `apply=true` → запись о прогоне уходит в
issue #22. Пропущенный последний шаг и есть та самая потерянная конверсионная
статистика (ANL-001): сайт шлёт, кабинет не ждёт, в отчёте ноль.

## Версия схемы

События воронки карточки несут `analytics_schema_version: 'pcf_v3'`. Метка
описывает воронку карточки, а не весь сайт: ставить её на события каталога,
лендингов и корзины нельзя — это подписало бы их схемой, к которой они не
относятся. Меняется состав шагов карточки — поднимается версия, и старые
данные остаются сопоставимыми внутри своей.

## События новых механик

Заводятся в реестре вместе с решением руководителя, до этого в коде их нет:

| Событие | Когда |
|---|---|
| `quote_collection_add` | позиция добавлена в подборку КП |
| `quote_collection_remove` | позиция убрана |
| `quote_collection_open` | подборка открыта |
| `quote_collection_submit` | запрошено единое КП по подборке |
| `assistance_cta_click` | нажата помощь с выбором — это не запрос КП |
| `multi_seat_open` | блок расчёта объёма показан на экране |

Разделять `assistance_cta_click` и обычный призыв обязательно: это разные
намерения, и смешивать их в одно число значит потерять долю сомневающихся.

На макете аналитика не подключается вовсе: фиктивные события в боевом
счётчике портят ту самую статистику, ради которой цели заводятся.

## Жёсткие правила

- Цель уровня заявки отправляется только после успешного ответа сервера.
- Одно действие не шлёт цель дважды: кнопка с `data-goal` не вызывает
  `trackGoal` сама, обработчик `data-ev` и `data-goal` живёт один на сайт, в
  `src/layouts/BaseLayout.astro`.
- Одно понятие — одно имя параметра (`form_source`, не `source`).
- Персональные данные в параметры целей не попадают никогда: ни почта, ни
  телефон, ни ИНН. Поля ввода ПДн несут класс `ym-disable-keys`
  (правило `docs/rules/webvisor-masking.md`).
- Каждая форма передаёт атрибуцию на сервер (`attributionPayload()`).
