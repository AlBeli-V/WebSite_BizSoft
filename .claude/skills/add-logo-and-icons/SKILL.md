# Добавление logo and icons

Выполняй задачу в текущей рабочей ветке репозитория BIZSoft. Не ограничивайся созданием файлов: задача завершена только после корректной привязки по слагам, технических проверок, визуального QA и проверки затронутых поверхностей сайта.

## Два основных сценария

### Сценарий A — новый производитель и/или товары
Пользователь обычно пишет: «Создан новый производитель X и товары Y, Z — добавь соответствующие иконки».

1. Зафиксируй текущую ветку и HEAD.
2. Сравни критичные пути/структуру с текущим `main`, но не переключай ветку, не merge/rebase без явного запроса.
3. Найди заведённого вендора/товары и их финальные слаги.
4. Определи, нужны ли отдельные product marks или штатно достаточно vendor fallback.
5. Найди/переиспользуй официальные assets, создай недостающие пары color/mono.
6. Обнови нужные карты/алиасы/манифесты.
7. Выполни build/tests + обязательную визуальную проверку.
8. Покажи краткий отчёт: что добавлено, что переиспользовано, какие поверхности проверены, есть ли нерешённые вопросы.

### Сценарий B — исправление визуальной ошибки
Пользователь обычно пишет: «На сайте у производителя X неправильная/растянутая/не та иконка — исправь».

1. Сначала определи, какой из четырёх каналов фактически выигрывает по приоритету рендера.
2. Не добавляй новый файл в более низкий канал, если выше уже существует asset и продолжит его перекрывать.
3. Сохрани существующий ключ/имя файла, если меняешь asset в том же канале.
4. Если пользователь приложил эталон, считай его `USER_APPROVED_ASSET`.
5. Перегенерируй производные данные только там, где это требуется текущим каналом.
6. Проверь color/mono, hover, карточку/лендинг и другие поверхности, где этот asset используется.

### Сценарий C — импорт списка из файла
Пользователь прикладывает Excel/CSV/Markdown со списком вендоров/товаров: «добавь недостающие иконки по файлу».

1. Нормализуй список: `python scripts/parse_catalog.py <файл> [--exclude ...] [--json out.json]` (поддерживает CSV и XLSX; Markdown-таблицу сначала приведи к CSV).
2. Сверь каждую пару vendor/product с Directus и `src/data/vendors.ts`: работай только с заведёнными сущностями и финальными слагами. Позиции, которых нет в каталоге, сам не заводи — вынеси в отчёт как «требуют заведения».
3. Далее для каждой недостающей иконки действуй по сценарию A; одинаковые product marks — один canonical asset, без дубликатов по SKU.

## Сначала изучить текущую архитектуру

Перед изменениями прочитай `references/bizsoft-graphics-pipeline.md`. Этот файл описывает проверенный срез архитектуры ветки `claude/ai-catalog-redesign-fu0cik`, commit `be8b8aa` от 21.08.2026. Пути могли измениться — используй его как карту системы, но всегда сверяй с текущим кодом.

Ключевой принцип: в проекте четыре независимых канала графики и жёсткий приоритет рендера. Нельзя считать, что «файл положен — значит он появится».

## Правила поиска и выбора asset

Используй источник в таком порядке:
1. официальный brand/press kit правообладателя;
2. официальный сайт/официальный CDN продукта;
3. официальная документация/marketplace правообладателя;
4. вторичный logo repository — только если официального источника нет.

Для каждого asset зафиксируй статус:
- `OFFICIAL_VENDOR_MARK`
- `OFFICIAL_PRODUCT_MARK`
- `VENDOR_FALLBACK`
- `USER_APPROVED_ASSET`
- `UNRESOLVED`

`UNRESOLVED` автоматически на сайт не устанавливай.

Не генерируй вымышленный логотип бренда. Не выполняй автотрейсинг растрового оригинала. Если источник raster — встраивай его в самодостаточный SVG или используй официальный raster в поддерживаемом текущим каналом формате.

## Типовая модель vendor/product

- Вендор: предпочитай полный официальный logo/wordmark, если он читаем на поверхности сайта.
- Продукт: предпочитай компактный официальный product mark.
- Если несколько SKU используют один и тот же mark, создавай один canonical asset и переиспользуй через `product-icon-map.json`/эквивалент.
- Не плодить одинаковые SVG по числу тарифов.
- Если у продукта нет отдельного официального знака, штатный fallback на vendor icon допустим и не считается дефектом.

## Стандарт pair assets

Для пакетных vendor/product иконок:
- `512x512`, прозрачный фон;
- сохранить пропорции, не растягивать;
- safe zone 12.5% как базовый стандарт для новых подготовленных файлов;
- обязательно color + mono;
- mono должен быть реально монохромным; CSS grayscale — страховка, а не замена правильному asset;
- светлый знак обязан читаться на белой карточке;
- wordmark-only нельзя механически растягивать на квадрат — подбирать/готовить подходящий compact mark либо фиксировать `UNRESOLVED`.

## Обязательный визуальный gate

Технически валидный SVG не считается готовым.

1. Создай contact sheet по всем изменённым color/mono assets (`scripts/make_contact_sheet.py` либо текущим эквивалентом).
2. Отрендери его и визуально проверь каждую пару.
3. Проверь реальные поверхности сайта локально через Chromium/Playwright, если окружение позволяет.
4. Проверь hover mono→color.
5. Исправь до PASS:
   - растяжение/искажение;
   - clipping/cropping;
   - слишком маленький знак;
   - фон/шахматка/водяной знак внутри изображения;
   - неправильный бренд;
   - vendor wordmark вместо известного product mark;
   - неправильный mapping slug→icon;
   - одинаковый asset размножен по SKU вместо reuse.

Если доступен предустановленный Chromium, используй путь из `references/bizsoft-graphics-pipeline.md`; не переустанавливай браузер без необходимости.

## Техническая проверка

Минимально:
- `python scripts/validate_repo_icons.py <repo-root>` — проверка пар color/mono, карт и базовой структуры;
- если пользователь передал внешний пакет ассетов (папка/архив вне репозитория) — сначала `python scripts/validate_assets.py <package-root>`; шаблон манифеста такого пакета: `assets/manifest.template.json`;
- `npx vitest run`;
- `npx astro check` — 0 ошибок;
- при изменении канала `public/brand-logos` — `node scripts/build-logos.mjs`;
- локальный render/screenshots затронутых поверхностей.

При несовпадении с текущим репозиторием сначала адаптируй проверку к фактической структуре, а не ломай архитектуру под старый snapshot.

## Запрещено

- Не править `src/data/logos.ts` вручную — он автогенерируемый.
- Не класть vendor icon в `public/`, если корректный путь — пакет `src/assets/vendor-icons`.
- Не создавать product icon «на всякий случай», если vendor fallback — правильная модель.
- Не переименовывать существующие файлы ради косметического единообразия: имя является ключом.
- Не менять slug после привязки иконки без одновременного исправления карт/алиасов.
- Не подтверждать успех только по наличию файла или локальному build.
- Не merge/deploy в `main` без явного разрешения пользователя.

## Финальный отчёт

Отчёт пишется на русском (правило проекта «Язык общения: только русский»); технические метки статусов (PASS/FAIL и т.п.) остаются как есть. Верни компактно:

```text
ОТЧЁТ: LOGO & ICONS
Ветка/HEAD: <branch> / <sha>
Тип запроса: NEW | FIX | REBRAND | IMPORT
Затронуто вендоров: <n>
Затронуто товаров: <n>
Переиспользовано canonical assets: <n>
Новых/заменённых assets: <n>
Fallback: <n>
Unresolved: <n>
QA пар color/mono: PASS|FAIL
Техническое QA: PASS|FAIL
Визуальное QA contact sheet: PASS|FAIL
Визуальное QA сайта: PASS|NOT RUN|FAIL
Изменённые пути: <краткий список>
Нужны решения руководителя: <нет / краткий список>
```

Не называй задачу готовой при `FAIL` и не скрывай `NOT RUN`.
