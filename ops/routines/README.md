# Операционные Routine: реестр и самовосстановление

Установлено руководителем 03.09.2026: контур операционных прогонов работает
на автомате — без обращений к руководителю и без тревог, пока чинится сам.

## Зачем это здесь

Routine (расписания Claude) живут не в репозитории, а в аккаунте, и их
состояние ниоткуда не следует. Дважды подряд — 02.09 и 03.09.2026 — контур
вставал молча: Routine формально была настроена правильно, а прогон уходил в
сессию без рабочей копии репозитория и без GitHub MCP. Поэтому здесь лежит
**реестр** `registry.json` — источник истины, к которому живое состояние
приводится ежедневно, и **промпты** в `prompts/`, которые проходят ревью в PR,
а не правятся вслепую в интерфейсе.

## Как это работает

- `registry.json` — какие Routine должны существовать: имя, расписание, файл
  промпта, модель, теги сессии-исполнителя, ветка данных контура.
- Ежедневный сторож **routine-health** (10:00 МСК) читает реестр из `main`,
  сверяет с живым состоянием и приводит его к реестру: заводит сессию-исполнителя
  с `source_url`, проверяет её карточку, пересоздаёт Routine, удаляет старую.
- Сторож не может починить сам себя — сломанная Routine не запускается. За ним
  присматривает ночная **serp-catchup** (02:45 МСК): у неё в промпте есть раздел
  «Взаимный присмотр за сторожем».
- Записи с `"autoheal": false` сторож не пересоздаёт: они привязаны к рабочим
  сессиям с накопленным контекстом. Их поломка идёт в журнал с меткой alert.

## Правило приёмки

Привязку подтверждает **карточка сессии-исполнителя**, а не флаг Routine.
`persist_session: true` и непустой `persistent_session_id` не значат ничего:
идентификатор может указывать на несуществующую сессию, а может — на сессию,
которую планировщик выпустил на лету при первом срабатывании, без репозитория.

Здорова привязка, только если `get_session` по `persistent_session_id`:

1. вернул сессию (не «the requested resource was not found»);
2. в `session_context.sources` есть `git_repository` нужного репозитория;
3. в `tags` нет `config:routine-lineage-none` и `routine:agent-minted`;
4. `origin` — `claude_code_mcp_seed` или `web_claude_ai`, но не
   `scheduled_trigger` и не `force_run_trigger`.

**`fire_trigger` для приёмки не годится.** Ручной запуск игнорирует
`persistent_session_id` и заводит отдельную сессию с `origin: force_run_trigger`,
пустыми `sources` и метками минтованной сессии — ровно ту калеку, от которой
контур уходит. Приёмка идёт по первому срабатыванию **по расписанию**: у
исправной привязки сдвигается `updated_at` самой сессии-исполнителя. Признак
обойдённой привязки — свежий `last_fired_at` при неподвижном исполнителе.

## Порядок восстановления

1. `create_session`: `source_url` репозитория, `environment_id`, `model`, `tags`
   и `title` из реестра, плюс подготовительный прогон — новая сессия должна
   тремя строками подтвердить рабочую копию, ветку данных и `mcp__github__*`.
2. `get_session` по новой сессии — `session_context.sources` заполнены. Не
   заполнены — сессию не использовать, повторить (не более трёх попыток).
3. `create_trigger`: `name` и `cron_expression` из реестра,
   `persistent_session_id` новой сессии, `prompt` — полный текст файла из
   `prompt_file`, без сокращений.
4. `delete_trigger` старой Routine, старую сессию `archive_session` (отказ
   «not found» — не ошибка).
5. Приёмка — по следующему срабатыванию расписания, как выше.

`update_trigger` промпт привязанной Routine менять отказывается («editing the
prompt of a routine whose fires deliver into a session that is not your own is
not available via this tool») — только пересозданием. Поэтому правка промпта в
`prompts/` вступает в силу не сразу: её разносит сторож, когда пересоздаёт
контур. Чтобы применить правку немедленно, пересоздайте Routine вручную тем же
порядком.

## Тишина

Руководителю не пишет ничего, кроме деловых результатов (письмо конкурентной
разведки, письмо Growth Committee — они уходят почтовыми workflow). Всё
инфраструктурное идёт в журнал-issue #22: одна запись, только когда что-то
делалось. Метка `alert` — только для контуров с `autoheal: false` и для
починки, не удавшейся после трёх попыток.

Проверка: `pnpm test` прогоняет `tests/ops-routines-registry.test.ts` — реестр
разбирается, у каждой записи с `autoheal: true` есть существующий файл промпта,
cron корректен, имена уникальны.
